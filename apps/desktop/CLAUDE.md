# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**harpyhare** — a Tauri 2 desktop app для **macOS 14.2+ и Windows 10 версии 2004+** (процесс маскируется под «Audio System», бренд `harpyhare` — только в UI). Hold a push-to-talk key → capture **system audio** (e.g. voice from a video) → transcribe via Groq Whisper → edit the text (with pasted screenshots) → stream an answer from the Anthropic API.

**Окон два, и это главное, что надо знать про структуру фронта.** Приложение стартует с **лаунчера** (`launcher.html` → `src/launcher.tsx` → `features/launcher/LauncherApp`) — обычное центрированное окно с настройками, библиотекой контекстов, масками и кнопкой «Запустить». HUD (`index.html` → `src/main.tsx` → `src/App.tsx`) — плавающее фреймлесс always-on-top окно — **создаётся по требованию** командой `launch_main_window` и уничтожается `stop_main_window` (кнопка в шапке HUD возвращает в лаунчер). Оба входа собираются одним Vite-конфигом (`build.rollupOptions.input: {main, launcher}`), делят `src/lib`, `src/ipc`, `src/hooks` и `src/components/ui`, но НЕ делят состояние: у каждого окна свой React-рут и свой стор. Бутстрап рута общий — `lib/render-root.renderWindowRoot` (поиск `#root` + StrictMode + `QueryClientProvider`), поэтому `main.tsx`/`launcher.tsx` — по три строки; третий вход заводится через него же, а не копией.

Следствия, которые легко нарушить: (1) **`tauri.conf.json` не описывает ни одного окна** (`"windows": []`) — оба создаются кодом (`window::create_launcher_window` из `setup_app`, `window::create_main_window` из `launch_main_window`), поэтому размеры и флаги (`transparent`/`decorations`/`alwaysOnTop`/`contentProtected`) задаются там, а не в конфиге; обе функции принимают `&Settings` параметром, а защита контента ставится ОДИН раз флагом билдера `.content_protected(...)` — пост-билд повторный вызов удалён, `window::apply_content_protection_all` остался только для смены настройки на лету и проходит по обоим окнам; (2) глобальные хоткеи регистрируются на `launch_main_window` и снимаются на `stop_main_window` — в лаунчере их нет; (3) готовность (ключи API + разрешение на запись звука) проверяется в лаунчере (`useLauncherReadiness`), а не в HUD — HUD запускается уже готовым.

Two halves: a **Rust backend** (`src-tauri/src/`) and a **React 19 frontend** (`src/`). The backend does all the privileged/native work; the frontend is pure UI over a typed IPC boundary.

Живёт в `apps/desktop/` монорепозитория **harpyhare** (Nx + npm workspaces; лендинг — `apps/landing`). Все пути и команды ниже — относительно `apps/desktop/` (запускать из этой папки, либо через Nx из корня: `nx <target> desktop`). Обзор монорепо — в корневом `CLAUDE.md`.

## Code style

- **Комментарии в коде запрещены полностью.** Знание живёт в говорящих именах; неочевидные инварианты и «почему» — в этом файле, а не в комментариях.
- **Хардкод запрещён.** Магические значения → именованные константы; вычислимое — деривация, а не копия; поведение моделей — по capabilities API, а не по спискам имён (единственные допустимые исключения по имени описаны в разделе про модели).
- **Одна ответственность.** Функции/компоненты, делающие несколько вещей, дробятся на маленькие с говорящими именами.
- **Публичные контракты меняются только синхронно по обе стороны.** IPC-команды/события, serde-ключи, форматы на диске (settings.json, chats.json), строковый формат хоткеев (`hotkeyFromEvent` ⇄ `parse_hotkey`).

## The Rust ⇄ frontend contract (read this first)

The backend exposes a **fixed set of commands and events**; the frontend mirrors them 1:1. When changing one side, change the other and keep names identical.

- **Контракт генерируется из Rust, а не пишется дважды.** `src/ipc/bindings.ts` — **сгенерированный файл, руками не править**: его пишет `cargo test` (тест `bindings::tests::typescript_bindings_are_up_to_date`, `tauri-specta` + `specta-typescript`). Внутри: типизированный объект `commands.*` (имена команд и аргументы больше не строки), все типы, пересекающие границу, и константы, объявленные через `.constant()` в `bindings.rs` — `SETTINGS_LIMITS`, `SETTINGS_DEFAULTS` (`Settings::default()` целиком) и `MODIFIER_COMBOS`. Файл исключён из eslint/prettier/knip. Добавил команду → `#[tauri::command] #[specta::specta]` + строка в `collect_commands!` в `bindings.rs` → `cargo test` перегенерит биндинги. **Типы, которые ездят только событием, сами не подхватываются** — их надо перечислить в `.typ::<>()` там же, иначе в биндингах их не будет и `contract.test.ts` не с чем сверять. **specta не экспортирует `u64`/BigInt**: поле помечается `#[specta(type = f64)]` (как байты в `UpdateProgress`) — на границу оно всё равно едет как JS number. **`bindings.ts` обязан получаться ОДИНАКОВЫМ на macOS и на Windows.** Файл генерируется на машине сборки и коммитится, а CI гоняет `cargo test` + `git diff --exit-code src/ipc/bindings.ts` (на macos-раннере: на windows-раннере тестовый бинарь не стартует, см. корневой CLAUDE.md) — значение, зависящее от `#[cfg]`, разведёт файл на двух хостах и уронит сборку. Отсюда три следствия: платформенные дефолты уезжают **парой платформ** (`PlatformCombo {macos, windows}` у `HotkeyAction.default_combo`, `MODIFIER_COMBOS.macos`/`.windows`), а не «текущим» значением — `.current()` зовёт только сам Rust; команды, которые на второй платформе не работают (маскировка облика), из `collect_commands!` НЕ убираются — они остаются в контракте и возвращают понятную ошибку; константы «какая это платформа» в биндингах нет вовсе — фронт определяет её сам (`lib/platform.ts`).
- **Команды регистрируются в `bindings.rs`** (`collect_commands!`), `lib.rs` только отдаёт `specta_builder.invoke_handler()`. `src/ipc/commands.ts` — **прямой реэкспорт** (`export const {cancelStream, closeApp, …} = commands`); ручная обёртка заводится ТОЛЬКО когда добавляет поведение или рукописный тип: `sendToClaude`/`countChatTokens` (`ChatMessageDto`/`RequestOptions`), `getSettings`/`setSettings` (каст к рукописному `Settings`), `checkForUpdate` (`UpdateInfo`), `redeemAccessCode` (идемпотентность), `startWindowDrag` (не команда, а JS-API окна). Однострочные форварды не писать — их было ~28 и они удалены.
- **Рукописные типы во фронте остались ради эргономики, но сверяются компилятором.** Сгенерированный `Settings` слабее рукописного (`#[serde(default)]` делает все поля опциональными, а `f64` в specta — `number | null`), поэтому `ipc/types.ts` держит чистые интерфейсы, а `ipc/contract.test.ts` содержит тип-уровневые утверждения `SameShape<Ours, Rust.X>` для `Settings`, `AppError`, `UpdateInfo`, `RecorderState`, `PromptPreset`, `OutputDeviceInfo`, `IdentityInfo`, `RequestOptions` и payload'ов событий (LLM, `resize-key.dim`, `update-progress`, `update-done`). Переименовал/убрал/переTипизировал поле в Rust → `tsc -b` падает на этом файле. Не удаляй эти утверждения — без них рукописные типы снова начнут расходиться (проверено: переименование поля в биндингах роняет сборку).
- **Границы настроек живут в Rust и экспортируются.** `settings::limits` (сгруппировано: `window`/`chat`/`teleprompter`/`capture`) — единственный источник `default/min/max`; из него берут и `Settings::default()`, и `Settings::clamp()`, и константа `SETTINGS_LIMITS` в биндингах. `lib/window-size.ts` остаётся framework-free (свои числа), но тест `window-size.test.ts` сверяет их с `SETTINGS_LIMITS` — разъедутся, упадёт тест. Новая числовая настройка = запись `Bounds` в нужной группе + поле + контрол; отдельных `DEFAULT_*`/`*_MIN`/`*_MAX` констант больше нет. **Контролы лаунчера берут `min`/`max` из `SETTINGS_LIMITS` напрямую — свою копию границ не заводить**: локальные копии уже разъезжались (слайдер `chat_font_size` был 11–18 при Rust-клампе 10–20, и пользователь не мог выставить значения, которые бэкенд принимает). Локально в секциях остаётся только `step` слайдера — его в реестре нет.
- **`set_settings` возвращает применённые (клампнутые) `Settings`**, а не `()`. Фронт обязан принять их как новое состояние (`useSettingsStore.save` → `adopt`), а не перечитывать `get_settings` вторым раундом: иначе UI держит введённое пользователем сырое значение, пока не придёт ответ второй команды.
- **Опции запроса едут объектом, не россыпью флагов.** `send_to_claude`/`count_chat_tokens` принимают `options: RequestOptions {thinking, webSearch}` (Rust `llm::RequestOptions`, `#[serde(rename_all="camelCase", default)]` ⇄ `lib/chats.RequestOptions`, собирается `chatRequestOptions(chat)`). Новая опция запроса = поле в этих двух типах + контрол в UI; сигнатуры `sendToClaude`/`useClaudeStream.send`/`useSendPipeline` не трогаются. Раньше `thinking`/`web_search` шли позиционными аргументами через пять сигнатур подряд.
### События

Эмитятся **только через типизированные хелперы `events.rs`**, и исключений больше нет: имена, payload-структуры и хелперы всех событий (включая `update-*` и `official-presets-updated`) лежат там, а `Emitter` не импортируется больше нигде. Фронт слушает через `src/ipc/events.ts`, типы — `EventMap` в `src/ipc/types.ts`. Список: `state-changed`, `transcript-ready`, `stt-error`, `llm-delta`, `llm-done`, `llm-error`, `llm-usage`, `update-available`, `update-progress`, `update-done`, `toggle-teleprompter`, `resize-key`, `official-presets-updated`, `screenshot-ready`, `screenshot-error`. LLM-события несут `chatId` (`{chatId, delta}` / `{chatId}` / `{chatId, code, message}`) — стримы независимы по чатам. `resize-key.dim` — не строка, а Rust-enum `ResizeDim` (`serde(rename_all="lowercase")` → union `"width" | "height"` в биндингах).

**Ошибки типизированы кодом, а не текстом.** `stt-error` несёт `AppError {code, message}`, `llm-error` — его же плюс `chatId` (поля перечислены явно, без `serde(flatten)` — иначе specta не экспортирует тип). Коды (`error.rs` в Rust, `lib/errors.ts` на фронте, списки обязаны совпадать): `network | badApiKey | badAccessCode | retryable | api | cancelled | permission | silence | internal`. Ветвление UI — ТОЛЬКО по `code` (`isRetryable` → кнопка «Повторить», `isNetworkError` → `ConnectivityOverlay`); `message` идёт только на экран. Раньше фронт парсил русскую прозу регулярками (`/перегружен|соединение|VPN/`) — не возвращай это, переформулировка текста ошибки не должна ничего ломать. Новый вариант ошибки: вариант enum + `CodedError::code()` в Rust ⇄ строка в `ErrorCode` на фронте.

**Дельты коалесируются в Rust и раскрываются плавно во фронте.** `llm-delta` копятся флашером ~25мс в `chat::send_to_claude`; финальный дрен буфера обязан уйти **до** `llm-done`, иначе фронт потеряет хвост ответа. Поверх коалесинга `useClaudeStream` раскрывает буфер не разом, а в rAF-цикле (`lib/stream-reveal`: скорость по dt = max(минимальная, доля отставания в секунду) — отставание показа ограничено ~100мс; срез не рвёт суррогатные пары). При done/stop/error в историю уходит ПОЛНЫЙ буфер, а не раскрытая часть — мгновенный доскок хвоста в конце осознан.

**Заполненность контекста — целиком из API, без хардкода окон:**

- Числитель-фолбэк: `llm-usage {chatId, inputTokens}` из `message_start.usage` стрима — СУММА `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` (при включённом prompt-cache голый `input_tokens` почти нулевой!). Пишется в `Chat.lastInputTokens`, персистится в chats.json — мгновенный фолбэк при входе в чат.
- Знаменатель: `ModelInfo.maxInputTokens`.
- **Основной показатель — проекция через `count_tokens`:** команда `count_chat_tokens` (Rust `AnthropicClient::count_tokens`, `POST /v1/messages/count_tokens`, бесплатный, без лиза на прокси) считает, сколько займёт СЛЕДУЮЩИЙ запрос (system + текущая история); хук `useProjectedContextTokens` в App.tsx (дебаунс 400мс, для пустого чата — плейсхолдер-сообщение `.`, чтобы учесть вес библиотечных материалов ещё до отправки).
- Итог: `usedTokens = projected || lastInputTokens` → `ContextUsageGauge` в шапке (StatusBar, перед иконками действий; скрыт, пока данных нет или окно модели неизвестно).
- **Прокси (репо `itech-relay`) обязан маршрутизировать `/v1/messages/count_tokens`** — иначе 404 и проекция не работает.
### Settings (28 полей)

Определён одинаково в `src-tauri/src/settings.rs` и `src/ipc/types.ts` (совпадение сторон проверяет `ipc/contract.test.ts`). Числовые границы НЕ дублируй в этом файле — они живут в `settings::limits` (см. выше). **Дефолты не дублируются**: `DEFAULT_SETTINGS` в `ipc/types.ts` (им инициализируется стор до первого `get_settings`, из него берутся фолбэки `normalizeDraft` в лаунчере) собирается из генерируемой `SETTINGS_DEFAULTS`, а не перечисляет значения руками — пропало или переименовалось поле в Rust, и `tsc` падает прямо на этой сборке объекта. Спред `prompt_presets: [...SETTINGS_DEFAULTS.prompt_presets]` там **обязателен и не подлежит «упрощению»**: specta печатает константу с `as const`, то есть массив приходит `readonly`, а `Settings.prompt_presets` изменяемый (лаунчер правит его прямо в draft) — без копии это ошибка типов.

**Глобального системного промпта и модели в Settings нет** — вместо них `prompt_presets: {id,name,text}[]` (сид «Расшифровка речи», id `transcription`) и per-chat поля. Чат хранит `presetId`, `thinkingEnabled`, `model`, `webSearch` (селекты в поповере «Параметры запроса» тулбара Composer — тулбар иконочный внутри карточки промпта, одинаков на любой ширине окна) и `context` (диалог «Контекст» — постоянный справочный текст чата). `system` собирается на фронте (`App.dispatchSend`): текст пресета (`lib/presets.presetText`) + выбранные материалы библиотеки контекстов (`lib/context-library.libraryContextBlocks` по `chat.libraryDocIds`) + контекст чата, и всё уходит в `send_to_claude(messages, chat_id, system, model, options)` при каждом запросе (Anthropic API stateless). Дефолты нового чата — `NEW_CHAT_DEFAULTS` в `lib/chats.ts`, они же fallback при десериализации старого chats.json: без препромпта (`presetId=""`), `thinkingEnabled=false`, `model` = `DEFAULT_MODEL` (haiku 4.5, `lib/models.ts`), `webSearch=false`, `context=""`. Старые чаты без соответствующего поля получают тот же дефолт (обратной совместимости с ранее сохранёнными значениями opus/thinking-on специально НЕ держим — реальных пользователей со старым chats.json нет).

**Вид и чат:**

- `chat_font_size` → CSS-переменная `--chat-font-size` (`applyChatFontSize`), масштабирует текст и код чата.
- `theme` — `"gray"` (дефолт, CSS-переменные `:root`) или `"black"` (оверрайды в `:root[data-theme="black"]`); применяется `applyTheme` (data-атрибут на documentElement), кламп неизвестных значений в gray — в `settings.clamp` и `applyTheme` синхронно.
- `scroll_step`/`scroll_modifier` — шаг и модификатор скролла чата стрелками (дефолт `Alt`; обработчик `useHotkeyScroll` в AnswerPanel, document-level keydown с preventDefault — прыжок каретки по абзацам через Option+стрелки пожертвован, прецедент Cmd+стрелок).

**Окно:**

- `window_width`/`window_height` — базовый логический размер HUD (дефолт 960×680); применяется при создании HUD (`window::create_main_window`) и при каждом изменении через `useWindowFrameSync` в App.tsx.
- `move_step`/`resize_step` — шаг хоткеев сдвига/размера окна стрелками; сами модификаторы отдельными полями больше не хранятся, они биндинги в `hotkeys` (дефолты платформенные: ⌘ и ⌘⇧ на macOS, Ctrl и Ctrl+Shift на Windows). Все три модификатора (`move`/`resize`/`scroll`) селект лаунчера предлагает строго из реестра `hotkeys::MODIFIER_COMBOS`, а он **парный по платформам**: шесть комбо на macOS против четырёх на Windows (клавиша Win под модификатор не отдаётся). Свободная склейка известных токенов отвергнута: `Cmd+Ctrl` проходил валидацию, но в списке его нет, и селект для такого значения рисовался пустым. Про обязанности слоёв см. «Управление окном».
- `screen_share_visible` — показывать окно при демонстрации экрана (см. Window chrome).

**Распознавание речи:**

- `stt_language`/`stt_translate` — язык Whisper и перевод на английский (см. stt.rs).
- `capture_device_uid` — UID устройства вывода для захвата (`""` = системный дефолт + автопересоздание тапа при его смене; см. capture.rs).
- `buffer_enabled`/`buffer_seconds` — фоновый кольцевой буфер последних N секунд системного звука (включён по умолчанию): звук непрерывно ресемплируется в 16 кГц и живёт только в RAM (`audio::RollingBuffer` внутри `capture::Shared`), при старте PTT-записи снимок буфера автоматически приклеивается к началу транскрипции (и в стриминговое тело Groq, и в аккумулятор сессии) — подхватывает сказанное до нажатия. Выключение тумблера немедленно очищает буфер, на диск ничего не пишется; side-effects смены полей — `apply_buffer_settings_change` в `set_settings`; при пересоздании tap буфер начинается заново (потеря ≤10 с осознанна).

**Телесуфлёр:** `teleprompter_speed`/`teleprompter_font_size` (клампы дублирует `lib/teleprompter`), персистятся при закрытии суфлёра; `teleprompter_hotkey` (дефолт `F10`); `teleprompter_resume` (дефолт `true`) — суфлёр открывается с сохранённой позиции скролла, если текст ответа тот же, иначе с начала.

**Хоткеи:** одно поле `hotkeys: Vec<HotkeyBinding {action, combo}>` вместо прежних семи строк (`hotkey`, `toggle_hotkey`, `teleprompter_hotkey`, `screenshot_hotkey`, `move_modifier`, `resize_modifier`, `scroll_modifier`). Пустой массив = всё по дефолтам реестра; см. «Хоткеи: реестр действий».

**Прочее:** `anthropic_api_key`/`groq_api_key`/`access_token` (см. «API keys» и «Коды доступа»), `auto_send`, `auto_preview_html`, `hotkey`/`toggle_hotkey`, `skipped_version`, `identity_id` (см. «Маскировка»).
- **Модели — динамические, не хардкод.** Команда `list_models` (Rust `llm::list_models`, `GET /v1/models`, бесплатный) отдаёт модели аккаунта с выжимкой capabilities (`ModelInfo {id, displayName, adaptive, alwaysThinks, codeExec, maxInputTokens}`; `maxInputTokens` — из поля `max_input_tokens` ответа `/v1/models`, у фолбэк-моделей 0 = «неизвестно»); кэш в `App.models`, первичный фетч на старте, фронт берёт через `useModels` (фолбэк — `lib/models.FALLBACK_MODELS`). `useModels` отдаёт не весь список, а курированную тройку: `curatedModels` (lib/models) оставляет по свежайшей модели семейств opus/sonnet/haiku — первое вхождение семейства в порядке `/v1/models` (API сортирует новыми вперёд), датированные id не хардкодятся и новые версии подхватываются сами; Rust-кэш `App.models` остаётся полным (capabilities находятся и для модели старого чата вне тройки, а `selectableModels` подмешает её в селект). Поле `thinking` собирает `llm::thinking_value` по capabilities: вкл → `adaptive` где поддержан; выкл → явный `{"type":"disabled"}` (на Sonnet 5 «опустить поле» = adaptive!); haiku (adaptive не поддержан) и Fable/Mythos («думают всегда» — единственное исключение по имени, capabilities этого не выражают) → поле не отправляется. Селект thinking в Composer блокируется через `lib/models.thinkingLocked`. Веб-поиск (`llm::web_search_value`) — server-side tool `web_search_20260209` в `tools` (Anthropic ищет сам, внутри того же стрима — клиентского tool-loop нет); моделям без code execution (haiku, `capabilities.code_execution`) обязателен `allowed_callers:["direct"]`, иначе API отвергает запрос (проверено живыми пробами — сами tool-версии в capabilities не выражены).

## Frontend architecture (`src/`)

Strict layering — keep each layer's responsibility intact:

- **`src/ipc/`** — the **only** place that imports `@tauri-apps/api`. `commands.ts` (typed `invoke`), `events.ts` (`onEvent`/`onFileDrop`/`onWindowResized`), `types.ts`. Commands/events call Tauri directly — **браузерного мока больше нет**: фронт работает только внутри Tauri (интернет и Rust-бэкенд обязательны). Раньше был `env.ts` c `isTauri()`-гейтами и no-op/fallback в браузере — удалён целиком (см. connectivity ниже).
- **`src/lib/`** — framework-free pure logic with unit tests: `platform.ts` (чистая `detectPlatform(userAgent)` + `PLATFORM` из `navigator.userAgent` — **единственный источник платформы во фронте**: из Rust её не спрашиваем, иначе разъедется `bindings.ts`; всё платформенное — подписи хоткеев, «из Finder»/«из проводника», видимость экранов лаунчера — принимает платформу параметром с дефолтом `PLATFORM`, чтобы тесты гоняли обе), `api-keys.ts` (`missingApiKeys`/`missingKeysNotice` — какие ключи API отсутствуют и текст баннера), `errors.ts` (`ErrorCode`/`AppError`/`isRetryable`/`isNetworkError`/`internalError` — зеркало Rust-кодов ошибок; вся логика «повторить/оффлайн» здесь, не в компонентах), `composer.ts` (attachment limit/downscale, `Attachment` type), `chats.ts` (chat model, `CHAT_LIMIT`, serialize/deserialize), `models.ts` (`ModelInfo`, `FALLBACK_MODELS`, `thinkingLocked`), `hotkey-capture.ts` (`hotkeyFromEvent`, `conflictsWithTyping`), `hotkey-modifier.ts` (`parseModifier`/`matchesModifier` — сверка модификаторов keyboard-события с настройкой), `window-controls.ts` (`applyOpacity`/`applyChatFontSize`/`applyTheme`/`isDraggableChromeTarget`), `stream-reveal.ts` (`advanceReveal`/`sliceRevealed` — математика плавного раскрытия стрима для `useClaudeStream`), `stream-markdown.ts` (`splitStableTail` — деление стрима на стабильный префикс/хвост для мемоизации markdown-парса; авторост поля промпта — JS-хук `usePromptAutosize` в Composer через scrollHeight + ResizeObserver, `field-sizing: content` в WKWebView не работает), `teleprompter.ts` (`toReadingText` markdown→проза, `advanceOffset` скролл-мат, `clampSpeed`/`clampFont`).
- **`src/hooks/`** — one hook per contract slice (`useClaudeStream`, `useChats`, `useModels`, `useRecorder`, `useTranscription`, `useWindowControls`, `usePttSuspend`, `usePermissions`). **Настройки — два слоя:** `useSettingsStore` (общий: загрузка, `save`, `reload`, применение визуальных настроек через колбэк) используется обоими окнами; `useSettings` — надстройка только для HUD (дебаунс-персист `bumpOpacity`/`bumpWindowSize`/`applyNativeWindowSize`) и `reload` наружу не отдаёт: перечитывание нужно одному лаунчеру после redeem. Лаунчер берёт `useSettingsStore` напрямую. `useChats` owns the chat list, per-chat drafts/attachments, and disk persistence. **Per-chat поля меняются одним `patchChat(id, patch: ChatPatch)`**, а не сеттером на поле (было семь: `setChatPreset`/`setChatThinking`/`setChatModel`/`setChatWebSearch`/`setChatContext`/`setChatLibraryDocs`/`setChatUsage` + `setDraft`). `ChatPatch` (`lib/chats.ts`) — `Partial<Pick<Chat, …>>` по изменяемым полям; `messages`/`id`/`title` через него не правятся (для них отдельные методы). `Composer` принимает `chat: Chat` + `onPatch`, а не 15 пропсов. Новое per-chat поле = поле в `Chat` + в `ChatPatch` + контрол в UI; `ChatsApi`, `AppComposer` и `ComposerProps` не трогаются. Hooks depend on `ipc`, never on `@tauri-apps` directly; tested with `renderHook` + `vi.mock("@/ipc/...")`.
- **`src/components/`** — presentational, built on shadcn/ui primitives in `src/components/ui/` (run `npx shadcn@latest add <name>` to add more). `App.tsx` composes hooks + components.

Stack: React 19 + Vite + Tailwind v4 (CSS-first `@theme` tokens in `src/index.css`, gray + oxblood dark theme, dark-only) + react-markdown + rehype-highlight. Path alias `@` → `src`. **Правило палитры: primary (окс-красный) НЕ используется как цвет текста** (заголовки секций, ссылки, бейджи, чипы — нейтральные `text-foreground/*`); primary допустим только для индикаторов (точки, эквалайзер, маркеры списков, подчёркивание активного таба), заливок кнопок и `destructive`-ошибок.

**Подсветка кода:** rehype-highlight в `AnswerPanel` (`REHYPE_PLUGINS`); палитра токенов — в `index.css`. Инвариант: `html` в `plainText` — чип превью (`HtmlBlockChip` через `makePre`) требует, чтобы children код-элемента остались **сырой строкой**; подсветка превратила бы их в массив span'ов и молча сломала чип. Во время стрима markdown-чанки мемоизированы (`MarkdownChunk` + `splitStableTail`) — история и завершённые блоки не перепарсиваются на каждый флаш дельт. `splitStableTail` режет стрим на префикс/хвост ТОЛЬКО по границе абзаца `\n\n` вне fenced-код-блока (признак «внутри fence» — нечётное число fence-маркеров, backtick- или tilde-, в префиксе): незакрытый fence сломал бы рендер обеих половин.

**Скролл чата:**

- **Скролл-к-низу при переключении чата — синхронно ДО пейнта** (`useLayoutEffect` в AnswerPanel, а не `useEffect`): иначе браузер успевает показать кадр со старой позицией → видимый «полёт сверху вниз».
- **Автоскролла во время стрима НЕТ намеренно** (stick-to-bottom раздражал — прокрутка «убегала» и останавливалась только ручным скроллом вверх): вниз прокручивают только переключение чата, отправка СВОЕГО сообщения (рост messages с user-хвостом в AnswerPanel) и кнопка «↓ Вниз»; рост partial лишь обновляет видимость кнопки (`syncJump`).
- `content-visibility` на сообщениях НЕ используется намеренно: он делал `scrollHeight` оценочным (офскрин-элементы схлопнуты в intrinsic-size), из-за чего пре-пейнт-скролл промахивался мимо низа и приходилось добивать rAF-циклом — костыль убран вместе с ним. Для реально огромной истории правильный инструмент — виртуализация (virtua), а не content-visibility (он ломает точность `scrollHeight`).

**Кнопки действий сообщения не перекрывают текст:** никакого absolute-чипа поверх — flex-раскладка `MessageShell` (у user-пузыря кнопки слева от него в свободной зоне, у assistant — постоянный правый жёлоб под одну кнопку), проявление по ховеру только через opacity (место зарезервировано, лейаут не прыгает).

- Ховер — обычный CSS `group-hover`, но **БЕЗ `transition-opacity`**: в прозрачном frameless-окне анимация прозрачности выносит элемент в отдельный композитный слой WKWebView, и при его схлопывании остаются несмытые пиксели (кнопки «залипали» видимыми на нескольких сообщениях сразу — при корректном DOM! — до полной перерисовки сменой чата; на скриншотах всплывали даже призраки текста прошлых кадров). События `:hover`/`mouseleave` были ни при чём — JS-трекинг ховера уже пробовался и откачен как лишний.
- Правило: у hover-reveal контролов показ/скрытие мгновенные, никаких opacity-переходов (снято и в `AttachmentChip`, и в `ContextLibraryPanel`). В скрытом состоянии — `pointer-events-none`, чтобы невидимые кнопки не ловили клики.
- `pr-7` у `StreamingAssistant` обязан равняться ширине жёлоба (`gap-1` 4px + `size-6` 24px) — иначе готовый ответ перевёрстывается при переезде из стрима в историю.

**Интернет обязателен + connectivity-лоадер.** Оффлайн-режим не поддерживается. Детект связи — хук `useConnectivity` (`hooks/useConnectivity.ts`): `offline` инициализируется `!navigator.onLine`, на маунте — активная проба `probe_connectivity` (Rust-команда `AnthropicClient::reachable` — авторизованный GET `{base_url}/v1/models` с коротким таймаутом; **любой HTTP-ответ = связь есть**, ошибка connect/DNS/timeout = нет; автоматически бьёт в тот же прокси в прокси-режиме). Слушает события `online`/`offline`; пока `offline` — опрашивает пробу каждые 4с и снимает флаг при успехе. App дополнительно поднимает `offline` через `connectivity.reportNetworkError()`, когда сводный `error` (`sttError ?? stream.error`) содержит текст `LlmError/SttError::Network` («Нет соединения»). При `offline` рендерится полноэкранный `ConnectivityOverlay` (`absolute inset-0 z-50` над `.app-shell`, рядом с оверлеем телесуфлёра) — **не размонтирует чат/стримы**, снимается автоматически. Сетевые фолбэки списка моделей (`FALLBACK_MODELS`/`fallback_models()`) и вшитых пресетов оставлены сознательно (мгновенный рендер до первого фетча + сид для `presets:publish`).

## Rust backend (`src-tauri/src/`)

**Провайдеры за портами — командный слой не знает про Anthropic/Groq.** `App.llm: Mutex<Arc<dyn llm::LlmProvider>>` и `App.stt: Mutex<Arc<dyn stt::SttEngine>>` — трейт-объекты, не конкретные клиенты.

- `llm::LlmProvider` — `stream(LlmRequest, cancel, &mut dyn LlmStreamSink)` / `count_tokens(LlmRequest)` / `list_models()` / `reachable()` / `warm_up()`. `LlmRequest {model, system, messages, options}` нейтрален: ни `thinking`-поля, ни `tools`, ни JSON. Сборка тела Anthropic (`build_request_body`, `thinking_value`, `web_search_value`) живёт ТОЛЬКО внутри `impl LlmProvider for AnthropicClient` — в командном слое (`chat.rs`) её быть не должно.
- Capabilities резолвит сам провайдер: `AnthropicClient` держит `catalog: ModelCatalog` (`Arc<Mutex<Vec<ModelInfo>>>`, тот же Arc, что `App.models`), `list_models()` его обновляет, `capability_fields()` читает. Прежней `find_cached_model` в `lib.rs` нет — не возвращай.
- `stt::SttEngine` — `transcribe(&[f32])` / `transcribe_stream(AudioChunkStream, cancel)` / `warm_up()`. `AudioChunkStream = Pin<Box<dyn Stream<Item = Result<Vec<u8>, io::Error>> + Send>>` — **`reqwest::Body` через границу порта не проходит**, `wrap_stream` вызывается внутри `GroqStt`.
- Дельты стрима идут в `LlmStreamSink` (две колбэк-функции не годятся — обе занимали бы `&mut` на один буфер); в `chat.rs` его реализует `ChatStreamSink` (перф-тайминг ttfb + push в буфер флашера + эмит `llm-usage`).
- Второй провайдер (другая модель/локальный STT) = новый `impl` + строка в `build_llm_client`/`build_stt_client`; ни `lib.rs`, ни фронт не меняются.

**`lib.rs` — только сборка (≈100 строк): `run()`, `setup_app()` и передача `invoke_handler` из `bindings::builder()`.** Всё остальное разложено по модулям, каждый владеет своими `#[tauri::command]`'ами; новую команду клади в модуль по смыслу и добавляй в `collect_commands!` в `bindings.rs` (единственный список). Реэкспорт-шимов (`pub use app_state::App`, `pub use window::…`) в `lib.rs` намеренно нет — зови модуль по полному пути, иначе `lib.rs` снова начнёт обрастать поверхностью.

| модуль | ответственность |
| --- | --- |
| `app_state.rs` | `App`, `SttStream`, конструкторы клиентов/капчера, пути к файлам, аксессоры (`current_settings`, `llm_provider`, `stt_engine`) |
| `events.rs` | имена ВСЕХ событий + payload-структуры + типизированные emit-хелперы. **Событие эмитится только отсюда** — `app.emit`/`Emitter` в других модулях не писать (`update.rs` и `remote_presets.rs` тоже ходят через хелперы) |

Доменные модули (`audio`, `capture`, `stt`, `llm`, `state`, `settings`, `identity`, `error`) остались как были — они не знают про Tauri. The domain modules are pure and unit-tested. **Юнит-тесты живут отдельно от кода**: в конце `src/<mod>.rs` — только объявление `#[cfg(test)] mod tests;`, тело — в `src/<mod>/tests.rs` (child-модуль, `use super::*` даёт доступ к приватному — поэтому НЕ интеграционные `tests/`, там виден только публичный API); новые тесты класть туда же, инлайновые `mod tests {}` не заводить. Тесты платформенного бэкенда — по той же конвенции этажом ниже: `src/identity/macos/tests.rs`.

**Платформенное расщепление — один приём на все модули.** `src/<модуль>.rs` — платформенно-нейтральный фасад со всей переносимой логикой, рядом `src/<модуль>/macos.rs` и `src/<модуль>/windows.rs`, подключаемые `#[cfg(target_os = ...)] mod ...; use ... as backend;`. Так расщеплены `capture`, `platform`, `screenshot`, `identity`; остальные модули общие. **`#[cfg]`-ветку посреди общего кода не заводить** — платформенный вызов добавляется в ОБА бэкенда, второй при необходимости честной ошибкой (`identity/windows.rs`) или no-op (`disable_cursor_autohide_on_typing` в `platform/windows.rs`): иначе фасад начнёт знать про платформы и разъедется с контрактом (см. инвариант про одинаковый `bindings.ts`). Гейт по `cfg!` в общем коде остаётся только там, где это одно значение, а не ветка логики: `permissions::AUDIO_REQUIRES_PERMISSION = cfg!(target_os = "macos")`, `#[cfg(unix)]`-режим файла в `settings::create_owner_only`. **Платформенные крейты обязаны лежать в `[target.'cfg(target_os = "…")'.dependencies]`** (`cidre`/`objc2*`/`block2`/`plist` — macOS; `windows` 0.61 с явным списком features и `png` — Windows): в общем `[dependencies]` они не «просто тянут лишнее», а роняют сборку второй платформы. **А вот `[build-dependencies]` так гейтить НЕЛЬЗЯ: их `cfg` матчится по ХОСТУ сборки, а не по цели.** `cc` держим в общих build-зависимостях и гейтим только его ВЫЗОВ (`build.rs` компилирует C-оверлей и линкует Apple-фреймворки при `CARGO_CFG_TARGET_OS == macos`). Грабля неочевидна и локально невидима: на macOS-хосте `cfg(target_os = "macos")` в build-зависимостях истинен при любом `--target`, поэтому кросс-проверка Windows-сборки её не ловит — падает только настоящая сборка на Windows-раннере (`cannot find crate cc` в build.rs).

- `audio.rs` — downmix → resample (rubato, 48k→16k) → WAV (hound); RMS silence gate. `StreamResampler` — инкрементальный ресемплинг для стриминга (батчевый `resample_to_16k` идёт через него же — один код-путь; к тому же rubato `process_all_into_buffer` дублирует первые `output_delay` фреймов, инкрементальный путь от этого бага свободен); параметры sinc намеренно «речевые» (`sinc_len=32`) — студийный 128 для 16кГц-Whisper уже отвергнут (~4x CPU впустую); `wav_header_streaming` (размеры 0xFFFFFFFF) + `f32_to_i16le_bytes` для тела стриминговой загрузки.

#### capture.rs — инварианты

Продюсер (RT-колбэк Core Audio на macOS, поток захвата WASAPI на Windows) пишет в lock-free ring buffer (`ringbuf`, без мьютексов/аллокаций); поток-консьюмер на лету даунмиксит+ресемплит в 16кГц, копит буфер и отдаёт чанки в опциональный `ChunkSink` (его дроп = EOF для стриминга). `stop()` возвращает готовый 16кГц-моно. Сигнатура — `SystemAudioCapture::new(uid, buffer_secs)`.

**Вся переносимая часть живёт в `capture.rs`** (кольцо, консьюмер-тред, `Session`/`Shared`/`Scratch`, PTT-сессии, `run_buffering`, `RollingBuffer`, `OutputDeviceInfo`, публичные методы `SystemAudioCapture`), бэкенд обязан дать ровно четыре вещи, и **контракт `open`/`start` двухфазный не случайно**: `open(uid) -> (Source, StreamSpec)` открывает источник и СНАЧАЛА сообщает формат (`sample_rate`, `channels`) — от него зависят размер кольца и поля `Shared`, поэтому создать их до `open` нельзя; `start(source, ctx: Box<CallbackCtx>) -> Running` только запускает подачу сэмплов, а `Running` глушит захват в `Drop`; плюс `list_output_devices()` и `watch_default_output_device(handler)`. **Сэмплы попадают в кольцо только через `CallbackCtx::wants_samples()`/`push_samples()`** — гейт по `recording || buffering` и учёт `produced`/`dropped` живут в общем коде: на `produced` стоит `recording_secs()` (минимальная длительность записи и вотчдог 10 минут), а `dropped` виден только строкой `[perf]` в stderr, так что бэкенд, пишущий в кольцо мимо этих методов, ломает счёт длительности молча. Вариант ошибки — `CaptureError::Backend(String)` с платформой в тексте («Core Audio: …» / «WASAPI: …»), отдельного `CoreAudio` больше нет.

- **Порядок остановки обязателен:** сначала `recording=false`, потом дрен хвоста кольца. Флагом `recording` управляет только консьюмер (протокол `Session` + `stop_requested` исключает гонку «stop до пробуждения консьюмера»).
- **Порядок полей `Running` в `capture/macos.rs` — это порядок drop** (`_started` → `_tap` → `_ctx`; на `_ctx` ссылается C-колбэк): перестановка = use-after-free в IO-потоке. `unsafe impl Send` (тоже в бэкенде, а не на фасаде) отключает автопроверку компилятора — при добавлении полей пересматривать вручную; доступ — только под Mutex.
- **Windows-бэкенд (`capture/windows.rs`) — WASAPI loopback на устройстве ВЫВОДА** (`IAudioClient` + `AUDCLNT_STREAMFLAGS_LOOPBACK`, shared mode, mix format). **COM инициализируется в MTA, но `RPC_E_CHANGED_MODE` — это успех, а не ошибка**: tao/wry уже подняли STA на главном потоке, и `CoInitializeEx(MULTITHREADED)` оттуда возвращает именно этот код; трактовать его как отказ значит не поднять захват вообще ни разу (все входы — `list_output_devices`, `open`, `set_settings` — синхронные команды главного потока). В этом случае `CoUninitialize` звать нельзя — апартамент чужой. Через границу потоков COM-указатели не ездят: `open` резолвит устройство и возвращает **его конкретный id**, а клиент активируется заново уже в потоке захвата — иначе смена дефолта между `open` и `start` давала бы «формат изменился» на ровном месте. Старт синхронно рапортует об успехе/ошибке через канал — без этого `SystemAudioCapture::new` возвращал бы Ok на сдохшем потоке и «Тишина» вместо ошибки доступа. Цикл **опрашивающий**, интервал выводится из `GetDevicePeriod`: событийный режим у loopback не сигналится, когда звук не играет, — на нём захват вставал бы до первого звука. Пакеты с флагом `AUDCLNT_BUFFERFLAGS_SILENT` дополняются нулями, иначе таймлайн рвётся и записанное съезжает. **Тишину приходится синтезировать самим**: loopback вообще не выдаёт пакетов, пока на устройство никто не рендерит, а `recording_secs()` считает время по числу сэмплов — без добивки нулями по настенным часам (`Timeline` в бэкенде) пятисекундное удержание PTT в тишине давало бы «запись слишком короткая», а вотчдог 10 минут не срабатывал бы никогда. **Поток захвата переоткрывает стрим сам**: `AUDCLNT_E_DEVICE_INVALIDATED` (выдернули гарнитуру, сменили частоту устройства) не убивает поток молча — он ретраится раз в секунду, иначе `App.capture` остался бы `Some` с мёртвым потоком и PTT работал бы вхолостую без единого сигнала. Внутренний цикл дренажа сверяется с флагом остановки: `Running::drop` джойнит поток **под удерживаемым локом `App.capture`**, и бесконечный дренаж заморозил бы всех, кто ждёт капчер. Формат проверяется на декодируемость (float32 / int16 / int32) при открытии — внятная ошибка лучше молчаливой тишины. `E_ACCESSDENIED` → `CaptureError::PermissionDenied`.
- **Отказ TCC не различим по коду ошибки (macOS):** Core Audio отдаёт `kAudioHardwareIllegalOperationError` ('!hog'), и именно он маппится в `PermissionDenied` — «более точного» кода нет. При отказе в state кладётся `None`, UI видит это через `permissions_status`. «Выдать» зовёт `request_permission("audio")` (пересоздание тапа, что триггерит TCC-промпт при статусе «не спрошено»), «Настройки» — `open_permission_settings("audio")`. `NSAudioCaptureUsageDescription` живёт в `src-tauri/Info.plist` и встраивается и в dev-бинарь — без него macOS не спрашивает, а молча отказывает.
- **Главный sub-device приватного aggregate — устройство вывода как clock source** (macOS; `Settings.capture_device_uid`, `""` = системный дефолт через `resolve_output_device`; несуществующий uid молча падает на дефолт — на Windows та же политика фолбэка). Убирать `sub_device_list` «за ненадобностью» нельзя.
- **Захват привязан к устройству на момент создания** — сменился вывод → на macOS тап отдаёт нули («Тишина»), на Windows loopback остаётся висеть на старом эндпоинте. Следит за этим `capture::watch_default_output_device` (macOS — слушатель свойства `kAudioHardwarePropertyDefaultOutputDevice`, Windows — отдельный тред, раз в две секунды сверяющий id дефолтного эндпоинта: опрос выбран вместо COM-колбэка `IMMNotificationClient` сознательно — он не требует реализовывать COM-интерфейс и не добавляет unsafe-поверхности, а двухсекундная задержка на смене устройства незаметна), но **политика остаётся в `recording.rs` и в бэкенды не переезжает**: колбэк деферится в async runtime и пересоздаёт капчер при смене дефолта только когда uid="", при смене `capture_device_uid` в `set_settings`, а если рекордер занят — лениво на следующем PTT через флаг `capture_rebuild_pending`.
- **Режим непрерывной буферизации:** `set_buffering(true)` переводит консьюмер в цикл `run_buffering` с долгоживущим ресемплером (продюсер пропускает сэмплы по `wants_samples()`, то есть `recording || buffering`), каждый 16кГц-чанк уходит в `audio::RollingBuffer` под мьютексом. PTT-сессия при включённом буфере обслуживается тем же циклом: `take_pending_session` сбрасывает снимок буфера в аккумулятор и `ChunkSink` ДО живых чанков (преролл), rolling-лок берётся только после отпускания session-лока (**session- и rolling-локи никогда не держатся одновременно**), `finish()` ресемплера не зовётся (потеря хвоста ~20 мс речи при отпускании осознанна). При выключенном буфере путь консьюмера прежний. Буферизованная сессия тоже ведёт флаг `recording` (`take_pending_session` ставит, наблюдение стопа и финализация снимают) — гейт продюсера остаётся корректным при выключении тумблера посреди записи, а выход из режима буферизации чистит rolling на стороне консьюмера.
- Список устройств для UI — `list_audio_output_devices` (`capture::list_output_devices`: на macOS фильтр по наличию output ASBD, на Windows активные render-эндпоинты с `PKEY_Device_FriendlyName`). Ручная приёмка — `examples/record5s.rs`; живой смоук стриминга в Groq — `examples/stream_smoke.rs`.

## Non-obvious invariants (do not break these)

### Чаты и библиотека контекстов

**Чаты независимы и параллельны.** Источник истины — фронт (`useChats`: `Chat[]` + `activeId`); Rust хранит чаты как непрозрачную JSON-строку в `chats.json` (атомарно, `0600`, модуль `chats.rs`, команды `load_chats`/`save_chats`). `send_to_claude(messages, chat_id, system, model, options)` шлёт всю историю чата; отмена по-чатная через `Mutex<HashMap<chat_id, CancellationToken>>`. Картинки в `chats.json` не сохраняются (стрипаются в `serializeChats`); текстовый `context` чата — сохраняется; `libraryDocIds` — сохраняется, старые чаты без поля → `[]`. Лимит — `CHAT_LIMIT = 6`.

**Дебаунс-сохранение на диск (500мс) включается только после завершения первичной загрузки** (флаг `loaded` в `useChats`) — иначе стартовое пустое состояние перезаписало бы сохранённые чаты. Тот же инвариант — в `useContextLibrary`.

**Библиотека контекстов** — отдельный файл `context-library.json`, тот же паттерн, что chats.json: Rust хранит непрозрачный JSON через `chats::load/save`, команды `load_context_library`/`save_context_library`; модель и (де)сериализация — `lib/context-library.ts`, битые `folderId` чинятся в корень, тексты клампятся `DOC_TEXT_LIMIT_CHARS`. UI — экран «Контексты» лаунчера (`ContextLibraryPanel`, правки применяются сразу через свои команды, мимо draft/автосейва лаунчера); выбор материалов в чате — диалог «Контекст» Composer (чекбоксы + свой текст).

**Импорт файлов** — пикер (`input type=file`) и drag-and-drop из файлового менеджера ОС (в подписи «из Finder» / «из проводника» — по платформе):

- HTML5-drop для файлов ОС в Tauri НЕ работает (webview перехватывает) — используется `getCurrentWebview().onDragDropEvent` (обёртка `ipc/events.onFileDrop`, физпиксели → CSS через devicePixelRatio), папка-цель — `elementFromPoint` по атрибуту `data-drop-folder`.
- Типы — **.md/.markdown/.txt и .pdf** (`context_import.rs` диспетчеризует по расширению): текст читается `read_to_string` (лимит 1 МБ), PDF — `pdf-extract::extract_text_from_mem` в `catch_unwind` (битый PDF не должен ронять процесс; лимит 20 МБ), затем `normalize_extracted_text` (CR/form-feed → `\n`, схлопывание пустых строк, trim). Пустой результат = скан без текстового слоя → ошибка `ERR_PDF_NO_TEXT` (OCR нет). Извлечённый текст всё равно клампится `DOC_TEXT_LIMIT_CHARS`.
- Пути: drop даёт реальный путь → `read_context_import_file(path)`; у пикера реального пути нет ни в WKWebView, ни в WebView2 (`File.text()` для текста, PDF — `File.arrayBuffer()` → `lib/base64.arrayBufferToBase64` → `read_context_pdf_bytes(dataBase64)`). Обе команды парсят в `tokio::spawn_blocking` (парс 20 МБ не блокирует рантайм).
- Перенос материалов между папками — кастомный pointer-драг (`useDocDrag`: mousedown+порог 5px → mousemove → `moveDoc` по `data-drop-folder` под курсором), НЕ HTML5 draggable — внутристраничный HTML5-dnd в Tauri-вебвью ненадёжен.
- **PTT обязан работать при фокусе в поле промпта.** `usePttSuspend` глушит PTT при фокусе в текстовых полях ТОЛЬКО для хоткеев, конфликтующих с печатью (`conflictsWithTyping`: одиночная буква/цифра, в т.ч. с Shift). F-клавиши и комбинации с Cmd/Ctrl/Alt не глушатся никогда — не возвращай безусловную заглушку.
- **Hotkey handlers must defer all work.** `tauri-plugin-global-shortcut` invokes the handler while holding its registry mutex; doing register/unregister synchronously inside (e.g. registering Esc) is a re-entrant deadlock that hard-freezes the app. `hotkey.rs` wraps handlers in `defer()` (spawns onto the async runtime). The same applies to anything a handler triggers.
### Управление окном идёт через Rust-команды, не через JS

`set_window_size`, `close_app`, `hide_main_window`, позиция и видимость окна — Rust-команды и обработчики хоткеев (нативный монитор стрелок зовёт `set_position` напрямую). JS-путь вроде `getCurrentWindow().setSize()` **молча не работает без соответствующего разрешения** в `src-tauri/capabilities/default.json`, поэтому по умолчанию предпочитай Rust-команду; реально нужна возможность из JS — сначала добавь разрешение туда. Из сеттеров явно выдан ровно один, `core:window:allow-start-dragging` под `startWindowDrag`, — это единственный прямой вызов Tauri-API окна из фронта; **разрешения-сеттеры «про запас» не держим**: `set-position`/`show`/`hide` были выданы явно, но из JS не звались ни разу, и удалены. Геттеры (`scale-factor`, `outer-position`, `inner-size`/`outer-size`, `current-monitor`) входят в `core:window:default`, то есть уже в `core:default`, и перечислять их отдельно не надо — `onWindowResized` со своим `scaleFactor()` работает, хотя `allow-scale-factor` в capability никогда не значился (а `allow-outer-position` там был просто избыточен и тоже удалён). Состав набора сверяй по сгенерированному `src-tauri/gen/schemas/acl-manifests.json`, а не на глаз. Окна перечислены поимённо (`"windows": ["main", "launcher"]`) — окно, забытое в этом списке, не получит даже `core:default`, и любой `invoke` из него будет отвергнут.

**Твин ресайза** (`set_window_size`) анимирует ширину+высоту (ease-out) в фоновом треде, диспатчит каждый кадр через `run_on_main_thread`, с генерационным guard'ом `resize_gen`. Верхний край Y фиксирован (рост вниз), целевой `x` — текущий, только клампится в границы монитора (`anchored_target_x` → `window_geom::clamp_window_x`): окно растёт вправо на месте и сдвигается влево лишь упёршись в правый край (не уедет за экран). Центрирования НЕТ намеренно — оно раздражало при хоткей-ресайзе и открытии превью. Ранний выход — по эпсилону размеров; вызов с тем же размером — полный no-op.

**Перетаскивание ЛКМ — явным `getCurrentWindow().startDragging()`** (`startWindowDrag` в `ipc/commands.ts`), а НЕ через `data-tauri-drag-region`: атрибутная инъекция Tauri в этом фреймлесс+transparent окне не срабатывала.

- `useWindowDrag` вешает `onMouseDown` на шапку (StatusBar); корневой `.app-shell` в App.tsx тоже стартует драг, но только при клике прямо по нему (`target === currentTarget` — отступы и зазор колонок; иначе клик по тексту чата ломал бы выделение).
- Драг стартует только для ЛКМ и только если `isDraggableChromeTarget` (клик не по интерактиву — селектор `button, a, input, textarea, select, [role='tab'], [data-no-drag]`), поэтому кнопки/табы остаются кликабельными, а клик по значку внутри кнопки (SVG, не HTMLElement) драг не стартует.
- Курсор над драг-зоной остаётся стрелкой (глобальный `cursor: default`) — осознанно.

**Шапка HUD:** футера-шпаргалки больше нет — справочник всех хоткеев живёт в поповере `HotkeysPopover` (иконка клавиатуры); данные — единый реестр `lib/hotkeys.hotkeyGroups(cfg)` (настраиваемые комбо приходят из Settings; **при добавлении хоткея дополняй реестр, а не разметку**). Табы чатов — номерные квадраты `ChatTabs` (скроллятся по горизонтали в узком окне; × по ховеру только на активном табе — у неактивных клик выбирает чат; переименование чатов удалено, поле `title` живёт в данных для совместимости chats.json; слева табы НЕ размещать — боковая рейка ломала симметрию чат-колонки и отвергнута). Кнопки окна — ghost-иконки (`WindowButton`): `X` → `close_app` (ховер краснеет), `Minus` → `hide_main_window` (возврат — глобальным toggle-хоткеем).
- **Модификатор+стрелки двигают окно нативным перехватом клавиш, а не через вебвью** (`platform::install_move_keys_monitor`: на macOS — локальный NSEvent-монитор, на Windows — низкоуровневый хук `WH_KEYBOARD_LL`), который поглощает keyDown ДО вебвью — иначе каретка прыгала бы по текстовому полю, а сдвиг окна ходил бы через IPC. **Вся логика стрелок — общая `platform::handle_arrow_key(app, mask, dx, dy)`**: чтение настроек, сдвиг окна, эмит `resize-key`; бэкенду остаётся перехватить событие, перевести нативные флаги в `ModifierMask` и поглотить keyDown ровно тогда, когда функция вернула `true` (дублировать разбор настроек в бэкенде нельзя — разъедется полярность и клампы). Перехват ставится один раз в `setup_app` и живёт весь рантайм, поэтому пересоздание HUD его не ломает — но **поглощать keyDown он вправе только тогда, когда действительно его обработал**: нет окна `main` — событие уходит дальше, иначе ⌘+←/→ в текстовых полях лаунчера съедаются вместо перемещения каретки по строке (HUD может быть ещё не создан, а перехват уже живёт). Это горячий путь: **при пустой маске модификаторов выходим ДО взятия лока настроек** — иначе обычная навигация стрелками в поле промпта (с автоповтором) лочит глобальные `Settings` на каждый keyDown. **Хук Windows — глобальный, в отличие от локального монитора macOS**, поэтому в нём обязательна сверка `GetForegroundWindow()` с hwnd HUD: без неё те же стрелки перехватывались бы в чужих приложениях; ставится он один раз, `AppHandle` для него живёт в `OnceLock`. `resize_modifier`+стрелки меняют **размер** окна: монитор поглощает keyDown и эмитит `resize-key {dim, dir}`; фронт (`useWindowControls` → `useSettings.bumpWindowSize`) шагает `Settings.window_width/height` на `resize_step` с клампами из `lib/window-size.ts`, окно применяет `useWindowFrameSync`, персист — дебаунсом (как opacity). Полярность: ←/↑ меньше, →/↓ больше.
- **Стрелки сдвига и размера принадлежат нативному монитору целиком — параллельной JS-ветки под них нет и заводить её нельзя.** Монитор съедает keyDown СОВПАВШИХ с настройкой комбинаций, поэтому до вебвью долетают ровно те, что пользователь НЕ выбирал: JS-обработчик мог только противоречить его выбору (окно двигалось на чужой комбинации), «фолбэком» он не был никогда — зашитый `metaKey || ctrlKey` (+Shift) был багом, вывернутым наизнанку, а настраиваемая версия того же кода осталась бы багом. Вместе с веткой ушла её обвязка: раскладка «код клавиши → ось и знак» на фронте (ось и знак решает Rust и присылает готовыми в payload `resize-key`) и Rust-команда сдвига окна — монитор двигает окно `set_position`'ом напрямую, звать команду было неоткуда, и в `collect_commands!` её больше нет. `useWindowControls(onSend, onOpacityStep, onResizeKey)` отвечает теперь только за прозрачность, отправку по Cmd/Ctrl+Enter и подписку на `resize-key`. Единственный оставшийся JS-путь модификаторов — скролл чата (`useHotkeyScroll`: его комбо монитор не трогает и пропускает в вебвью), там спека разбирается `parseModifier` ОДИН раз в эффекте, а не на каждый keydown (иначе каждое нажатие в вебвью аллоцирует массив на `split("+")`); в реестр хоткеев комбо приходят полями `moveWindow`/`resizeWindow`/`scrollChat` в `HotkeyConfig`.
- **Словарь модификаторов — один источник, `hotkeys::MODIFIER_COMBOS`** (переехал из `settings.rs`), и он **парный по платформам** (`{macos, windows}`): через `.constant()` в биндинги уезжает пара целиком, селект `WindowSection` берёт свою половину (`MODIFIER_COMBOS[PLATFORM]`, своей копии списка во фронте нет), Rust — через `.current()`. Обе реализации разбора покрыты тестами: `platform/tests.rs` (каждое комбо реестра даёт непустой и уникальный `modifier_mask`, дефолты семейств лежат в реестре) и `lib/hotkey-modifier.test.ts` (то же для `parseModifier`, прогон по обеим платформам плюс проверка, что в Windows-списке нет комбо с Win). Клавишу Win на Windows нельзя и **захватить** мышью: `hotkeyFromEvent` отдаёт `null`, если зажат Meta, — иначе получался бы мёртвый биндинг, который `assignHotkey` уже отобрал у прежнего владельца, а `RegisterHotKey` с `MOD_WIN` система не отдаёт (ошибка регистрации при этом глотается). Бит `ModifierMask::CMD` в Windows-бэкенде при этом остаётся привязан к `VK_LWIN`/`VK_RWIN` намеренно: `settings.json`, перенесённый с macOS, содержит комбо с `Cmd`, и они обязаны продолжать работать, а не молча игнорироваться. Добавляешь комбо — правишь массив нужной платформы в Rust и гоняешь `cargo test`, чтобы перегенерить биндинги. `formatCombo` обязан сворачивать спеку из одних модификаторов, без клавиши на конце (`Cmd` → ⌘, `Cmd+Shift` → ⌘⇧): regex, требовавший `+` после токена, оставлял подписи вида «⌘Shift»; на Windows глифов нет — токены текстовые (`Ctrl/Shift/Alt/Win`) и соединяются через `+`. **Прозрачность (`+`/`−`) в UI настраиваемой НЕ делаем намеренно** — селект отдаёт пользователю ровно три модификатора (сдвиг, размер, скролл); комбо прозрачности живёт действием `opacity` в реестре `hotkeys.rs`, откуда его одинаково берут подпись в поповере и сверка события в `useWindowControls` (`effectiveCombo(hotkeys, "opacity")`), потому что литерал «⌘⇧ + −» в подписи и `e.metaKey && e.shiftKey` в обработчике уже жили порознь и могли разъехаться.
- **Указатель мыши никогда не прячется и не меняет форму.** WebKit при печати в текстовом поле просит спрятать указатель «до движения мыши» через `+[NSCursor setHiddenUntilMouseMoves:]` в UI-процессе; на старте (`platform::disable_cursor_autohide_on_typing`, зовётся из `setup_app`) этот класс-метод свизлится в no-op — публичный objc-runtime API, детерминированный фикс. Пост-фактум `setHiddenUntilMouseMoves(false)` НЕ работает: скрытие приходит асинхронным IPC и гонку выигрывает (такая компенсация была в прежней команде сдвига окна и удалена как ненужная при свизлинге). Форма указателя — всегда стандартная стрелка: глобальный `cursor: default !important` в index.css намеренно подавляет I-beam/pointer/not-allowed во всех кейсах — не убирай. У WebView2 такого автоскрытия нет, поэтому `disable_cursor_autohide_on_typing` на Windows — осознанный пустой no-op, а не забытая реализация.
- **`onEvent` uses a `live` flag** to pair subscribe/unsubscribe across the async `listen` promise — required for React StrictMode double-mount safety. `useClaudeStream` likewise cancels its pending rAF on unmount and gates late deltas after `stop`. Частичный ответ на `stop`/`llm-error` НЕ выбрасывается — уходит в историю через `onComplete` (дубля нет: `llm-done` отменённого стрима подавляется, чат уже снят с `active`). Буферы дельт и набор активных стримов живут в ref, а не в state: обработчики событий подписаны один раз и обязаны видеть свежие значения без переподписки — перенос в state/deps сломает роутинг дельт.
- **API keys: `.env` is a fallback only.** `lib.rs` setup reads `ANTHROPIC_API_KEY`/`GROQ_API_KEY` and applies them via `settings.apply_key_fallback` **only when** the corresponding settings.json field is empty (UI-saved keys win). `.env` is read from cwd and from `CARGO_MANIFEST_DIR/..` (so a Finder-launched `.app`, whose cwd is `/`, still finds the project `.env`). `.env` is gitignored. **Гейт «нет ключей» живёт в лаунчере, а не в HUD** (`features/launcher/useLauncherReadiness`): `get_settings` отдаёт настройки уже с применённым `.env`-фолбэком, поэтому пустое поле на фронте = ключа нет нигде. `missingApiKeys(settings)` (`lib/api-keys`) + разрешение на запись звука (`usePermissions`) дают `ready` (считается один раз в хуке и приходит в панель пропом `readiness`, а не пересчитывается формулой на месте); пока не `ready`, кнопка запуска HUD заблокирована. В HUD баннера про разрешения нет вовсе — гейт лаунчера не выпустит в HUD без доступа к звуку (см. «Доступы»). Поэтому у `Composer` **нет пропа `disabled`**: гейта в HUD не существует, флаг приходил константным `false` и протаскивался через полтора десятка компонентов (`ComposerToolbar` → `RequestParamsPopover` → селекты) — не возвращай его. `ToggleSelect.disabled` при этом остался: им блокируется thinking (`thinkingLocked`).
- **Коды доступа (прокси-режим).** Альтернатива своим ключам: пользователь вводит одноразовый код, команда `redeem_access_code` (`access.rs`) обменивает его на bearer-токен прокси-сервера (Cloudflare Worker, репо `itech-relay`, дизайн — `docs/superpowers/specs/2026-07-09-access-codes-proxy-design.md`) и кладёт в `Settings.access_token`. **Непустой `access_token` глушит ОБА ключа** — единый источник истины: `build_llm_client`/`build_stt_client` (`app_state.rs`) строят клиент в прокси-режиме (`llm::AnthropicClient::for_proxy` — `Auth::ProxyBearer`, base_url прокси, `Authorization: Bearer` вместо `x-api-key`; STT — тот же bearer с другим base_url, код `stt.rs` не менялся), `apply_key_fallback` не подставляет `.env`, `missingApiKeys` возвращает `[]`. `rebuild_changed_api_clients` пересобирает ОБА клиента при смене `access_token`. Порядок в `apply_access_token`: сеть (redeem) → `save` на диск → rebuild → in-memory (ошибка save = reject, состояние не тронуто). Прокси-URL — константа `access::PROXY_BASE_URL`; env-override `ITECH_PROXY_ENDPOINT` — **только `cfg!(debug_assertions)` и только `https://`** (в релизе игнорируется — защита от редиректа токена/контента). Идемпотентность redeem — ключ из `crypto.randomUUID()` в `localStorage` (`redeem-idem:<норм.код>`), переиспользуется при повторе, чистится при успехе; `normalizeAccessCode` (`lib/access-code.ts`) обязана совпадать с серверной нормализацией. В прокси-режиме `require_ok_status` отдаёт тело `error.message` прокси на 401/403 (понятный текст «код недействителен»/«лимит исчерпан») вместо `BadApiKey`; STT-инвариант «401→BadApiKey без рефоллбэка» сохранён (Groq-путь не трогался).
### Лаунчер автосохраняет `draft` — кнопки «Сохранить» нет

`LauncherPanel` держит локальный `draft: Settings`; любое изменение поля дебаунсится `AUTOSAVE_DEBOUNCE_MS` (600мс) и уходит в `set_settings` через `useSettingsStore.save`. Дебаунс не косметический: посимвольный ввод ключа/кода схлопывается в одну пересборку клиентов (`rebuild_changed_api_clients`).

- `onSave` вызывается ЧЕРЕЗ ref (`onSaveRef`), а НЕ из зависимостей эффекта: `save` делает `adopt(getSettings())` → ре-рендер родителя → новая идентичность колбэка, и если бы эффект зависел от `onSave`, каждое сохранение перезапускало бы эффект и зацикливало автосейв (`save → adopt → ре-рендер → save`).
- Эффект сравнивает `draft` с ref `lastQueuedDraft` **по идентичности** (так пропускаются первый рендер и StrictMode-ремоунт; каждое новое изменение сбрасывает таймер через cleanup).
- Нормализуется (`normalizeDraft`: пустые хоткеи → одноимённое поле `DEFAULT_SETTINGS` + отсев незаполненных пресетов `isPresetFilled`) только сохраняемая копия — сам `draft` в UI НЕ трогается, иначе пустое поле хоткея заменялось бы фолбэком на глазах у пользователя, а полупустой пресет исчезал бы при редактировании. **Свои `FALLBACK_*`-константы под эти фолбэки не заводить**: прежний `FALLBACK_PTT_HOTKEY` был `V` при дефолте `F9`, и очистка поля PTT давала биндинг, которого не бывает при чистой установке.
- При `launching` эффект ранне-выходит, а cleanup гасит отложенный таймер: «Запустить» сам персистит нормализованный `draft` до `launch_main_window`, двойного сохранения нет.
- Слияние `settings.access_token` в `draft` после redeem возвращает ТОТ ЖЕ объект, если токен не изменился, — холостое слияние не должно порождать новую идентичность `draft` и лишний автосейв.
- Автосейв опирается на Rust-инвариант: `reregister_changed_hotkeys` (`preferences.rs`) ранне-выходит, пока main-окна нет, поэтому автосейв хоткеев из лаунчера НЕ дёргает глобальную регистрацию — она происходит один раз в `launch_main_window` из уже персистнутых настроек.
- **Способ достучаться до бэкенда в фиче один: секции импортируют команды из `@/ipc/commands` напрямую** (`SttSection` → `listAudioOutputDevices`, `AppearanceSection` → `applyTheme` из `lib/window-controls`). DI-слой `LauncherPort` был и удалён: половина секций всё равно ходила мимо контекста, и две конвенции в одной фиче стоили дороже прямого импорта. Пропсами приходит только то, у чего есть состояние в `LauncherApp`: `onRedeem` (после успеха дёргает `reload` стора, чтобы токен влился в `settings`), `onCheckUpdates` и целиком `updater` — экран «Обновления» живёт в лаунчере, иначе `update-available` от автопроверки (бьёт через 5 с после старта, когда на экране именно лаунчер) уходил бы в никуда.
### Window chrome (HUD)

Окно `main` — `transparent` + `decorations: false` (фреймлесс, без нативного тайтлбара) + `alwaysOnTop` + `visibleOnAllWorkspaces` + `contentProtected` (невидимо при демонстрации экрана; `Settings.screen_share_visible` снимает защиту через `set_content_protected`). На Windows два флага из этого набора ведут себя иначе, и это не баг вызова: `visible_on_all_workspaces` молча ничего не делает (в tao не реализован), а `contentProtected` работает через `SetWindowDisplayAffinity` и требует **Windows 10 версии 2004+** — на более старых сборках окно попадёт в демонстрацию экрана.

**Размер и скругление:**

- Мышиный ресайз за невидимые края разрешён и синкается в настройки: `useNativeResizeSync` (App.tsx) слушает `onWindowResized` (`ipc/events.ts`, физпиксели → логические через scaleFactor), вычитает превью-экстру и пишет в `Settings.window_width/height` через `applyNativeWindowSize` (кламп + дебаунс-персист).
- Эхо программных твинов гасится guard-окном `PROGRAMMATIC_RESIZE_GUARD_MS` (600мс), которое `useWindowFrameSync` ставит ТОЛЬКО когда цель отличается от текущего нативного размера (`nativeSizeRef`) — иначе живой драг мышью сам себя заблокировал бы. Гейт `readyRef` обязателен: событие до загрузки настроек иначе персистнуло бы DEFAULT_SETTINGS (пустые ключи!) на диск.
- Скругление продублировано нативно: `platform::clip_native_window_corners` вешает `cornerRadius = WINDOW_CORNER_RADIUS_LOGICAL_PX` (22, обязан совпадать с `rounded-[22px]` шелла) + `masksToBounds` на слой contentView — иначе при твине ресайза WKWebView отстаёт на кадр и правые углы мигали бы острыми. CSS-радиус при этом не убирать (клип рисует форму, CSS — фон). На Windows тот же вызов ставит DWM-атрибут `DWMWA_WINDOW_CORNER_PREFERENCE` = `DWMWCP_ROUND`: радиус там системный и под 22px не настраивается.

**Прозрачность и порталы:** `html/body` прозрачны, фон рисует корневой `.app-shell` через альфу `--app-opacity` (слайдер прозрачности ставит переменную на `documentElement`; CSS-дефолт `--app-opacity: 0.9` в `index.css` обязан совпадать с дефолтом `window_opacity` — иначе до загрузки настроек окно рендерится с другой прозрачностью). Не переопределяй `.bg-background` глобально — им пользуется shadcn'овский `DialogContent` и станет полупрозрачным. Портальному контенту (dialog/select/tooltip) нужен `body { color: var(--foreground) }`, потому что он рендерится вне `.app-shell`.

**Модалки:**

- `DialogOverlay` обязан быть `rounded-[22px]` под радиус окна: окно прозрачное+фреймлесс, `fixed inset-0` без скругления залил бы угловые треугольники `bg-black/50` и они торчали бы острыми за скруглением.
- `DialogContent` НЕ использует `overflow-hidden`: в WKWebView `overflow:hidden`+`border-radius` на `transform`-элементе (диалог центрируется через `translate`) даёт острые углы; собственный фон радиус и так уважает, контент внутри `p-6` до углов не достаёт.
- `DialogOverlay` обязан нести `duration-200` под стать `DialogContent`: без него бэкдроп затухал за дефолтные 150мс tw-animate-css, а контент за `duration-200` — фон пропадал раньше модалки.
- **Данные, от которых зависит контент модалки с exit-анимацией, нельзя обнулять синхронно с закрытием** — контент обязан дожить до конца анимации: `ConfirmIdentityDialog` (`IdentityPanel.tsx`) открыт по `open={target !== null}`, но тело (иконка + текст) рисует из залатченного `shownTarget` (санкционированный паттерн «adjust state during render»); иначе при обнулении target тело исчезает мгновенно, пока Radix ещё 200мс проигрывает exit, и модалка дёргано схлопывается по высоте. Латч выглядит избыточным — его удаление вернёт дёрганье.

**HTML-превью ответов** рендерится встроенной панелью `PreviewPanel` (правая колонка того же окна). Контент грузится с отдельного origin (кастомная схема `register_uri_scheme_protocol("preview", …)` в `lib.rs`, отдаёт `App.preview_html`, заполняемый командой `set_preview_html`) в `<iframe src sandbox="allow-scripts allow-same-origin">` — `localStorage`/сеть работают, но cross-origin к `tauri://localhost` + отсутствие capability на схему изолируют превью от IPC и ключей. **Адрес схемы платформенный** — `preview://localhost` на macOS против `http://preview.localhost` на Windows, — поэтому origin руками не собирается: его строит `ipc/preview.previewUrl` через `convertFileSrc("", "preview")` самого Tauri, и это **единственное место фронта, знающее о схеме**; захардкоженный `preview://localhost` на Windows просто не загрузится. Нонс в `src` iframe'а (`…/?v=N`) обязателен: заставляет WKWebView перезагрузить iframe даже при том же HTML и гасит гонку быстрых открытий (устаревший ответ `setPreviewHtml` игнорируется). Открытие расширяет окно на месте через `useWindowFrameSync` (`set_window_size`).

**Телесуфлёр** (`Teleprompter`, оверлей `absolute inset-0` над `.app-shell`) — крупный центрированный текст ответа (`toReadingText` снимает markdown), плавный автоскролл через один rAF-цикл (скролл — программный `scrollTop` на `overflow-hidden`; смещение считает `advanceOffset` по dt, чтобы скорость не зависела от частоты кадров), маска-фейд по краям + фокус-полоса по центру («глаз в одной точке»). Контейнер — `overflow-y-auto` (ручной скролл колёсиком; `onScroll` синхронит `offsetRef`, чтобы автоскролл продолжал с новой позиции, а не прыгал назад). Space — пауза, Esc — закрыть. Позиция/скорость/шрифт персистятся на размонтировании (`onPersist` в cleanup — ловит и закрытие хоткеем): App хранит `{text, offset}` в ref и при повторном открытии восстанавливает offset, если `teleprompter_resume` и текст тот же. Текст — стриминговый `partial`, иначе последний ответ ассистента.

**Левая (чат) колонка — деривированной фикс-ширины** (`chatColumnWidth = window_width − 2·SHELL_PADDING_PX` в App.tsx — симметрично по краям окна), НЕ `flex-1`: иначе при монтировании панели `flex-1` сжимал бы чат на каждом кадре твина (перевёрстка markdown → видимое дёрганье). Ширина меняется только дискретно по хоткею размера; во время твина превью колонка стабильна — панель просто клипается `overflow-hidden` пока окно узкое и проявляется по мере разъезда; чат не релэйаутится и главный поток свободен для твина.
- **Window height меняется только пользователем.** Высота задаётся `Settings.window_height` (хоткей `resize_modifier`+↑/↓); UI-логика высоту не трогает. Ширина — та же база плюс превью: окно = `window_width` + `PREVIEW_EXTRA_WIDTH_PX` при открытом превью, всё через `useWindowFrameSync` → `set_window_size` (эффект гейтится `!settingsLoading`, иначе дефолт затёр бы персистнутый размер, применённый Rust'ом на старте).
- **Платформ две, и они не равны по возможностям.** macOS 14.2+ (Core Audio process tap) и Windows 10 версии 2004+ (WASAPI loopback). На Windows структурно НЕТ трёх вещей: разрешения на запись системного звука (у loopback его не существует — `permissions::AUDIO_REQUIRES_PERMISSION`), разрешения на запись экрана (`screen_capture_access`/`request_screen_capture_access` возвращают `true`) и маскировки облика (нет `.app`-бандла — см. «Маскировка»); ещё `0600` там не ставится, а `visible_on_all_workspaces` — no-op. Одинаково на обеих: внешние ссылки открываются платформенным шеллом (`open(1)` / `ShellExecuteW`), но **фильтр «только `http://`/`https://`» живёт в общем `platform::open_web_url`** — намеренная защита от `file://`/`smb://`, дублировать её в бэкендах не надо; панели системных настроек — `x-apple.systempreferences:` против `ms-settings:`.
- **Имя процесса — «Audio System» по умолчанию (сборочно, стелс), бренд `harpyhare.ai` — только подпись в UI.** `productName` + `mainBinaryName` + window `title` = `Audio System`, identifier = `com.audioservice.helper` (`tauri.conf.json`) → `CFBundleName`, исполняемый файл (`Contents/MacOS/Audio System`, т.е. `ps`/`proc_name`/Activity Monitor/меню-бар) и метаданные окна (`CGWindowList` owner+title) единообразно показывают «Audio System»; на Windows тот же `productName` даёт `Audio System.exe` в диспетчере задач и такую же запись в списке установленных программ (NSIS, установка для текущего пользователя, WebView2 докачивается бутстраппером). Бренд `harpyhare.ai` (`lib/brand.BRAND_NAME`) выводится только внутри приложения (подпись в настройках — её видит лишь пользователь). Пользователь может сменить это на один из 8 обликов маскировки (см. ниже, `identity.rs`) — но только на macOS. Осознанный потолок: `contentProtected` скрывает пиксели окна из захвата, но НЕ факт присутствия — процесс и окно (`CGWindowListCopyWindowInfo` на macOS, перечисление окон и процессов на Windows) видны всегда; от выделенного детектора на той же машине скрыться нельзя. Имперсонация системных процессов (`com.apple.*`) намеренно НЕ используется: ad-hoc-подпись + чужой namespace — сама по себе сигнатура фейка и ломает TCC/нотаризацию. Артефакты сборки (`Audio System.app.tar.gz`, dmg, `Audio System_<версия>_x64-setup.exe`) называются с пробелом (Tauri берёт `productName` дословно); в `release.mjs` загружаемые ассеты и URL в `latest.json` используют ASCII-слаг `AudioSystem` — GitHub заменяет пробелы на точки в именах ассетов и сломал бы ссылку апдейтера.
### Маскировка облика приложения

`identity.rs`, экран «Маскировка» в лаунчере (`IdentityPanel.tsx`). **Фича существует только на macOS, и это не «пока не сделано»**: на Windows нет ни `.app`-бандла с `Info.plist`, ни hard-link на исполняемый файл, ни `codesign`, ни LaunchServices — переписывать нечего. Поэтому `identity/windows.rs` отдаёт понятную ошибку на `prepare`/`apply`/`relaunch`, его `IDENTITIES` пуст, `list()` возвращает один оригинал, а ~5 МБ иконок обликов вообще не попадают в Windows-бинарь (`include_bytes!` живёт в macOS-бэкенде). Команды при этом остаются в контракте — иначе разъедется `bindings.ts` (см. инвариант выше); прячет экран фронт (`screens.ts`, поле `platforms`). Дальше — про macOS. 8 статических обликов (`identity::IDENTITIES`: Obsidian/Spotify/Proton VPN/Discord/Android Studio/Steam/DisplayBuddy/The Unarchiver) — иконки сторонних приложений (`src-tauri/identities/<id>/{icon.icns,icon.png}`, `.png` — кадр `icon_128x128` из `iconutil -c iconset` на исходном `.icns`). Оригинал — встроенная запись `ORIGINAL` (пустой id, имя `identity::ORIGINAL_DISPLAY_NAME` = «Audio System», иконка `icons/icon.icns`); **`identity::list()` отдаёт её ПЕРВЫМ элементом**, поэтому UI — один грид `grid-cols-3` (9 плиток = 3×3), где «Audio System» — обычная плитка, активная при `identity_id == ""` (отдельной кнопки «вернуть оригинал» нет; клик по активной плитке — no-op). Обводка плитки — `ring-1` строго с `ring-inset` (общее правило лаунчера: внешний ring — это box-shadow, у плитки вплотную к кромке скролл-контейнера контента он срезается, и от выделения остаются только дуги на углах).

**Порядок применения** (клик применяется сразу, мимо draft/автосейва лаунчера — как библиотека контекстов). Команда `set_app_identity`: (1) зовёт `identity::prepare` (в `spawn_blocking` переписывает бандл), (2) **только на успехе** персистит `Settings.identity_id` на диск, (3) зовёт `identity::relaunch`. Порядок «сначала переписать бандл, потом сохранить id» намеренный: сбой `prepare` (dev-режим/права) не оставляет `settings.json` впереди реального облика.

**`apply_sync` переписывает установленный `.app` атомарно и в порядке, где `Info.plist` НИКОГДА не ссылается на отсутствующий `CFBundleExecutable`** (частичный сбой оставляет запускаемый бандл):

1. атомарная запись байтов `.icns` (temp+rename) по имени файла из `CFBundleIconFile` (фолбэк `icon.icns`);
2. `link_executable_alias` — hard-link `Contents/MacOS/<старое>` → `<новое>` (оба имени указывают на один inode, оба валидны; на POSIX-ФС не рвёт запущенный процесс — та же гарантия, на которую опирается штатный апдейтер);
3. атомарная подмена `Info.plist` (temp+rename) с `CFBundleExecutable`/`CFBundleName`/`CFBundleDisplayName` = имя облика (`CFBundleIdentifier` НЕ трогается — на нём держится грант TCC на запись звука);
4. `remove_superseded_executable` — удаление старого имени (inode жив как `<новое>`);
5. best-effort ad-hoc `codesign --force -s -` (**без `--deep`** — депрекейтнут, у бандла нет вложенного кода; нет `codesign` в системе — не валит операцию, только eprintln);
6. `bump_bundle_mtime` — `touch` самого `.app` (переименование внутри `Contents/MacOS/` и codesign не бампают mtime верхнего `.app`, а на него завязан кэш иконок LaunchServices/Finder);
7. `reregister_with_launch_services` — best-effort `lsregister -f` бандла: имя в Dock/⌘-Tab — это `NSRunningApplication.localizedName` из записи в базе LaunchServices, ключуемой путём и `CFBundleIdentifier` (оба намеренно неизменны), и эта запись переживает touch/codesign/перезапуск — без форс-перерегистрации Dock показывал старое имя, хотя иконка и имя процесса в Activity Monitor уже менялись.

**Перезапуск** (`relaunch`) — явный `Command::new(<новый путь>).spawn()` + `app.exit(0)`, а НЕ `app.restart()`: после переименования файла `current_exe()` может вернуть протухший путь. Ручной путь даёт 300мс (`PRE_RELAUNCH_RENDER_DELAY`, дорисовать «Применяю…»), стартовое авто-переприменение — без задержки (`Duration::ZERO`). Работает только внутри собранного `.app` (`identity::bundle_dirs()` детектит dev-режим по структуре `Contents/MacOS/…` и отдаёт понятную ошибку вместо паники — в `npm run tauri dev` фича недоступна). Фронт держит таймаут `APPLY_TIMEOUT_MS` (15с) на «Применяю…»: на успехе процесс умирает и промис не резолвится, но зависший `apply` (напр. codesign не отвечает) снимает залипшее состояние.

**Авто-обновление сбрасывает облик** (скачанный бандл всегда «Audio System» — `release.mjs`/`latest.json` не знают про маскировку). `reapply_identity_if_needed` при старте синкает заголовок окна (`set_title`, если `identity_id` не пуст), сравнивает имя текущего экзека с ожидаемым и, если они разошлись, автоматически повторяет `identity::apply` — то есть после рестарта апдейтера следует ещё один рестарт, восстанавливающий выбранный облик.

**Риск TCC:** пересборка ad-hoc-подписи меняет cdhash при каждой смене облика — macOS может (не обязательно) заново спросить право «Запись системного звука» (recovery — `open_audio_permission_settings`); `CFBundleIdentifier` неизменен намеренно, чтобы минимизировать этот риск. `Settings.identity_id` клампится по статичному списку (`identity::is_known_id`) — неизвестное значение сбрасывается в `""`.

### Снимок области экрана

Хоткей действия `screenshot` (дефолт ⌘⇧S / Ctrl+Shift+S) или иконка `Crop` в тулбаре Composer → выделение области → PNG уезжает вложением в черновик активного чата. Общая часть (`screenshot.rs`) — проверка разрешения, `backend::capture_region()`, base64 и события; оверлей у каждой платформы свой. На macOS это **C-код, вкомпилированный в бинарь приложения** (`src-tauri/native/region_capture.c`, собирается `cc` в `build.rs` **только под macOS**, экспорт `harpy_capture_region`/`harpy_capture_region_free`, Rust-обёртка — `screenshot/macos.rs`). Исходник взят из плагина `harpyshot` (репозиторий `harpyhare-plugins`), но живёт здесь копией: sidecar-процессом его делать нельзя — грант TCC «Запись экрана» ключуется по cdhash, и у отдельного ad-hoc-бинаря он бы переспрашивался после каждой пересборки, тогда как у самого приложения он один на бандл.

Инварианты C-оверлея macOS (нарушишь — крэш или зависший UI):

- **Снимок всего экрана делается ДО показа оверлея** (`CGDisplayCreateImage` через `dlsym` — символ депрекейтнут, но на macOS 26 есть), выделенная область потом вырезается из него `CGImageCreateWithImageInRect`. Иначе в кадр попало бы собственное затемнение. Окно HUD в кадр не попадает вообще — оно `contentProtected`.
- **ObjC-классы оверлея регистрируются один раз**: `objc_getClass` перед `objc_allocateClassPair` обязателен — при втором вызове `allocateClassPair` вернёт NULL, и `objc_registerClassPair(NULL)` уронит приложение (в изначальном плагине проблемы не было: процесс жил одну активацию).
- **NSWindow сабклассится ради `canBecomeKeyWindow = YES`** — borderless-окно иначе не становится key и не получает keyDown, то есть Esc не отменял бы выделение.
- **Каждое событие своего цикла форвардится в `[NSApp sendEvent:]`** — цикл `nextEventMatchingMask` крутится внутри главного потока приложения, и без форварда всё остальное приложение стоит, пока пользователь тянет рамку.
- **Вызов только с главного потока** (`app.run_on_main_thread`) — это AppKit; команда и обработчик хоткея оба идут через `screenshot::on_capture_region`.
- Только главный дисплей (`CGMainDisplayID`); мультимонитор — отдельная задача.

Windows-оверлей (`screenshot/windows.rs`) — свой Win32 на GDI, и грабли те же по смыслу, но другие по механике: **снимок всего ВИРТУАЛЬНОГО экрана делается ДО показа окна** (`SM_XVIRTUALSCREEN`…, мультимонитор поддержан, начало координат может быть отрицательным — не считай его нулём); **класс окна регистрируется один раз за процесс** (`OnceLock`: повторный `RegisterClassW` вернул бы 0 — ровно та же грабля, что с `objc_allocateClassPair` в ObjC-версии, и по той же причине: процесс переживает много активаций); рисование двойной буферизацией с инвалидацией только изменившейся области (рамка + её прошлое положение), иначе полноэкранный перерисов на каждое движение мыши; **`PostQuitMessage` НЕ зовётся** — `WM_QUIT` убил бы цикл сообщений самого Tauri, выход из локального цикла идёт по флагу состояния; отмена — Esc, ПКМ или слишком маленькое выделение; результат — PNG без альфы.

Хост-часть: разрешение проверяется в Rust ДО оверлея (`platform::screen_capture_access`; на Windows такого права нет и функция всегда `true` — ветка «нет доступа» там просто недостижима); нет доступа → уходит `screenshot-error` с кодом `permission` **без системного промпта** (промпты живут только на экране «Доступы», см. ниже). Успех → PNG в base64 → `screenshot-ready` → `useRegionScreenshot` → **`useChats.addDraftImage`, то есть тот же конвейер вложений, что вставка/дроп картинки** (`fileToAttachment`, даунскейл >5 МБ, лимит вложений) — своей ветки обработки изображений у снимка нет. Хоткей регистрируется в `window::register_main_window_hotkeys` (жизненный цикл HUD, как PTT/toggle/суфлёр) и перерегистрируется в `set_settings`; пока HUD не запущен, он не слушается. UI настройки — группа «Горячие клавиши» на экране настроек; разрешение «Запись экрана» выдаётся на экране «Доступы».

### Доступы (единственное место выдачи прав)

Весь раздел — **про macOS**: на Windows у WASAPI loopback разрешения нет вовсе (`permissions::AUDIO_REQUIRES_PERMISSION = cfg!(target_os = "macos")` — статус звука сразу `granted`, ни промптов, ни проб), у записи экрана тоже, поэтому экран «Доступы» там скрыт целиком (`screens.ts`, поле `platforms`). **Гейт готовности при этом выводится ТОЛЬКО из `permissions_status`, а не из видимости экрана**: на Windows команда отдаёт `granted`, блокера не возникает, и вести в никуда нечему. Соблазн написать «звук требуется, только если экран доступов есть» надо давить: тогда любая правка реестра экранов (перенос доступов внутрь «Настроек», ещё одна платформа) молча снимала бы требование доступа к звуку — ровно тот регресс, ради которого гейт и живёт в лаунчере. Команды доступов остаются в контракте на обеих платформах. Поля `audio_permission_requested`/`screen_permission_requested` на Windows не используются и остаются в `Settings` намеренно: форма настроек и биндинги обязаны совпадать на обеих платформах.

Все TCC-разрешения выдаются с одного экрана лаунчера (`features/launcher/screens/PermissionsScreen`, данные — хук `usePermissions` поверх `permissions.rs`). Модалки нет: на первом запуске лаунчер сам открывается на экране блокера (`LauncherPanel`, реф `landed` + `readiness.blockers[0].screen`), в остальное время экран доступен из сайдбара. Разрозненных точек выдачи больше нет и заводить их нельзя: удалены `useCapturePermission`/`useScreenCapturePermission`, баннер разрешения в HUD, строка «Запись экрана» во вкладке хоткеев и шесть отдельных команд (`capture_available`, `request_audio_capture_permission`, `open_audio_permission_settings`, `screen_capture_available`, `request_screen_capture_permission`, `open_screen_capture_settings`) — вместо них три: `permissions_status`, `request_permission(kind)`, `open_permission_settings(kind)`.

**Ни один системный промпт не должен появляться сам по себе** — только в ответ на кнопку «Выдать». Отсюда два инварианта:

- **`setup_app` НЕ создаёт капчер** (`App.capture` стартует `None`). Создание Core Audio tap и есть запрос разрешения: раньше он строился на старте и macOS показывала промпт при первом запуске, до того как пользователь что-то нажал. Капчер поднимается лениво — `recording::ensure_capture` при запуске HUD и при явном запросе доступа. Не возвращай `build_capture` в `setup_app`. **И не зови его из `launch_main_window` синхронно** — только `spawn_blocking`: создание капчера медленное (на Windows старт WASAPI-потока ждёт готовности до 5 секунд), а `launch_main_window` — синхронная команда, поэтому ожидание внутри неё держит запуск целиком: окно HUD уже создано, но вебвью не успевает отрисоваться (белое окно), а лаунчер не уничтожается, потому что до его `destroy` дело не дошло. Жизненный цикл окна не должен зависеть от готовности звука: нет устройства — HUD всё равно открывается, а PTT честно сообщает об ошибке.
- **Состояние звука знать без промпта нельзя** (у Core Audio нет preflight, в отличие от `CGPreflightScreenCaptureAccess`), поэтому первый запрос фиксируется флагом `Settings.audio_permission_requested`: пока он `false`, статус — `unknown` и проб не делается; после первого нажатия «Выдать» статус определён, и повторная проба уже безопасна (промпт возможен только при статусе «не спрошено»). По той же причине `rebuild_capture_now` (смена аудиоустройства) ранне-выходит, пока капчер ни разу не строился и флаг не взведён.
- **`screen_permission_requested` — про «спрашивали ли», а не про сам доступ.** `CGPreflightScreenCaptureAccess` не отличает «отказано» от «ещё не спрашивали», а без этого различия модалка всплывала бы при каждом запуске у того, кто осознанно отказался от необязательного доступа. Поэтому: preflight `true` → `granted` (даже если флага нет — доступ могли выдать мимо приложения), иначе флаг решает `denied` против `unknown`. Автооткрытие модалки — по `needsAttention` (звук не выдан ИЛИ про экран ещё не спрашивали), а не по `allOk`.

`PermissionState` — `unknown | granted | denied`. Звук required (без него кнопка запуска HUD заблокирована), запись экрана — нет: она нужна только снимку области.

**Геометрия строки доступа не зависит от его состояния** — это не косметика. TCC-промпт на звук асинхронный: команда возвращает `denied` раньше, чем пользователь нажмёт «Разрешить», то есть статус меняется прямо под курсором, и любая зависимость размеров от состояния дёргала бы кнопку из-под пальца. Отсюда: колонка действий фиксированной ширины (`grid-cols-[…_10.75rem]`), у «Выдать» `min-w-18`, у пояснения `min-h-9` (одна и две строки занимают одинаково), набор кнопок одинаков для `unknown` и `denied` — у `denied` «Выдать» работает повторной пробой и ловит ровно этот случай («разрешил по промпту после того, как команда уже вернула отказ»); только `granted` убирает кнопки, и по высоте строка от этого не меняется. Про недостающий доступ говорит статус в шапке рядом с кнопкой «Запустить»: он называет блокер словами и кликом ведёт на его экран — `disabled` без объяснения не оставляем.

### Лаунчер: шапка, сайдбар, экраны

Окно лаунчера — три части: **шапка** (`LaunchBar`: бренд, статус готовности, «Запустить»), **сайдбар** (`Sidebar`) и **экран** (`ScreenShell` + содержимое). Реестр экранов — `screens.ts` (`LAUNCHER_SCREENS`: id, лейбл, описание, иконка, группа и **необязательный список платформ**: без него экран есть везде, с `platforms: ["macos"]` — «Маскировка» и «Доступы» — на Windows не рисуется вообще); сайдбар рисует группу `content` сверху и группу `system` (Настройки, Доступы, Обновления) прижатой к низу через `mt-auto`. Фильтрует один `screenGroup(group, platform)`; гейт готовности на видимость экранов НЕ опирается (см. «Доступы»). Модалок в лаунчере не осталось: доступы и обновления — полноценные экраны, а не диалоги.

- **Заголовок и описание экрана рисует только `ScreenShell`**, по данным из `screens.ts`. Панель внутри своих заголовков не заводит — иначе вернётся прежняя тавтология, когда лейбл вкладки повторялся заголовком карточки внутри неё.
- **Готовность структурная, а не булева.** `useLauncherReadiness` отдаёт `blockers: {label, screen}[]`, `checking` и `ready`. `checking` (`!permissions.loaded`) обязателен: `audioOk` до ответа `permissions_status` равен `false`, и без этого флага настроенный пользователь на КАЖДОМ запуске видел «нет доступа к звуку» и заблокированный запуск. Кнопка запуска гасится при `checking || !ready || launching`, а статус рядом с ней называет первый блокер словами и ведёт на его экран.
- **Первый экран выбирается по блокеру** (реф `landed` в `LauncherPanel` — ровно один раз за сессию окна, после того как доступы опрошены). Нет ключей → «Настройки», нет звука → «Доступы», всё в порядке → `DEFAULT_SCREEN`.
- **Форма настроек — один язык на все строки** (`fields.tsx`): `SettingGroup` (карточка с заголовком и описанием, строки разделены `divide-y`), `SettingRow` (подпись + пояснение слева, контрол в колонке фиксированной ширины справа), `SettingBlock` (когда контрол занимает всю ширину), `SettingSelect`/`SettingSwitch`/`SettingSlider`. Прежние `Field`/`SelectField`/`SwitchRow`/`SectionColumns` удалены: подпись поля и подпись тумблера рисовались двумя разными способами, а трёхколоночная сетка ломала длинные лейблы.
- **Ограниченное число задаётся только слайдером с readout.** Голый `type=number` для `move_step`/`resize_step`/`scroll_step`/`buffer_seconds` удалён намеренно: `Number("")` давал 0, а введённое сверх лимита оставалось в UI, хотя Rust уже клампнул значение на диске (`draft` синкается из `settings` только по `access_token`). Слайдер физически не выходит за `SETTINGS_LIMITS` — рассинхрона нет by design.
- **Парные настройки живут в одной строке.** Модификатор и его шаг (перемещение / размер / скролл) настраиваются вместе в `WindowSection`; раньше модификатор был во вкладке «Горячие клавиши», а шаг — во вкладке «Вид», и так трижды.
- **Поверхности лаунчера разведены светлотой, а не альфой.** Переопределения живут в `body.launcher` (и `:root[data-theme="black"] body.launcher` — иначе чёрная тема не доедет из-за равной специфичности): `--background`/`--card`/`--surface`/`--surface-active` — непрозрачные ступени, `--ring` отвязан от `--primary` (бордовое кольцо при 50% альфы было практически невидимым в окне настроек). Это единственный шов, который не задевает HUD: окна — разные документы, но `index.css` общий, поэтому в `:root` для лаунчера ничего не правим.
- Шкала шрифтов дополнена ступенями `--text-title`/`--text-display` (`cn` знает о них через группу `font-size` в `lib/utils.ts`). Добавление ступеней HUD не трогает; менять `--text-body`/`--text-caption` глобально нельзя — на них стоит вся вёрстка чата.

### Хоткеи: реестр действий

Все клавиатурные команды приложения перечислены **в одном месте** — `src-tauri/src/hotkeys.rs`, константа `HOTKEY_ACTIONS` (уезжает в биндинги через `.constant()`, фронт читает её же). У действия есть `id`, `group`, `label`, `hint`, `kind`, `scope` и `default_combo`. Захардкоженных сочетаний в коде больше нет и заводить их нельзя: и Rust, и фронт спрашивают `hotkeys::effective(&settings.hotkeys, ACTION_X)` / `effectiveCombo(settings.hotkeys, "x")`.

- **`kind`** — `combo` (полное сочетание), `modifier_arrows` (модификатор + стрелки) и `modifier_plus_minus` (модификатор + `+`/`−`). Семейства не разворачиваются в четыре биндинга на стрелку: у них хранится только модификатор.
- **`scope`** — где действие слушается: `global` (шорткат ОС, живёт вместе с HUD), `recording` (только пока идёт запись), `hud` (обработчики вебвью), `teleprompter` (только пока открыт суфлёр).
- **Пустой `combo` = «не назначено»**, действие просто не регистрируется. `normalizeDraft` в лаунчере больше НЕ подставляет дефолт вместо пустого значения — иначе снятый хоткей возвращался бы сам собой.
- **`default_combo` — не строка, а пара платформ** (`PlatformCombo {macos, windows}`): Rust берёт своё через `.current()`, фронт — через `defaultCombo(id, platform)` с дефолтом `PLATFORM`. Основной модификатор выводится макросом `primary_combo!` (⌘ на macOS, Ctrl на Windows), поэтому пары не выписываются руками. **На Windows клавиша Win под модификатор не отдаётся** — она занята системным снапом окон, а `Win+Shift+S` вообще системный снимок экрана; закреплено тестом `windows_defaults_avoid_the_super_key` (проверяет и дефолты, и `MODIFIER_COMBOS.windows`). Windows-дефолты: `Ctrl+Enter`, `Ctrl+Shift+S`, `Ctrl+Shift+H`, `Ctrl` (сдвиг), `Ctrl+Shift` (размер и прозрачность), `Alt` (скролл); F9/F10/`Escape`/`Space` общие. Тесты реестра (`hotkeys/tests.rs`) прогоняют разбор и отсутствие конфликтов для ОБЕИХ платформ, а не для текущей: платформа тестового хоста про вторую не говорит ничего.

**Конфликт = пересечение по клавишам И сосуществование областей.** Пересечение: два `combo` совпадают по модификаторам и клавише (регистр и порядок модификаторов не важны, `KeyS` и `S` — одно и то же); два семейства одного вида — по модификатору; `combo` конфликтует с семейством, если его модификатор совпадает, а клавиша попадает в семейство (стрелка либо `+`/`−`). Разные семейства (`arrows` и `plus_minus`) на одном модификаторе НЕ конфликтуют — именно поэтому дефолтные «изменить размер» и «прозрачность» оба живут на одном модификаторе (⌘⇧ / Ctrl+Shift). Не сосуществуют только `recording` и `teleprompter`, поэтому `Esc` штатно стоит и на отмене записи, и на закрытии суфлёра.

**Политика разрешения — отобрать у прежнего владельца** (как в IDE): новое назначение всегда применяется, а конфликтующее действие остаётся без хоткея, о чём в UI пишется строкой «‹сочетание› снят у действия ‹название›». Это правило реализовано дважды и обе реализации покрыты тестами: `hotkeys::normalize` в Rust (последний в списке биндингов побеждает; вызывается из `Settings::clamp`, то есть на каждом `set_settings`) и `assignHotkey` во фронте (`lib/hotkey-conflicts.ts`, даёт мгновенный отклик и список `stolenFrom`). Расходиться им нельзя — правила пересечения зеркальны, тест-кейсы совпадают по смыслу.

**Миграция.** `hotkeys::migrate_legacy_fields` правит сырой JSON **до** десериализации в `Settings` (`Settings::load`): семь старых полей превращаются в биндинги, значения, совпадающие с дефолтом, не переносятся, сами поля из json убираются. Если `hotkeys` уже непустой — миграция ничего не делает. Поэтому кастомные сочетания пользователя переживают обновление, а `Settings` не тащит легаси-поля.

**Словарь клавиш.** `Shortcut::from_str` (tauri) принимает буквы, цифры, F1–F24, стрелки, `Space`/`Enter`/`Tab`/`Escape`/`Backspace`/`Delete`, `Home`/`End`/`PageUp`/`PageDown`, знаки препинания и нумпад. Раньше узким местом был фронт: `hotkeyFromEvent` умел только буквы, цифры и F-клавиши — теперь он отдаёт `event.code` для всего перечисленного (буквы и цифры нормализуются в короткую форму). **`Escape` остаётся отменой захвата** в `HotkeyCapture`, поэтому назначить его мышью нельзя — он приходит только дефолтом, а вернуть его можно кнопкой сброса строки.

**Горячий путь.** Обработчики `keydown` не разбирают строку сочетания на каждое нажатие: `prepareCombo` вызывается один раз в эффекте (`useWindowControls`, `Teleprompter`), скролл чата по-прежнему держит `parseModifier` в эффекте (`AnswerPanel`). Стрелки с автоповтором иначе аллоцировали бы массив на каждый кадр.

**Не настраивается намеренно:** `↵` (отправить) и `⇧↵` (перенос строки) в поле ввода — это поведение текстового поля, а не команда приложения; `⌘V`/`Ctrl+V` — событие вставки, а не хоткей. В справочнике HUD они показаны отдельными подсказками — `fieldHints(platform)` в `lib/hotkeys.ts` (была константа `FIELD_HINTS`, стала функцией: подписи платформенные, и группа берётся из реестра, а не литералом).
