# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**harpyhare** — a Tauri 2 desktop app for **macOS 14.2+ and Windows 10 version 2004+** (the process disguises itself as "Audio System"; the `harpyhare` brand lives in the UI only). Hold a push-to-talk key → capture **system audio** (e.g. voice from a video) → transcribe via Groq Whisper → edit the text (with pasted screenshots) → stream an answer from the Anthropic API.

**There are two windows, and that is the single most important thing to know about the frontend's structure.** The app starts at the **launcher** (`launcher.html` → `src/launcher.tsx` → `features/launcher/LauncherApp`) — an ordinary centred window with settings, the context library, the masks and a "Launch" button. The HUD (`index.html` → `src/main.tsx` → `src/App.tsx`) — a floating frameless always-on-top window — is **created on demand** by the `launch_main_window` command and destroyed by `stop_main_window` (the button in the HUD header returns you to the launcher). Both entry points are built by one Vite config (`build.rollupOptions.input: {main, launcher}`) and share `src/lib`, `src/ipc`, `src/hooks` and `src/components/ui`, but they do NOT share state: each window has its own React root and its own store. The root bootstrap is shared — `lib/render-root.renderWindowRoot` (find `#root` + StrictMode + `QueryClientProvider`) — which is why `main.tsx`/`launcher.tsx` are three lines each; a third entry point goes through the same helper rather than a copy of it.

Consequences that are easy to break: (1) **`tauri.conf.json` describes no windows at all** (`"windows": []`) — both are created in code (`window::create_launcher_window` from `setup_app`, `window::create_main_window` from `launch_main_window`), so sizes and flags (`transparent`/`decorations`/`alwaysOnTop`/`contentProtected`) are set there and not in the config; both functions take `&Settings` as a parameter, and content protection is applied ONCE through the builder flag `.content_protected(...)` — the post-build second call has been removed, and `window::apply_content_protection_all` survives only for changing the setting on the fly, walking both windows; (2) global hotkeys are registered on `launch_main_window` and removed on `stop_main_window` — the launcher has none; (3) readiness (API keys + audio recording permission) is checked in the launcher (`useLauncherReadiness`), not in the HUD — the HUD starts up already ready.

Two halves: a **Rust backend** (`src-tauri/src/`) and a **React 19 frontend** (`src/`). The backend does all the privileged/native work; the frontend is pure UI over a typed IPC boundary.

It lives in `apps/desktop/` of the **harpyhare** monorepo (Nx + npm workspaces; the landing page is `apps/landing`). Every path and command below is relative to `apps/desktop/` (run them from that folder, or through Nx from the root: `nx <target> desktop`). The monorepo overview is in the root `CLAUDE.md`.

## Code style

- **Comments are allowed, but they are not free.** The former blanket ban has been lifted. The spirit of the rule is unchanged: knowledge lives in speaking names, and the coherent "why it is this way" picture lives in this file. A comment earns its place where a name cannot hold the reason: an invariant the compiler does not check (drop order, lock acquisition order, a required order of operations), a workaround for someone else's bug, a non-obvious formula. A comment that restates the code (`// increment the counter`) is still noise. A comment does not replace a section in CLAUDE.md: the whole picture stays in the file, and a short marker stays at the site in the code.
- **Hardcoding is forbidden.** Magic values → named constants; anything computable is derived, not copied; model behaviour comes from the capabilities API, not from lists of names (the only acceptable by-name exceptions are described in the models section).
- **One responsibility.** Functions/components that do several things are split into small ones with speaking names.
- **Public contracts change only in lockstep on both sides.** IPC commands/events, serde keys, on-disk formats (settings.json, chats.json), the hotkey string format (`hotkeyFromEvent` ⇄ `parse_hotkey`).

## The Rust ⇄ frontend contract (read this first)

The backend exposes a **fixed set of commands and events**; the frontend mirrors them 1:1. When changing one side, change the other and keep names identical.

- **The contract is generated from Rust, not written twice.** `src/ipc/bindings.ts` is a **generated file, never edit it by hand**: it is written by `cargo test` (the `bindings::tests::typescript_bindings_are_up_to_date` test, `tauri-specta` + `specta-typescript`). Inside it: a typed `commands.*` object (command names and arguments are no longer strings), every type that crosses the boundary, and the constants declared through `.constant()` in `bindings.rs` — `SETTINGS_LIMITS`, `SETTINGS_DEFAULTS` (the whole of `Settings::default()`), `MODIFIER_COMBOS`, `HOTKEY_ACTIONS` and `QUICK_ACTION_LIMIT`. The file is excluded from eslint/prettier/knip. Added a command → `#[tauri::command] #[specta::specta]` + a line in `collect_commands!` in `bindings.rs` → `cargo test` regenerates the bindings. **Types that travel only through an event are not picked up automatically** — they must be listed in `.typ::<>()` in the same place, otherwise they will be missing from the bindings and `contract.test.ts` will have nothing to check against. **specta does not export `u64`/BigInt**: mark the field `#[specta(type = f64)]` (as the byte counts in `UpdateProgress` are) — it still crosses the boundary as a JS number; `usize` is rejected by the same `BigIntForbidden`, so a `usize` constant is cast right inside `.constant()` (`settings::QUICK_ACTION_LIMIT as u32`) — without the cast it is the bindings generation test that fails, not the frontend build. **`bindings.ts` must come out IDENTICAL on macOS and on Windows.** The file is generated on the build machine and committed, and CI runs `cargo test` + `git diff --exit-code src/ipc/bindings.ts` (on the macos runner: on the windows runner the test binary fails to start, see the root CLAUDE.md) — a value that depends on `#[cfg]` would split the file across the two hosts and break the build. Three consequences follow: platform defaults travel as a **pair of platforms** (`PlatformCombo {macos, windows}` on `HotkeyAction.default_combo`, `MODIFIER_COMBOS.macos`/`.windows`) rather than as the "current" value — only Rust itself calls `.current()`; commands that do not work on the second platform are NOT removed from `collect_commands!` — they stay in the contract and return a clear error; and there is no "which platform is this" constant in the bindings at all — the frontend determines it itself (`lib/platform.ts`).
- **Commands are registered in `bindings.rs`** (`collect_commands!`); `lib.rs` only hands over `specta_builder.invoke_handler()`. `src/ipc/commands.ts` is a **direct re-export** (`export const {cancelStream, closeApp, …} = commands`); a hand-written wrapper is introduced ONLY when it adds behaviour or a hand-written type: `sendToClaude`/`countChatTokens` (`ChatMessageDto`/`RequestOptions`), `getSettings`/`setSettings` (a cast to the hand-written `Settings`), `checkForUpdate` (`UpdateInfo`), `redeemAccessCode` (idempotency), `startWindowDrag` (not a command but a window JS API). Do not write one-line forwards — there were about 28 of them and they have been deleted.
- **Hand-written types on the frontend stayed for ergonomics, but the compiler checks them.** The generated `Settings` is weaker than the hand-written one (`#[serde(default)]` makes every field optional, and `f64` in specta becomes `number | null`), so `ipc/types.ts` keeps clean interfaces while `ipc/contract.test.ts` holds the type-level assertions `SameShape<Ours, Rust.X>` for `Settings`, `AppError`, `UpdateInfo`, `RecorderState`, `PromptPreset`, `AudioDeviceInfo`, `RequestOptions` and the event payloads (LLM, `resize-key.dim`, `update-progress`, `update-done`). Rename/remove/retype a field in Rust and `tsc -b` fails on that file. Do not delete these assertions — without them the hand-written types will start drifting again (verified: renaming a field in the bindings breaks the build). **`SameShape` also compares the key sets (`SameKeys`), and that third check is not cosmetic**: two assignability checks are not enough, and a field forgotten in the hand-written type used to pass them SILENTLY — in `Generated` it is optional (so `Ours` is assignable), and structural typing permits extra properties (so `Loosened<Generated>` is assignable to `Ours`). That is exactly how `audio_permission_requested`/`screen_permission_requested` survived: 28 fields in Rust against 26 declared on the frontend (the count at the time of the discovery), with a green test. Runtime survived it only because the settings object is always produced by spreading the real JSON from Rust; build it as a literal somewhere and `set_settings` would receive the field missing, and `#[serde(default)]` would silently overwrite the user's value with the default.
- **Settings bounds live in Rust and are exported.** `settings::limits` (grouped: `window`/`chat`/`teleprompter`/`capture`) is the single source of `default/min/max`; both `Settings::default()` and `Settings::clamp()` read from it, as does the `SETTINGS_LIMITS` constant in the bindings. `lib/window-size.ts` stays framework-free (its own numbers), but the `window-size.test.ts` test compares them against `SETTINGS_LIMITS` — let them drift and the test fails. A new numeric setting = a `Bounds` entry in the right group + a field + a control; there are no separate `DEFAULT_*`/`*_MIN`/`*_MAX` constants any more. **Launcher controls read `min`/`max` from `SETTINGS_LIMITS` directly — do not introduce a local copy of the bounds**: local copies have already drifted (the `chat_font_size` slider was 11–18 against a Rust clamp of 10–20, and the user could not set values the backend accepts). All that stays local in the sections is the slider's `step` — the registry has no such thing.
- **`set_settings` returns the applied (clamped) `Settings`**, not `()`. The frontend must adopt them as the new state (`useSettingsStore.save` → `adopt`) rather than re-reading `get_settings` in a second round trip: otherwise the UI keeps the raw value the user typed until the second command's answer arrives.
- **Request options travel as an object, not a scattering of flags.** `send_to_claude`/`count_chat_tokens` take `options: RequestOptions {thinking, webSearch}` (Rust `llm::RequestOptions`, `#[serde(rename_all="camelCase", default)]` ⇄ `lib/chats.RequestOptions`, assembled by `chatRequestOptions(chat)`). A new request option = a field in those two types + a control in the UI; the signatures of `sendToClaude`/`useClaudeStream.send`/`useSendPipeline` are left alone. Previously `thinking`/`web_search` were passed positionally through five signatures in a row.
### Events

They are emitted **only through the typed helpers in `events.rs`**, and there are no exceptions left: the names, the payload structs and the helpers for every event (including `update-*` and `official-presets-updated`) live there, and `Emitter` is not imported anywhere else. The frontend listens through `src/ipc/events.ts`, and the types are `EventMap` in `src/ipc/types.ts`. The list: `state-changed`, `transcript-ready`, `stt-error`, `llm-delta`, `llm-done`, `llm-error`, `llm-usage`, `update-available`, `update-progress`, `update-done`, `toggle-teleprompter`, `resize-key`, `official-presets-updated`, `screenshot-ready`, `screenshot-error`, `focus-prompt` (empty payload, like `toggle-teleprompter`; it has two emitters — `show_and_focus_prompt` and `recording::deliver_transcript`, see "Window control"), `auto-turn`, `auto-mode-changed`, `auto-mode-error`. The LLM events carry a `chatId` (`{chatId, delta}` / `{chatId}` / `{chatId, code, message}`) — streams are independent per chat. `resize-key.dim` is not a string but the Rust enum `ResizeDim` (`serde(rename_all="lowercase")` → the union `"width" | "height"` in the bindings).

**Errors are typed by code, not by text.** `stt-error` carries `AppError {code, message}`, and `llm-error` carries the same plus `chatId` (the fields are listed explicitly, without `serde(flatten)` — otherwise specta will not export the type). The codes (`error.rs` in Rust, `lib/errors.ts` on the frontend; the lists must match): `network | badApiKey | badAccessCode | retryable | api | cancelled | permission | silence | internal`. UI branching goes ONLY by `code` (`isRetryable` → the "Retry" button, `isNetworkError` → `ConnectivityOverlay`); `message` only ever goes on screen. The frontend used to parse Russian prose with regexes (`/перегружен|соединение|VPN/`) — do not bring that back; rewording an error message must not break anything. A new error variant: an enum variant + `CodedError::code()` in Rust ⇄ a string in `ErrorCode` on the frontend.

**Deltas are coalesced in Rust and revealed smoothly on the frontend.** `llm-delta` accumulates in a ~25 ms flusher in `chat::send_to_claude`; the final buffer drain must go out **before** `llm-done`, otherwise the frontend loses the tail of the answer. On top of the coalescing, `useClaudeStream` reveals the buffer in a rAF loop rather than all at once (`lib/stream-reveal`: speed by dt = max(minimum, a fraction of the lag per second) — display lag is capped at ~100 ms; the slice never splits surrogate pairs). On done/stop/error the FULL buffer goes into history, not the revealed part — the instant catch-up of the tail at the end is deliberate.

**Context fullness comes entirely from the API, with no hardcoded windows:**

- Numerator fallback: `llm-usage {chatId, inputTokens}` from the stream's `message_start.usage` — the SUM of `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` (with prompt caching on, bare `input_tokens` is nearly zero!). It is written to `Chat.lastInputTokens` and persisted in chats.json — an instant fallback when you enter a chat.
- Denominator: `ModelInfo.maxInputTokens`.
- **The primary figure is a projection through `count_tokens`:** the `count_chat_tokens` command (Rust `AnthropicClient::count_tokens`, `POST /v1/messages/count_tokens`, free, no lease on the proxy) computes how much the NEXT request will take (system + the current history); the `useProjectedContextTokens` hook in App.tsx (400 ms debounce; for an empty chat a placeholder message `.`, so that the weight of the library materials counts even before sending).
- Result: `usedTokens = projected || lastInputTokens` → `ContextUsageGauge` in the header (StatusBar, before the action icons; hidden while there is no data or the model's window is unknown).
- **The proxy (the `itech-relay` repo) must route `/v1/messages/count_tokens`** — otherwise it 404s and the projection does not work.

### Settings (36 fields)

Defined identically in `src-tauri/src/settings.rs` and `src/ipc/types.ts` (the two sides are checked by `ipc/contract.test.ts`). Do NOT duplicate the numeric bounds in this file — they live in `settings::limits` (see above). **Defaults are not duplicated either**: `DEFAULT_SETTINGS` in `ipc/types.ts` (it initialises the store before the first `get_settings`, and `normalizeDraft` in the launcher takes its fallbacks from it) is assembled from the generated `SETTINGS_DEFAULTS` rather than listing values by hand — if a field disappears or is renamed in Rust, `tsc` fails right on that object literal. The spread `prompt_presets: [...SETTINGS_DEFAULTS.prompt_presets]` there is **mandatory and not up for "simplification"**: specta prints the constant with `as const`, so the array arrives `readonly`, while `Settings.prompt_presets` is mutable (the launcher edits it directly in the draft) — without the copy it is a type error.

**There is no global system prompt or model in Settings** — instead there are `prompt_presets: {id,name,text}[]` (seeded with "Speech transcription", id `transcription`) and per-chat fields. A chat stores `presetId`, `thinkingEnabled`, `model`, `webSearch` (the "Request parameters" popover in the Composer toolbar — the toolbar is icon-based inside the prompt card and is identical at any window width; model and pre-prompt are selects, while the boolean thinking and web search are `Switch` toggles via `ParamToggle`. The former `ToggleSelect` with its two "On/Off" items has been removed and **is not coming back**: the same boolean settings in the launcher were always a toggle (`SettingSwitch`), and a dropdown costing two clicks for one bit in the HUD was the most visible sign of "two different apps in one product". **The row's label and the toggle's `aria-label` must be one constant** — `THINKING_PARAM_LABEL`/`WEB_SEARCH_PARAM_LABEL`: the label is rendered by `ParamRow` while the `aria-label` sits on the control itself, and they can only ever drift apart silently — nothing on screen shows it) and `context` (the "Context" dialog — the chat's permanent reference text). `system` is assembled on the frontend (`App.dispatchSend`): the preset's text (`lib/presets.presetText`) + the selected context-library materials (`lib/context-library.libraryContextBlocks` by `chat.libraryDocIds`) + the chat's context, and all of it goes into `send_to_claude(messages, chat_id, system, model, options)` on every request (the Anthropic API is stateless). A new chat's defaults are `NEW_CHAT_DEFAULTS` in `lib/chats.ts`, which double as the fallback when deserialising an old chats.json: no pre-prompt (`presetId=""`), `thinkingEnabled=false`, `model` = `DEFAULT_MODEL` (haiku 4.5, `lib/models.ts`), `webSearch=false`, `context=""`. Old chats missing the corresponding field get the same default (backwards compatibility with previously saved opus/thinking-on values is deliberately NOT kept — there are no real users with an old chats.json).

**Appearance and chat:**

- `chat_font_size` → the CSS variable `--chat-font-size` (`applyChatFontSize`), scaling the chat's text and code.
- `theme` — `"gray"` (the default, CSS variables on `:root`) or `"black"` (overrides in `:root[data-theme="black"]`); applied by `applyTheme` (a data attribute on documentElement), and unknown values are clamped to gray in `settings.clamp` and `applyTheme` in lockstep.
- `scroll_step`/`scroll_modifier` — the step and modifier for scrolling the chat with the arrow keys (default `Alt`; the handler is `useHotkeyScroll` in AnswerPanel, a document-level keydown with preventDefault — caret jumping between paragraphs via Option+arrows is sacrificed, following the precedent of Cmd+arrows).

**Window:**

- `window_width`/`window_height` — the HUD's base logical size (default 960×680); applied when the HUD is created (`window::create_main_window`) and on every change through `useWindowFrameSync` in App.tsx.
- `move_step`/`resize_step` — the step for the window move/resize arrow hotkeys; the modifiers themselves are no longer stored as separate fields, they are bindings in `hotkeys` (platform defaults: ⌘ and ⌘⇧ on macOS, Ctrl and Ctrl+Shift on Windows). All three modifiers (`move`/`resize`/`scroll`) are offered by the launcher's select strictly from the `hotkeys::MODIFIER_COMBOS` registry, and that registry is **paired by platform**: six combos on macOS against four on Windows (the Win key is not offered as a modifier). Free-form gluing of known tokens was rejected: `Cmd+Ctrl` passed validation but is not in the list, and the select rendered empty for such a value. For the layers' responsibilities see "Window control".
- `screen_share_visible` — show the window during screen sharing (see Window chrome). The only setting with TWO places to change it: the toggle in the launcher and the indicator in the HUD header.

**Speech recognition:**

- `stt_language`/`stt_translate` — Whisper's language and translation into English (see stt.rs).
- `capture_device_uid` — the UID of the output device to capture (`""` = system default + automatic tap recreation when it changes; see capture.rs).
- `buffer_enabled`/`buffer_seconds` — the background ring buffer of the last N seconds of system audio (on by default): the audio is continuously resampled to 16 kHz and lives in RAM only (`audio::RollingBuffer` inside `capture::Shared`); when a PTT recording starts, a snapshot of the buffer is automatically prepended to the transcription (both to the streaming Groq body and to the session accumulator) — catching what was said before the key went down. Switching the toggle off clears the buffer immediately, and nothing is ever written to disk; the side effects of changing the fields are in `apply_buffer_settings_change` inside `set_settings`; when the tap is recreated the buffer starts over (losing ≤10 s is accepted knowingly).

**Teleprompter:** `teleprompter_speed`/`teleprompter_font_size` (the clamps are mirrored in `lib/teleprompter`), persisted when the teleprompter closes; the shortcut that opens it is NOT stored as a separate field — it lives as the `teleprompter` action in the registry (default ⌘⇧T / Ctrl+Shift+T); `teleprompter_resume` (default `true`) — the teleprompter opens at the saved scroll position if the answer text is the same, otherwise from the top.

**Quick actions:** `quick_actions: {id, title, prompt}[]` — the row of buttons above the HUD's input field (three seeds: `detail`/`brief`/`code`), plus `quick_action_attachments` (default `false`) — whether to mix the draft's attachments into such a message. Off by default on purpose: a quick action must be predictable and send exactly its own prompt, not drag along a screenshot forgotten in the field; the "took a screenshot → pressed the button" pairing is enabled deliberately with a single toggle. The limit `settings::QUICK_ACTION_LIMIT = 9` is **derived from the hotkey, not picked by eye**: invocation is a modifier plus a digit 1…9, and there is nowhere for a tenth button's combo to come from; so `Settings::clamp` trims the tail of the list and the launcher disables "Add" at the limit. **A saved empty array stays empty**: `#[serde(default)]` substitutes the seeds only when the field is absent from the json entirely — buttons the user deleted do not rise again on restart (locked down by the `load_saved_empty_quick_actions_stays_empty` test). Rust does NOT filter out incomplete actions: the frontend filters them when rendering and the launcher filters them when saving (see "Quick actions" in the frontend section and `normalizeDraft`).

**Hotkeys:** a single `hotkeys: Vec<HotkeyBinding {action, combo}>` field replaces the former seven strings (`hotkey`, `toggle_hotkey`, `teleprompter_hotkey`, `screenshot_hotkey`, `move_modifier`, `resize_modifier`, `scroll_modifier`). An empty array = everything at the registry defaults; see "Hotkeys: the action registry".

**Everything else:** `anthropic_api_key`/`groq_api_key`/`access_token` (see "API keys" and "Access codes"), `auto_send`, `auto_preview_html`, `skipped_version`.
- **Models are dynamic, not hardcoded.** The `list_models` command (Rust `llm::list_models`, `GET /v1/models`, free) returns the account's models with a capabilities digest (`ModelInfo {id, displayName, adaptive, alwaysThinks, codeExec, maxInputTokens}`; `maxInputTokens` comes from the `max_input_tokens` field of the `/v1/models` response, and is 0 = "unknown" for the fallback models); the cache is `App.models`, the initial fetch happens at start, and the frontend reads it through `useModels` (with `lib/models.FALLBACK_MODELS` as the fallback). `useModels` returns not the whole list but a curated trio: `curatedModels` (lib/models) keeps the freshest model of the opus/sonnet/haiku families — the first occurrence of a family in `/v1/models` order (the API sorts newest first), so dated ids are not hardcoded and new versions are picked up automatically; the Rust cache `App.models` stays complete (capabilities are found even for an old chat's model outside the trio, and `selectableModels` will mix it into the select). The `thinking` field is assembled by `llm::thinking_value` from capabilities: on → `adaptive` where supported; off → an explicit `{"type":"disabled"}` (on Sonnet 5 "omit the field" means adaptive!); haiku (which does not support adaptive) and Fable/Mythos ("always thinking" — the only by-name exception, since capabilities do not express it) → the field is not sent at all. The thinking toggle in the Composer is greyed out through `lib/models.thinkingLocked`. Web search (`llm::web_search_value`) is the server-side tool `web_search_20260209` in `tools` (Anthropic searches on its own, inside the same stream — there is no client-side tool loop); models without code execution (haiku, `capabilities.code_execution`) require `allowed_callers:["direct"]`, otherwise the API rejects the request (verified with live probes — the tool versions themselves are not expressed in capabilities).

## Frontend architecture (`src/`)

Strict layering — keep each layer's responsibility intact:

- **`src/ipc/`** — the **only** place that imports `@tauri-apps/api`. `commands.ts` (typed `invoke`), `events.ts` (`onEvent`/`onFileDrop`/`onWindowResized`), `types.ts`. Commands/events call Tauri directly — **the browser mock is gone**: the frontend runs only inside Tauri (the internet and the Rust backend are both required). There used to be an `env.ts` with `isTauri()` gates and no-op/fallback behaviour in the browser — it has been deleted entirely (see connectivity below).
- **`src/lib/`** — framework-free pure logic with unit tests: `platform.ts` (the pure `detectPlatform(userAgent)` + `PLATFORM` from `navigator.userAgent` — **the single source of the platform on the frontend**: we never ask Rust for it, otherwise `bindings.ts` would diverge; everything platform-dependent — hotkey labels, "from Finder"/"from Explorer", launcher screen visibility — takes the platform as a parameter defaulting to `PLATFORM`, so tests can exercise both), `api-keys.ts` (`missingApiKeys`/`missingKeysNotice` — which API keys are missing and the banner text), `errors.ts` (`ErrorCode`/`AppError`/`isRetryable`/`isNetworkError`/`internalError`/`asAppError` — the mirror of the Rust error codes; all "retry/offline" logic lives here, not in components), `composer.ts` (attachment limit/downscale, the `Attachment` type), `chats.ts` (the chat model, `CHAT_LIMIT`, serialize/deserialize, `chatImageIds`/`hydrateChatImages` — substituting image bytes after loading), `models.ts` (`ModelInfo`, `FALLBACK_MODELS`, `thinkingLocked`), `auto-turns.ts` (ordering and the send policy for auto mode), `hotkey-capture.ts` (`hotkeyFromEvent`, `conflictsWithTyping`), `hotkey-modifier.ts` (`parseModifier`/`matchesModifier` — matching a keyboard event's modifiers against the setting), `window-controls.ts` (`applyOpacity`/`applyChatFontSize`/`applyTheme`/`isDraggableChromeTarget`), `stream-reveal.ts` (`advanceReveal`/`sliceRevealed` — the maths of smooth stream reveal for `useClaudeStream`), `stream-markdown.ts` (`splitStableTail` — splitting the stream into a stable prefix and a tail so the markdown parse can be memoised; the prompt field's auto-growth is the JS hook `usePromptAutosize` in Composer via scrollHeight + ResizeObserver, because `field-sizing: content` does not work in WKWebView), `teleprompter.ts` (`toReadingText` markdown→prose, `advanceOffset` scroll maths, `clampSpeed`/`clampFont`).
- **`src/hooks/`** — one hook per contract slice (`useClaudeStream`, `useChats`, `useModels`, `useRecorder`, `useTranscription`, `useAutoMode`, `useWindowControls`, `usePttSuspend`, `usePromptFocus`, `usePermissions`). **Settings come in two layers:** `useSettingsStore` (the shared one: loading, `save`, `reload`, applying visual settings through a callback) is used by both windows; `useSettings` is a HUD-only layer on top (the debounced persistence of `bumpOpacity`/`bumpWindowSize`/`applyNativeWindowSize`) and does not expose `reload` — only the launcher needs to re-read after a redeem. The launcher uses `useSettingsStore` directly. `useChats` owns the chat list, per-chat drafts/attachments, and disk persistence (chats and image bytes go into two different files, see "Chats and the context library"). **Per-chat fields change through a single `patchChat(id, patch: ChatPatch)`**, not through a setter per field (there used to be seven: `setChatPreset`/`setChatThinking`/`setChatModel`/`setChatWebSearch`/`setChatContext`/`setChatLibraryDocs`/`setChatUsage` + `setDraft`). `ChatPatch` (`lib/chats.ts`) is a `Partial<Pick<Chat, …>>` over the mutable fields; `messages`/`id`/`title` are not edited through it (they have their own methods). `Composer` takes `chat: Chat` + `onPatch` rather than 15 props. A new per-chat field = a field in `Chat` + one in `ChatPatch` + a control in the UI; `ChatsApi`, `AppComposer` and `ComposerProps` are left alone. **The caret in the prompt field belongs to the `usePromptFocus` hook, and so does the textarea ref**: `App` → `Composer.promptRef` → `PromptTextarea.fieldRef`; it is the same node that serves the auto-growth (`usePromptAutosize`), and no second ref should be introduced. Focus is set on mount (HUD launch) and on the `focus-prompt` event from Rust, with the caret **at the end of the text**: otherwise, after dictation or a region screenshot, you would have to type at the start of the line. **The suppression gate is not "do not focus" but "remove focus"**: while a full-screen overlay is open (the teleprompter or `ConnectivityOverlay`), the field gets `blur()`, and when the overlay closes the caret comes back — a half-measure gate (merely refusing new focus) left the caret in the field UNDERNEATH the overlay, typing went into an invisible draft, and `Enter` sent the message blind. Radix modals are deliberately NOT part of the gate: their focus trap already rolls back our `.focus()`, and enumerating dialogs would mean a list that drifts. The suppression flag is read through `useLatestRef` (`hooks/useLatestRef.ts` — the shared "always the freshest value in a ref" shim, moved out of `App.tsx` when it was needed here too): otherwise the `focus-prompt` subscription would be recreated on every overlay open and close. Hooks depend on `ipc`, never on `@tauri-apps` directly; tested with `renderHook` + `vi.mock("@/ipc/...")`.
- **`src/components/`** — presentational, built on shadcn/ui primitives in `src/components/ui/` (run `npx shadcn@latest add <name>` to add more). `App.tsx` composes hooks + components.

Stack: React 19 + Vite + Tailwind v4 (CSS-first `@theme` tokens in `src/index.css`, a gray + oxblood dark theme, dark-only) + react-markdown + rehype-highlight. Path alias `@` → `src`. **Shape and depth are set by tokens, not by literals in the markup.** `--radius` = 8px with a ladder built from it (`sm` 4 / `md` 6 / `lg` 8 / `xl` 12; `--radius-xl` is set explicitly — without it `rounded-xl` would take Tailwind's fixed default of 12px and come unhooked from `--radius`): controls are `rounded-md`, cards are `rounded-lg`, the composer card is `rounded-xl`, and `IconButton` defaults to `rounded-md` (the former `rounded-full` has been dropped). The window radius is a separate variable, `--window-radius`, and **not a single literal `rounded-[22px]`/`[14px]`/`[10px]` is left in the code**: `ConnectivityOverlay` was the last to move onto the variable. Shadows are `@theme` tokens as well: `--shadow-btn` (filled buttons), `--shadow-raise` (the cards' top inner light), `--shadow-pop` (menus, popovers, the launcher's search results), `--shadow-modal` (dialogs); **inputs, textareas and selects have no shadows at all** — they are separated by the `--input` hairline border, and shadcn's stock `shadow-xs` has been stripped from every field and is not coming back. Focus is one thing across the whole codebase — `focus-visible:ring-2`; there are no `ring-[3px]` rings left. Icon stroke width is set globally (`svg.lucide { stroke-width: 1.75 }` in `index.css`) and is not adjusted with a prop on an individual icon. `--font-sans` is set explicitly (SF Pro Text on macOS, Segoe UI Variable Text on Windows) so as not to rely on the webview's default UI stack: without an explicit stack, WebView2 serves classic Segoe UI with no optical sizing. The theme is dark-only with no second half: `@custom-variant dark (&)` in `index.css` makes shadcn's stock `dark:` classes unconditional, so the duplicating layer of them has been removed entirely — **not a single `dark:` is left in the markup** — and one dragged in from a fresh shadcn snippet will not "enable dark theme" but silently override the class next to it. **Palette rule: primary (the oxblood red) is NOT used as a text colour** (section headings, links, badges, chips are neutral `text-foreground/*`); primary is allowed only for indicators (dots, the equaliser, list markers, the active tab's underline), button fills and `destructive` errors. **The indicator dots have a fixed vocabulary**: `destructive` = "needs the user to act" (readiness blockers in the header status and in the sidebar), `primary` = "fine / brand / information" (ready to launch, permission granted, an update available), muted `muted-foreground` = the neutral "checking / not granted / not set". Painting a blocker in primary "so as not to scare anyone" is not allowed — then two opposite situations look the same. For the sake of that same vocabulary, **`--destructive` has been separated from `--primary` in BOTH hue and lightness** (oklch `0.6 0.21 27` against `0.47 0.17 18`): while both sat on hue 18, the "blocker" and "ready" dots at 6px (`size-1.5` in the sidebar and in the header status) were impossible to tell apart — merging them back onto a shared tone is not allowed.

**Code highlighting:** rehype-highlight in `AnswerPanel` (`REHYPE_PLUGINS`); the token palette is in `index.css`. The invariant: `html` in `plainText` — the preview chip (`HtmlBlockChip` through `makePre`) requires the code element's children to stay a **raw string**; highlighting would turn them into an array of spans and silently break the chip. During streaming the markdown chunks are memoised (`MarkdownChunk` + `splitStableTail`) — history and completed blocks are not reparsed on every delta flush. `splitStableTail` splits the stream into prefix/tail ONLY at a `\n\n` paragraph boundary outside a fenced code block (the "inside a fence" test is an odd number of fence markers, backtick or tilde, in the prefix): an unclosed fence would break the rendering of both halves. **`AnswerPanel` re-renders in full on EVERY frame of the stream reveal** (`partial` changes in the rAF loop of `useClaudeStream`/`stream-reveal`), and `MessageShell`/`UserBubble` are not memoised — which is why `MessageImages` is wrapped in `memo`, and **the wrapper must not be removed**: `imageDataUrl(image)` in the render body would rebuild the data URL, a string the size of the image itself (a screenshot's base64 is hundreds of kilobytes, up to megabytes), frame after frame and exactly while the main thread is busy revealing the answer. The image itself was not being repainted even before `memo` — React compares `src` by string VALUE, the attribute is not reassigned and the browser does not re-decode it — the cost was precisely in allocating garbage for the GC and in the character-by-character comparison of two identical megabyte strings. **`memo` on `MessageShell` is impossible in principle**: it receives `children` and the `onCopy`/`onRemove`/`onResend` callbacks created by inline arrows right inside the `.map` over messages — a shallow prop comparison will never match. `UserBubble` could technically be memoised (`text` is a stable string, `images` is a stable reference) and that would subsume the `memo` on `MessageImages`, but that is **deliberately not done** — the wrapper goes exactly where the megabyte is allocated, otherwise the code no longer shows what is being protected, and the very first inline prop on `UserBubble` would silently strip the images' protection. The memoisation rests on the stable `m.images` reference: `patchChat` copies the chat with a spread and never touches the `messages` array, and stream deltas live in `useClaudeStream`'s state rather than in the chats; start rebuilding `images` on every render and `memo` will silently stop helping. Locked down by the test "the data URL is not rebuilt on every stream frame" (`AnswerPanel.test.tsx` counts `imageDataUrl` calls through a partial mock of `@/lib/composer`; it has been verified that with `memo` removed the test fails). For the same reason **the attachment key in `AttachmentList` (`Composer`) is the index, not `att.preview`**: the draft's list re-renders on every keystroke (the draft lives in the chat's state), and a full data URL in `key` forced React to hash megabyte strings on every render. The index is correct here rather than lazy: the length is capped by `ATTACHMENT_LIMIT` = 5, items are only appended at the end and removed, there are no reorderings, and `onRemove` already works by index. **`att.id` is unsuitable as a key** — it is a content hash (`chat_images::content_id`), so the same image attached twice yields two attachments with the SAME key, and for anything that has not survived saving the id is empty (`NOT_PERSISTED_IMAGE_ID`) for all of them at once. The accepted price of the index: deleting from the middle changes the remaining chips' `src` and the browser re-decodes them — imperceptible across five small previews.

**Chat scrolling:**

- **Scroll-to-bottom on chat switch happens synchronously BEFORE paint** (`useLayoutEffect` in AnswerPanel, not `useEffect`): otherwise the browser manages to show a frame at the old position → a visible "flight from top to bottom".
- **There is deliberately NO autoscroll during streaming** (stick-to-bottom was irritating — the scroll "ran away" and only stopped when you scrolled up by hand): the only things that scroll down are switching chats, sending YOUR OWN message (the growth of messages with a user tail in AnswerPanel) and the "↓ Down" button; the growth of `partial` merely updates the button's visibility (`syncJump`).
- `content-visibility` on messages is deliberately NOT used: it made `scrollHeight` an estimate (off-screen elements collapse to intrinsic-size), so the pre-paint scroll missed the bottom and had to be finished off with a rAF loop — that crutch went away with it. For a genuinely huge history the right tool is virtualisation (virtua), not content-visibility (which breaks `scrollHeight` accuracy).

**A message's action buttons never cover the text:** no absolute chip on top — a flex layout in `MessageShell` (for a user bubble the buttons sit to its left in the free zone, for the assistant there is a permanent right-hand gutter wide enough for one button), revealed on hover through opacity alone (the space is reserved, so the layout never jumps).

- Hover is plain CSS `group-hover`, but **WITHOUT `transition-opacity`**: in a transparent frameless window an opacity animation promotes the element into a separate WKWebView compositing layer, and when that layer collapses, unflushed pixels remain (buttons "stuck" visible on several messages at once — with a correct DOM! — until a full repaint triggered by switching chats; screenshots even showed ghosts of text from earlier frames). The `:hover`/`mouseleave` events had nothing to do with it — JS hover tracking was tried and reverted as unnecessary.
- The rule: hover-reveal controls appear and disappear instantly, with no opacity transitions (removed in `AttachmentChip`, `ContextLibraryPanel` and `PresetsSection`). In the hidden state they get `pointer-events-none`, lifted by the same `group-hover:`/`focus-within:` that lifts the transparency, so invisible buttons cannot catch clicks; the launcher's clusters are gated by the same rule. **Not a single `transition-opacity` is left in the codebase** — the last one lived on a dialog's close button and was replaced with a colour transition (`text-muted-foreground` → `hover:text-foreground`); an empty grep for it is the check for the rule. The delete button additionally paints its icon `destructive` on hover — the buttons have no labels, and that is the only thing distinguishing "delete" from "edit" before the click.
- `StreamingAssistant`'s padding (`ASSISTANT_ACTIONS_GUTTER_CLASS`) must equal the gutter's width — otherwise a finished answer re-flows as it moves from the stream into history. The arithmetic: `gap-1` 4px up to the cluster + `size-6` buttons of 24px each separated by `gap-0.5` 2px. The assistant has TWO buttons (copy, delete), so 4+24+2+24 = 54px = `pr-13.5`; it was `pr-7` (28px) while there was only one button. **Add a button to `MessageActions` and you must recompute this class**, otherwise the stream and the history will drift apart along the right edge.
- **Copying a message: the text, or the image when there is no text.** For a message consisting of a single screenshot with no caption, the button would otherwise copy an empty string; the rule `messageCopyText` → `messageCopyImage` (`lib/message-clipboard`) covers exactly that case. The image goes to the clipboard THROUGH RUST (`clipboard::copy_image_to_clipboard`), not through `navigator.clipboard`: the same proven path the region screenshot uses. Before sending it, the frontend re-encodes the image to PNG with a canvas (`imagePngBase64`), because `tauri::image::Image::from_bytes` is built with the `image-png` feature and can handle png ONLY, while attachments may be jpeg/gif/webp; an image that is already PNG the canvas leaves alone. Writing PNG to the clipboard lives in one place — `clipboard.rs` (`write_png`, called by `screenshot::deliver` too); do not duplicate it across modules.

**Quick actions are a row of buttons above the input field** (`QuickActionsBar` sits **outside** the `Composer` card, as a separate row above it; the list editor is `QuickActionsSection` on the launcher's "Settings" screen). The button shows `title` while `prompt` is what goes into the chat — the prompt itself is not visible on the button; the same invocation is available as a "modifier + digit" hotkey (`useQuickActionKeys`). **They have their own send path, and `appendUserMessage` is not reused:** `useChats.appendQuickActionMessage` NEVER touches the draft's text (an unfinished question must survive pressing ⌘1) and clears `draftAttachments` only if they actually went into the message; an ordinary send still clears both. Attachments are mixed in only when `quick_action_attachments` is on. Assembling the system prompt and the history and starting the stream are factored out into a shared `streamChat` inside `App.useSendPipeline` — it is shared by `dispatchSend`, `dispatchQuickAction`, `dispatchAutoTurn` and `resendFromMessage`, and a new sender must not grow its own copy of that assembly.

**Quick actions have four gates, and each closes its own hole:** the row is rendered only when `!settingsLoading` — otherwise the seeds from `DEFAULT_SETTINGS` show up at start and vanish once `get_settings` answers, jolting the composer's height; `runQuickActionAt` does not fire while a full-screen overlay is open (`promptCoveredByOverlay` — the teleprompter or `ConnectivityOverlay`), because a quick action's prompt is ALWAYS non-empty and without the gate ⌘1 would send a message blind with any draft in the field (an ordinary send is protected by the empty draft, and here there is no such protection); `useQuickActionKeys` discards `e.repeat`, otherwise a held digit sends a second message at exactly the moment the `streaming` flag is cleared; the `onMouseDown` with `preventDefault` hangs on the row's CONTAINER rather than on the buttons — the row is mostly empty and sits right above the field, so a miss next to a button would pull the caret out of the prompt.

**Numbering follows the filtered `filledQuickActions`** (both the title AND the prompt filled in) and must match between the HUD and the launcher: ⌘2 in the settings and ⌘2 on the button are the same action, otherwise the labels lie. The label is assembled by `quickActionHint` (`lib/quick-actions`), and the "combo + key" gluing by `formatComboWithKey` (`lib/hotkeys`): these used to be two copies with their own separator constants in the two windows.

**The internet is mandatory + a connectivity loader.** Offline mode is not supported. Connectivity detection is the `useConnectivity` hook (`hooks/useConnectivity.ts`): `offline` is initialised from `!navigator.onLine`, and on mount there is an active probe, `probe_connectivity` (the Rust command `AnthropicClient::reachable` — an authorised GET of `{base_url}/v1/models` with a short timeout; **any HTTP response means there is a connection**, while a connect/DNS/timeout error means there is not; in proxy mode it automatically hits the same proxy). It listens to the `online`/`offline` events; while `offline` it re-runs the probe every 4 s and clears the flag on success. App additionally raises `offline` through `connectivity.reportNetworkError()` when the combined `error` (`sttError ?? stream.error`) carries the text of `LlmError/SttError::Network` ("No connection"). While `offline`, a full-screen `ConnectivityOverlay` is rendered (`absolute inset-0 z-50` above `.app-shell`, next to the teleprompter's overlay) — it **does not unmount the chat or the streams** and is removed automatically. The network fallbacks for the model list (`FALLBACK_MODELS`/`fallback_models()`) and the embedded presets are kept on purpose (an instant render before the first fetch + a seed for `presets:publish`).

## Rust backend (`src-tauri/src/`)

**Providers sit behind ports — the command layer knows nothing about Anthropic/Groq.** `App.llm: Mutex<Arc<dyn llm::LlmProvider>>` and `App.stt: Mutex<Arc<dyn stt::SttEngine>>` are trait objects, not concrete clients.

- `llm::LlmProvider` — `stream(LlmRequest, cancel, &mut dyn LlmStreamSink)` / `count_tokens(LlmRequest)` / `list_models()` / `reachable()` / `warm_up()`. `LlmRequest {model, system, messages, options}` is neutral: no `thinking` field, no `tools`, no JSON. Assembling the Anthropic body (`build_request_body`, `thinking_value`, `web_search_value`) lives ONLY inside `impl LlmProvider for AnthropicClient` — it must never appear in the command layer (`chat.rs`).
- The provider resolves capabilities itself: `AnthropicClient` holds `catalog: ModelCatalog` (`Arc<Mutex<Vec<ModelInfo>>>`, the same Arc as `App.models`), `list_models()` refreshes it and `capability_fields()` reads it. The former `find_cached_model` in `lib.rs` is gone — do not bring it back.
- `stt::SttEngine` — `transcribe(&[f32])` / `transcribe_stream(AudioChunkStream, cancel)` / `warm_up()`. `AudioChunkStream = Pin<Box<dyn Stream<Item = Result<Vec<u8>, io::Error>> + Send>>` — **`reqwest::Body` does not cross the port boundary**; `wrap_stream` is called inside `GroqStt`.
- Stream deltas go into `LlmStreamSink` (two callback functions will not do — both would hold a `&mut` on the same buffer); in `chat.rs` it is implemented by `ChatStreamSink` (ttfb perf timing + pushing into the flusher's buffer + emitting `llm-usage`).
- A second provider (a different model / a local STT) = a new `impl` + a line in `build_llm_client`/`build_stt_client`; neither `lib.rs` nor the frontend changes.

**Windows are created ONLY from the main thread.** `launch_main_window`/`stop_main_window` are async commands, and their entire body goes through `window::on_main_thread` (`run_on_main_thread` + `oneshot`, with the result awaited, so the main thread is not blocked and there is no deadlock). The reason is not cosmetic: on Windows, creating a WebView2 waits for its own thread's message queue to be pumped, and Tauri commands do NOT execute on the main thread — from a worker thread `WebviewWindowBuilder::build()` never returns. From the outside it looks like this: the HWND appeared (a white window with no content), the command hangs, the launcher is not destroyed, and the button is stuck at "Launching…" forever. On macOS the same thing is silently marshalled to the main thread, so the bug is platform-specific and invisible locally. The launcher window is created at startup in `setup_app`, i.e. already on the main thread — which is why it worked while the HUD was never opened.

**`device_event_filter(Always)` in `lib.rs` is not an optimisation but a precondition for arrow interception on Windows.** By default tao registers raw input for keyboard and mouse, and while OUR window is focused every keystroke additionally loads the main thread with a `WM_INPUT` message and a forced repaint. The low-level hook's callback lives on the same thread and must fit within `LowLevelHooksTimeout`; miss it and Windows removes the hook silently and permanently, with no way to learn about it. Hence the symptom "the arrows do not work at all, but only while the window is active" ([tauri#13919](https://github.com/tauri-apps/tauri/issues/13919)). `Always` removes the registration entirely (`Never`, despite the name, does the opposite and extends it to the unfocused state), and nothing in Tauri reads `DeviceEvent` anyway. For the same reason the callback itself must stay cheap: the decision is made synchronously, while moving the window and emitting `resize-key` are carried off the input thread (`handle_arrow_key` → `spawn` → `run_on_main_thread`).

**`tauri` must be ≥ 2.11.5 (`tauri-runtime-wry` ≥ 2.11.4).** In 2.11.2 the DPI getter leaks an `HDC`, which makes resize responsiveness of a `decorations: false` window on Windows degrade progressively and never recover without a restart ([tauri#15569](https://github.com/tauri-apps/tauri/issues/15569)). Downgrading is not allowed.

**`lib.rs` is assembly only (~100 lines): `run()`, `setup_app()` and passing `invoke_handler` from `bindings::builder()`.** Everything else is laid out across modules, each owning its own `#[tauri::command]`s; put a new command in the module it belongs to by meaning and add it to `collect_commands!` in `bindings.rs` (the single list). There are deliberately no re-export shims (`pub use app_state::App`, `pub use window::…`) in `lib.rs` — call the module by its full path, otherwise `lib.rs` will start accreting surface again.

The domain modules (`audio`, `capture`, `stt`, `llm`, `state`, `settings`, `error`) are unchanged — they know nothing about Tauri. The domain modules are pure and unit-tested. **Unit tests live separately from the code**: at the end of `src/<mod>.rs` there is only the `#[cfg(test)] mod tests;` declaration, and the body is in `src/<mod>/tests.rs` (a child module — `use super::*` gives access to private items, which is why these are NOT integration tests in `tests/`, where only the public API is visible); put new tests in the same place and do not introduce inline `mod tests {}`. Platform backend tests follow the same convention one level down: `src/<mod>/macos/tests.rs`.

**Platform splitting is one technique used across all modules.** `src/<module>.rs` is the platform-neutral facade holding all the portable logic, with `src/<module>/macos.rs` and `src/<module>/windows.rs` beside it, wired up by `#[cfg(target_os = ...)] mod ...; use ... as backend;`. `capture`, `platform` and `screenshot` are split this way; the other modules are shared. **Do not introduce a `#[cfg]` branch in the middle of shared code** — a platform call is added to BOTH backends, the second one with an honest error or a no-op where necessary (`disable_cursor_autohide_on_typing` in `platform/windows.rs`): otherwise the facade starts knowing about platforms and drifts away from the contract (see the invariant about an identical `bindings.ts`). A `cfg!` gate in shared code survives only where it is a single value rather than a branch of logic: `permissions::AUDIO_REQUIRES_PERMISSION = cfg!(target_os = "macos")`, the `#[cfg(unix)]` file mode in `settings::create_owner_only`. **Platform crates must live in `[target.'cfg(target_os = "…")'.dependencies]`** (`cidre`/`objc2*`/`block2`/`plist` — macOS; `windows` 0.61 with an explicit feature list and `png` — Windows): in the shared `[dependencies]` they do not merely "pull in extra weight", they break the other platform's build. **`[build-dependencies]`, however, must NOT be gated that way: their `cfg` matches the build HOST, not the target.** We keep `cc` in the shared build dependencies and gate only its INVOCATION (`build.rs` compiles the C overlay and links the Apple frameworks when `CARGO_CFG_TARGET_OS == macos`). The trap is non-obvious and invisible locally: on a macOS host, `cfg(target_os = "macos")` in build dependencies is true for any `--target`, so a cross-check of the Windows build does not catch it — only the real build on the windows runner fails (`cannot find crate cc` in build.rs).

- `audio.rs` — downmix → resample (rubato, 48k→16k) → WAV (hound); an RMS silence gate. `StreamResampler` is the incremental resampler for streaming (the batch `resample_to_16k` goes through it too — a single code path; besides, rubato's `process_all_into_buffer` duplicates the first `output_delay` frames, and the incremental path is free of that bug); the sinc parameters are deliberately "speech-grade" (`sinc_len=32`) — a studio-grade 128 for 16 kHz Whisper has already been rejected (~4x CPU for nothing); `wav_header_streaming` (sizes 0xFFFFFFFF) + `f32_to_i16le_bytes` for the streaming upload's body. `SpeechSegmenter` (endpointing for auto mode) lives here too — see the auto mode section.
- `capture.rs` — system audio capture: a portable facade + two backends (**a Core Audio process tap** through `cidre` on macOS, **WASAPI loopback** on the output device on Windows). The riskiest native piece; details are in a separate section below.
- `stt.rs` — `GroqStt` (whisper-large-v3-turbo; the language from `Settings.stt_language`, "" = autodetect; `stt_translate` → the `/audio/translations` endpoint + the whisper-large-v3 model, because turbo cannot translate and the language field is not sent), error mapping; `transcribe_stream` is a multipart with a streaming body (chunked, unknown length; Groq accepts this — verified with a live smoke test); its overall timeout is deliberately generous (11 min): the body lives for the whole recording (up to 10 min), and the usual 60-second timeout would cut the stream off. The client is recreated in `set_settings` when the key/language/translation changes.
- `llm.rs` — the Anthropic request body (image blocks; the `thinking` field is prepared by `thinking_value` and the web search `tools` element by `web_search_value`, both from the model's capabilities; prompt-cache breakpoints on the system prompt and on the last message; empty messages are dropped from the history — the API rejects empty content), an incremental `SseParser` (use `feed_bytes` for chunked UTF-8; the web search's server_tool_use events are ignored — only text deltas reach the UI), a streaming client with cancellation; API error bodies are forwarded to the UI (`error.message`, not a bare HTTP code). Diagnosing request bodies against the live API is `examples/llm_smoke.rs`.
- **Every reqwest client sends a `User-Agent`** (`llm::APP_USER_AGENT` = `AudioSystem/<version>`; llm, stt, access): reqwest without a UA runs into Cloudflare's Browser Integrity Check on the proxy → intermittent `403 error code: 1010`; non-JSON error bodies are now included in the message (`api_error_message` — a snippet of up to 120 characters).
- **The `itech-relay` proxy (a Cloudflare Worker, repo `screenfriskofficial/itech-relay`).** Worker changes are deployed separately: `wrangler login` (interactive) → `wrangler deploy` (node ≥22, e.g. `PATH=/opt/homebrew/opt/node@25/bin:$PATH`). Known worker invariants: (1) **There are no rate limits on requests** (removed 2026-07-21): the concurrency lease was deleted (the app's chats stream simultaneously) and the daily caps are `MAX_SAFE_INTEGER` — `usage_daily` accounting is still kept for `/admin/usage` but never cuts anything off; the clamps are not below the client's values (`max_tokens` 64000, `web_search max_uses` 10; the client sends 64000/5). What remains: an IP limit on `/v1/redeem`, body size limits (LLM 32 MB, STT 26 MB) and the route/model allowlist. The upstream `fetch` MUST carry `signal: request.signal` — otherwise, when the client cancels (the "Stop" button), the worker reads the generation to the end and the owner pays for the full answer. (2) `/v1/messages/count_tokens` is routed by an explicit branch (with no debit) — it is needed for the context fullness indicator. Both reqwest clients (`stt`/`llm`) are created once for the whole runtime, keep the pool "forever warm" (`http2_keep_alive_*`, `pool_idle_timeout(None)`) and have a `warm_up()`; the warm-up is called at app start and on a PTT press (Anthropic; Groq is not warmed up — its streaming request goes out immediately). In commands the client is cloned out of the state (the clone shares the pool's Arc) — among other reasons so as not to hold a MutexGuard across an `.await`. Perf timings are written to stderr with a `[perf]` prefix.
- **Streaming transcription.** On a PTT press, `on_ptt_pressed` opens the request to Groq (`App.stt_stream`) and the body is filled with 16 kHz chunks through the capture's sink; on release, `finish_transcribe` waits for the already running request ("release → text" ≈ inference + RTT). Cancellation (Esc/silence/too short a recording) is `cancel_stt_stream`; the order when cancelling a recording is mandatory: `cancel_stt_stream` first, `capture.stop()` only afterwards. On channel overflow the sink marks the stream `broken`; any stream failure (other than `BadApiKey`) falls back to the classic `transcribe` over the accumulated buffer — the feature degrades but does not break recognition. On the frontend, `transcript-ready` is APPENDED to the draft (`lib/composer.appendTranscript`) rather than replacing it; with `auto_send` on, the combined text is what goes out.
- `error.rs` — `ErrorCode`/`AppError` and the `CodedError` trait (implemented by `LlmError`, `SttError`, `CaptureError`); `AppError::from(&err)` = the code + the `Display` text. Everything that reaches the frontend as an error passes through it.
- `state.rs` — the recorder FSM (`Idle → Recording → Transcribing → Idle`); min 0.3 s / max 10 min, Esc cancels.
- `settings.rs` — JSON in `~/Library/Application Support/com.audioservice.helper/settings.json` (macOS) or `%APPDATA%\com.audioservice.helper\settings.json` (Windows), written atomically through `create_owner_only`: mode `0600` is applied only under `#[cfg(unix)]` — Windows has no POSIX modes and the profile folder itself provides privacy (the permissions test is gated by the same `cfg`).
- `update.rs` — auto-updating through `tauri-plugin-updater`: `check()` (the `latest.json` manifest from the public `screenfriskofficial/harpyhare-releases` repo, endpoint/pubkey in `tauri.conf.json`; `ITECH_UPDATE_ENDPOINT` overrides the endpoint for tests), `install()` (downloading the signed `.app.tar.gz`, minisign verification, replacing the bundle, `app.restart()`; a 300 ms pause before the restart so the webview can finish painting "Restarting…", since restart kills the process immediately), a background auto-check (at start and every 6 h; in debug only when `ITECH_UPDATE_ENDPOINT` is set). An `update-available` from the auto-check may arrive during an installation in progress — the frontend (`useUpdater`) does not let it override the downloading/restarting statuses. The `Update` that was found lives in `App.pending_update` between check and install; a repeat install is blocked by `App.update_installing`. Progress is throttled by `progress_step` (on each whole percent change) — the same idea as the `llm-delta` coalescing. An install error is delivered by rejecting the command (there is no separate event); `Settings.skipped_version` silences only the automatic badge, not a manual check. The release pipeline is `scripts/release.mjs` (signing key `~/.tauri/itech.key`, **back it up**; see README "Releasing"); it is **two-platform**: by default the platform is taken from `process.platform`/`process.arch` and its artifacts are built, and if a release with that tag already exists the version is NOT bumped and no tag is created — the script adds its own assets and merges its entry into the existing `latest.json` (keys `darwin-aarch64` / `windows-x86_64`; `notes`/`pub_date` and the other platforms are taken from the downloaded manifest, otherwise the second build would overwrite the first; on Windows the updater artifact and the installer are ONE file, the `-setup.exe` itself: `download_and_install` picks `WindowsUpdaterType::nsis` from the `exe` extension, and a separate `.nsis.zip` is not needed). A Windows bundle physically cannot be built on macOS, but **a Windows machine is not required for a release**: `--windows-setup path/to/setup.exe` takes the `-setup.exe` built by the CI job on the windows runner, signs it locally (`npx tauri signer sign` with the same key — the updater signature is minisign over the file's bytes and the build machine is irrelevant to it) and uploads it together with the merged manifest; the build is skipped in this mode, and `resolveTarget` returns a Windows host with `x64` arch regardless of `process.platform`. The mode works **only as an addition** (if there is no release with that tag you get a clear error), and the name of the file you pass must contain `_<version>_`: otherwise an installer for a different version gets signed with your key and ships to users as an update. **`shell: true` is enabled only for the node CLIs** (`runNodeCli` around `npm`/`npx`, with the flag set by `process.platform === "win32"`): on Windows `npm` is `npm.cmd`, `CreateProcess` only appends `.exe` to the name and does not find it, and Node refuses to launch `.cmd`/`.bat` without a shell (the CVE-2024-27980 fix) — because of which `execFileSync` failed with ENOENT and the script never once worked on a Windows host. The shell must NOT be extended to the general `run`: `gh release create --notes` receives multi-line text with quotes, and running it through `cmd.exe` would tear it apart. **A platform missing from `latest.json` is not "no updates" but an error on every check:** in `tauri-plugin-updater` 2.10.1, `Updater::check()` calls `get_urls(&release, &installer)?` BEFORE the `if should_update` branch, and that walks the keys `{os}-{arch}-{installer}` and `{os}-{arch}` (`windows-x86_64-nsis`, then `windows-x86_64`) and returns `Err(TargetsNotFound)` when neither exists — meaning `check()` rejects regardless of the user's version. That is exactly how the bug lived: the manifests for v0.9.0…v0.10.3 never had a `windows-x86_64` key (the installer was uploaded to the release by hand, bypassing the script), and updates never arrived on Windows. There is exactly one way to see this on Windows: a release build runs with `windows_subsystem = "windows"` (`main.rs`), so there is no console and the auto-check's `eprintln!` is visible nowhere, which makes **the line on the launcher's "Updates" screen the only diagnostic channel, and it must print the error text** (`CheckState = "idle" | "checking" | "latest" | {failure}` in `UpdatesScreen`, `catch((e: unknown) => …String(e))` in `LauncherPanel` — the idiom from `useUpdater.install`): a faceless "Could not check for updates" with no reason hid the missing platform among any other failure.
- `hotkey.rs` — push-to-talk registration + the global toggle hotkey for hiding/showing the window (`register_toggle` → `on_toggle_visibility`) + the global teleprompter hotkey (`register_teleprompter` → `on_toggle_teleprompter`: it emits `toggle-teleprompter` and the frontend switches the overlay — this works even when the HUD is not focused, because the always-on-top window is visible) + the global hotkey that focuses the input field (`register_focus_prompt` → `window::show_and_focus_prompt`, with no wrapper function of its own: that one already has the required `fn(&AppHandle)` signature) + the global auto mode hotkey (`register_auto_mode` → `auto::on_toggle`); `parse_hotkey` is the only unit-tested function here. The handlers are deferred (`defer`) — an invariant of the plugin's registry. All six global hotkeys (PTT, hide/show, teleprompter, region screenshot, focus field, auto mode) are registered from the `GLOBAL_HOTKEYS` table in `window::register_main_window_hotkeys` (on `launch_main_window`), removed in `stop_main_window` and re-registered in `set_settings` when they change.

#### Auto mode (`auto.rs`) — two sources, labelled turns

**Why.** PTT hears only the system output, i.e. the other party; the user's own speech never reached the app at all, and the model could only guess which part was the question and which the answer (today that "knowledge" is baked in as prose in the presets in `config/presets.json`: "I am the interviewer, you answer as the candidate"). Auto mode turns the guess into markup: two independent sources → two labels → ordered turns.

- **Separating the speakers is done by SOURCE, not by diarisation.** Groq Whisper (`whisper-large-v3-turbo`) has no speaker labels, and the audio is downmixed to mono before upload anyway (`audio::downmix_into`, `MONO_CHANNELS = 1`) — separating by channel is physically impossible. So `Speaker::Interviewer` = the system output (tap/loopback), `Speaker::User` = the microphone, and these are exactly two different `AudioCapture`s.
- **`SystemAudioCapture` has been renamed to `AudioCapture` and takes a `SourceKind` (`Output`/`Input`).** The portable core (the ring, the consumer, `Session`, `RollingBuffer`) never depended on the source; the backends gained a branch: macOS uses `ca::System::default_input_device()` plus the same `create_io_proc_id`/`device_start` with no tap and no aggregate (`Source`/`Running` became enums, and **the field order inside a variant is still drop order**); Windows uses `eCapture` instead of `eRender` and `Initialize(..., 0, ...)` instead of `AUDCLNT_STREAMFLAGS_LOOPBACK`.
- **`Timeline` (synthesising silence by wall clock) is DISABLED for the microphone** (`Option<Timeline>`, `None` for `Input`). It exists only because loopback emits no packets while nothing renders to the device; a real capture endpoint always delivers packets, and zero-filling would double-count samples.
- **`AudioCapture` now shuts its consumer thread down in `Drop`** (`Shared.shutdown` + `notify_all`, with checks in `wait_for_work` and `run_buffering`). Before this, a dropped capture left a thread running forever: on a device rebuild that was one leak per session and went unnoticed, but the auto mode toggle drops the microphone capture every time it is switched off.
- **Segmentation is pure logic in `audio.rs`** (`SpeechSegmenter`, a 10 ms frame, gating on `SILENCE_RMS_THRESHOLD`, a 200 ms lead-in before the attack, a 120 ms tail, minimum and maximum lengths from the settings). It is covered by unit tests; the code around it (`capture.rs`, `recording.rs`, `auto.rs`) has no test coverage at all, which is why everything that can be extracted into a pure function has been.
- **Segments are taken in the already existing `run_buffering` loop** — there is no new thread. A consequence: auto mode forces `set_buffering(true)` on both sources and restores `settings.buffer_enabled` on the system source when it stops; `apply_buffer_settings_change` has no right to switch buffering off while auto mode is alive (otherwise segmentation would die silently).
- **Lock order: `segmenting` is taken AFTER `session` and `rolling` have been released.** The `SegmentSink` callback is invoked while holding the `segmenting` lock, and that is acceptable precisely because it never touches `Shared`: it bumps counters in `AutoState` and spawns a task.
- **Auto mode and PTT are mutually exclusive.** With auto mode active, `on_ptt_pressed` returns an `stt-error` with a clear message, and `auto::start` refuses to start unless the recorder is `Idle`. Otherwise the same system audio would go into two transcriptions — exactly the "duplicate" the feature is supposed to avoid.
- **The `App.stt_stream` singleton deliberately remains a single slot**: there is exactly one streaming transcription (PTT), and the mutual exclusion above guarantees it. Auto mode does not use streaming — a segment is complete when it is finalised, so it takes the classic `transcribe(&samples)`, one independent task per segment.
- **Cancellation is by generation, not by token.** `SttEngine::transcribe` takes no cancellation token, so `AutoState.generation` is incremented on every start and stop and a result from a foreign generation is discarded. On top of that there is a ceiling of `MAX_IN_FLIGHT_PER_SPEAKER = 2` per speaker: a third segment is dropped with a line in stderr, otherwise a slow network would pile up requests without bound.
- **Turn order follows `seq`, not arrival time.** `seq` is issued synchronously at the moment a segment is finalised (before the `spawn`), and `at_ms` is the wall clock taken at the same point. Transcriptions come back out of order, and the frontend inserts them by `seq` (`lib/auto-turns.insertTurn`). The audio itself has no timestamps: `io_proc` ignores `_now`/`_input_time`, and the tap and the microphone are clocked by different clocks — matching them up by time would be a lie.
- **What goes to the network is decided by `lib/auto-turns.planSubmission`** (a pure function, covered by tests): a submission happens only when the newest unsent turn belongs to the interviewer; the user's turns ride along with it as context but never start a request on their own. Labels appear only in a mixed window: a plain interviewer question goes out unlabelled (the way a transcript always did), while a window containing the user's answer goes out as "Интервьюер: …" / "Я: …" lines. Anthropic messages carry only `user`/`assistant`, so the labels are rendered into the text rather than into a field.
- **Duplicates are cut off by three layers:** `insertTurn` ignores a repeated `seq`; `submittedThroughSeq` grows monotonically and moves ONLY when a submission is accepted; and a 900 ms debounce glues a question split across segments into a single submission. `dispatchAutoTurn` returns `false` when the chat is busy streaming — the turn is then not counted as sent and ships with the next window instead of being lost.
- **`dispatchAutoTurn` never touches the draft** (`useChats.appendAutoTurnMessage` → `appendUserTurn(..., keepDraft)`): auto mode's text never appeared in the input field, so it has nothing there to erase.
- **`auto_mode_enabled` is the "start auto mode when the HUD launches" setting, not a mirror of the live state.** The live state is queried with the `auto_mode_active` command and arrives through the `auto-mode-changed` event; the header toggle and the hotkey do not persist it. Otherwise every press would write `settings.json`.
- **The microphone is a separate permission.** macOS: `NSMicrophoneUsageDescription` in `src-tauri/Info.plist` (without it the system denies silently, just as with `NSAudioCaptureUsageDescription`), `PermissionKind::Microphone`, and its own `Privacy_Microphone` pane. On Windows `AUDIO_PRIVACY_PANE_URL` used to point at `ms-settings:privacy-microphone` — wrong for loopback; now audio leads to `ms-settings:sound` and the microphone leads to the privacy pane. The permission is **optional**: `allOk`/`needsAttention` ignore it, and the launcher starts without a microphone.
- **Cost and limits.** Continuously recognising both sides means one Groq request per turn, and the bill grows linearly with the length of the conversation. And: **with speakers instead of headphones the microphone hears the other party**, so the same sentence arrives twice under different labels; there is no echo cancellation in the stack. Both limitations are accepted knowingly and are not closed by code.

#### capture.rs — invariants

The producer (the Core Audio RT callback on macOS, the WASAPI capture thread on Windows) writes into a lock-free ring buffer (`ringbuf`, no mutexes and no allocations); the consumer thread downmixes and resamples to 16 kHz on the fly, accumulates a buffer and hands chunks to an optional `ChunkSink` (dropping it is EOF for the stream). `stop()` returns the finished 16 kHz mono. The signature is `AudioCapture::new(kind, uid, buffer_secs)`.

**All the portable machinery lives in `capture.rs`** (the ring, the consumer thread, `Session`/`Shared`/`Scratch`, PTT sessions, `run_buffering`, `RollingBuffer`, `AudioDeviceInfo`, the public methods of `AudioCapture`), and a backend must provide exactly four things. **The two-phase `open`/`start` contract is not an accident**: `open(kind, uid) -> (Source, StreamSpec)` opens the source and reports the format FIRST (`sample_rate`, `channels`) — the ring's size and the fields of `Shared` depend on it, so they cannot be created before `open`; `start(source, ctx: Box<CallbackCtx>) -> Running` only starts the flow of samples, and `Running` silences the capture in `Drop`; plus `list_devices(kind)` and `watch_default_output_device(handler)`. **Samples reach the ring only through `CallbackCtx::wants_samples()`/`push_samples()`** — the `recording || buffering` gate and the `produced`/`dropped` accounting live in the shared code: `recording_secs()` (the minimum recording length and the 10-minute watchdog) rides on `produced`, while `dropped` is visible only as a `[perf]` line in stderr, so a backend that writes into the ring bypassing these methods breaks the duration accounting silently. The error variant is `CaptureError::Backend(String)` with the platform in the text ("Core Audio: …" / "WASAPI: …"); there is no separate `CoreAudio` variant any more.

- **The stop order is mandatory:** `recording=false` first, then draining the ring's tail. The `recording` flag is controlled only by the consumer (the `Session` protocol + `stop_requested` rules out the "stop before the consumer wakes up" race).
- **The field order in `Running` in `capture/macos.rs` is drop order** (`_started` → `_tap` → `_ctx`; the C callback holds a reference to `_ctx`): reordering it means use-after-free on the Core Audio IO thread. `unsafe impl Send` (also in the backend rather than on the facade) switches off the compiler's check — review it by hand whenever fields are added; access it only under a Mutex.
- **The Windows backend (`capture/windows.rs`) is WASAPI loopback on the OUTPUT device** (`IAudioClient` + `AUDCLNT_STREAMFLAGS_LOOPBACK`, shared mode, mix format). **COM is initialised in MTA, but `RPC_E_CHANGED_MODE` is a success, not an error**: tao/wry have already raised an STA on the main thread, and `CoInitializeEx(MULTITHREADED)` from there returns exactly that code; treating it as a refusal means never bringing capture up at all (every entry point — `list_devices`, `open`, `set_settings` — is a synchronous main-thread command). In that case `CoUninitialize` must not be called — the apartment is not ours. COM pointers do not travel across thread boundaries: `open` resolves the device and returns **its concrete id**, and the client is activated afresh in the capture thread — otherwise a default change between `open` and `start` would produce a spurious "the format changed". The start reports success or failure synchronously through a channel — without that, `AudioCapture::new` would return Ok on a dead thread and give "Silence" instead of an access error. The loop is **polling**, with the interval derived from `GetDevicePeriod`: event mode is not signalled for loopback when no sound is playing, so capture would stall there until the first sound. Packets flagged `AUDCLNT_BUFFERFLAGS_SILENT` are padded with zeros, otherwise the timeline tears and what was recorded shifts. **Silence has to be synthesised by us**: loopback emits no packets at all while nothing renders to the device, and `recording_secs()` counts time by the number of samples — without padding with zeros by wall clock (`Timeline` in the backend), holding PTT for five seconds in silence would give "the recording is too short" and the 10-minute watchdog would never fire. **The capture thread reopens the stream itself**: `AUDCLNT_E_DEVICE_INVALIDATED` (a headset unplugged, a device sample rate changed) does not kill the thread silently — it retries once per second, otherwise `App.capture` would stay `Some` with a dead thread and PTT would run empty without a single signal. The inner drain loop checks the stop flag: `Running::drop` joins the thread **while holding the `App.capture` lock**, and an endless drain would freeze everyone waiting for the capture. The format is checked for decodability (float32 / int16 / int32) at open time — a clear error beats silent silence. `E_ACCESSDENIED` → `CaptureError::PermissionDenied`.
- **A TCC refusal is indistinguishable by error code (macOS):** Core Audio returns `kAudioHardwareIllegalOperationError` ('!hog'), and that is exactly what maps to `PermissionDenied` — there is no "more precise" code. On refusal, `None` is placed in the state and the UI sees it through `permissions_status`. "Grant" calls `request_permission("audio")` (recreating the tap, which triggers the TCC prompt when the status is "not asked"), and "Settings" calls `open_permission_settings("audio")`. `NSAudioCaptureUsageDescription` lives in `src-tauri/Info.plist` and is embedded in the dev binary too — without it macOS does not ask, it silently refuses.
- **The main sub-device of the private aggregate is the output device as the clock source** (macOS; `Settings.capture_device_uid`, `""` = the system default through `resolve_device`; a nonexistent uid silently falls back to the default — the same fallback policy on Windows). Removing `sub_device_list` "as unnecessary" is not allowed.
- **Capture is bound to the device as of creation time** — the output changes and on macOS the tap returns zeros ("Silence"), while on Windows the loopback stays hanging on the old endpoint. `capture::watch_default_output_device` watches for this (on macOS a listener on the `kAudioHardwarePropertyDefaultOutputDevice` property, on Windows a separate thread comparing the default endpoint's id every two seconds — polling was chosen over the `IMMNotificationClient` COM callback deliberately: it requires no COM interface implementation and adds no unsafe surface, and a two-second delay on a device change is imperceptible), but **the policy stays in `recording.rs` and does not move into the backends**: the callback is deferred into the async runtime and recreates the capture on a default change only when uid="", on a `capture_device_uid` change in `set_settings`, and — if the recorder is busy — lazily on the next PTT through the `capture_rebuild_pending` flag.
- **Continuous buffering mode:** `set_buffering(true)` switches the consumer into the `run_buffering` loop with a long-lived resampler (the producer passes samples through by `wants_samples()`, i.e. `recording || buffering`), and every 16 kHz chunk goes into `audio::RollingBuffer` under a mutex. A PTT session with the buffer on is served by the same loop: `take_pending_session` flushes a snapshot of the buffer into the accumulator and into the `ChunkSink` BEFORE the live chunks (the pre-roll), the rolling lock is taken only after the session lock is released (**the session and rolling locks are never held at the same time**), and the resampler's `finish()` is not called (losing ~20 ms of speech tail on release is accepted knowingly). A buffered session also maintains the `recording` flag (`take_pending_session` sets it, observing the stop and finalising clear it) — the producer's gate stays correct when the toggle is switched off mid-recording, and leaving buffering mode clears the rolling buffer on the consumer's side.
- The device list for the UI is `list_audio_output_devices` / `list_audio_input_devices` (`capture::list_devices`: on macOS filtered by the presence of an output/input ASBD, on Windows the active render/capture endpoints with `PKEY_Device_FriendlyName`). Manual acceptance testing is `examples/record5s.rs`; a live streaming smoke test against Groq is `examples/stream_smoke.rs`.

## Non-obvious invariants (do not break these)

### Chats and the context library

**Chats are independent and parallel.** The source of truth is the frontend (`useChats`: `Chat[]` + `activeId`); Rust stores chats as an opaque JSON string in `chats.json` (atomically, `0600`, the `chats.rs` module, the `load_chats`/`save_chats` commands). `send_to_claude(messages, chat_id, system, model, options)` sends the chat's whole history; cancellation is per chat through `Mutex<HashMap<chat_id, CancellationToken>>`. **Sent images are visible in the message bubble** — `MessageImages` inside `UserBubble` (`AnswerPanel`), sourced from `ChatMessage.images`, with the data URL assembled by `composer.imageDataUrl`. For a long time only the composer drew them (the attachment chip) while the bubble took a single `text`: the image went out with the request and the answer made sense, but the history had no trace of it — which looked like "the model sees something that is not on screen". What travels into `chats.json`, though, is not the image's bytes but a `{id, media_type}` reference (`serializeChats`) — the bytes themselves live in a separate file in `images/`, see below; the chat's textual `context` is saved; `libraryDocIds` is saved, and old chats without the field get `[]`. The limit is `CHAT_LIMIT = 6`. **Duplicating a chat copies the parameters but NOT the contents** (`createChatFrom` in `lib/chats.ts` → `useChats.duplicateChat`; the `CopyPlus` button in `ChatTabs` sits right after "+", greys out at the limit together with it, and always duplicates the ACTIVE chat): the preset, model, thinking, web search, `context` and `libraryDocIds` come across (the last one as a copy of the array — two chats must not share one reference), while the history, the draft with its attachments, the indexed title and `lastInputTokens` stay at a new chat's defaults — "duplicate" here means "the same settings, a clean conversation", not a clone of the correspondence. Switching to the new chat happens **inside the `setChats` updater** (the same technique as in `removeChat`) rather than next to it as in `newChat`: otherwise, on a no-op — hitting `CHAT_LIMIT` or failing to find `sourceId` — `activeId` would move to a chat that was never created, and then no tab is highlighted, the composer edits `chats[0]` through the `active` fallback, and the phantom id even settles into `localStorage`. From the keyboard the same thing is done by the registry action `duplicate_chat` (default ⌘⇧N / Ctrl+Shift+N) through its own `useDuplicateChatKey` hook, and **it is gated on `!promptCoveredByOverlay`** for the same reason quick actions are: duplication has no natural safety catch such as an empty draft, and under the teleprompter or the connectivity overlay the hotkey would silently switch the active chat blind. The handler is deliberately NOT built into `useWindowControls` — that one is responsible for the window and sending, and chat management is not its area.

**Image bytes live not in `chats.json` but in the `images/` folder beside it.** While they were simply being stripped, more than the bubble's image was broken: the history goes to the API in full on every turn (`historyWithNewUserMessage`, `useProjectedContextTokens`, `resendFromMessage`), so after a restart the model stopped seeing the screenshot it was being asked about, and `count_tokens` counted wrong. What goes into the chat file now is a `{id, media_type}` reference — for messages and for unsent `draftAttachments` alike, so a draft with an attachment survives a restart just as the history does; **the id is assigned once, in `fileToAttachment`** — the shared entry point for pasting, dropping and screenshots, rather than at send time, which is why drafts came for free and needed no separate code. The Rust side is `chat_images.rs` (pure functions over a path, following the `chats.rs` pattern; the commands live in `storage.rs`: `save_chat_image`/`load_chat_images`/`prune_chat_images`, all through `spawn_blocking`), the path is `app_state::chat_images_dir`, and writing goes through the same `settings::write_atomic_owner_only_bytes` (tmp + rename, `0600` on unix) as every other file: **all disk writing goes through one function**, so do not introduce your own `fs::write`. **The temporary file's name is unique per call** (`unique_tmp_path`: pid + an atomic counter, `create_new` instead of `create+truncate`), and this is not over-caution: the shared `path.with_extension("tmp")` broke on exactly this content-addressable store — two parallel `save`s of the same bytes (a screenshot on top of an in-flight drop of the same image) aimed at ONE tmp, the first `rename` carried it away, the second got `ENOENT`, `save` returned an error, `storedId` swallowed it, and an attachment with `NOT_PERSISTED_IMAGE_ID` silently failed to survive a restart even though the bytes were already on disk under that very id. A unique name fixes it at the root: both writes get through and `rename` overwrites the target normally. On a write or rename error the tmp is cleaned up right there — otherwise unique names would pile up instead of one file being overwritten. **`create_new` is not redundant with a unique name and must not be "simplified" to `create+truncate`:** it catches any future breakage of the name generator with a loud error instead of a silent race between two writers into one file. It cannot jam on a leftover from a killed process (that would require both the pid AND the counter value to coincide): the same cleanup deletes a foreign tmp right in the error branch, so at most one write can fail and the next one takes a different name. Locked down by `parallel_saves_of_one_image_share_the_id_and_the_file` and `parallel_atomic_writes_to_one_path_all_succeed`. **The image size is capped by `IMAGE_MAX_BYTES` = 20 MB** — the same ceiling and the same error text (`context_import::too_large_message`) as the PDF import: the frontend already downscales anything over 5 MB (`MAX_IMAGE_BYTES`), so the limit is unreachable for an honest attachment and sits where the other storage checks are — in `chat_images::save` rather than in the command, so it cannot be bypassed. **An image's id is a hash of its contents plus an extension** (`0f3a…9c.png`): the same screenshot attached twice or in two chats lies on disk as a single copy, and a repeat `save` simply returns the previous id without rewriting the file. The hasher is `DefaultHasher`, and its instability across Rust versions is safe precisely because **the id is computed ONLY on write** and afterwards lives in `chats.json` as a file name; start recomputing it on read and the whole history would lose its images after a toolchain update. **A hash collision is an accepted price:** on a name match `save` returns the existing id without comparing the bytes, so a theoretical collision would show an old image in a new message; but the hash is 64-bit and `<[u8]>::hash` also writes the slice's length, so both the length and the hash would have to match — on the order of 10⁻¹² across thousands of images, whereas comparing bytes on every hit would mean reading a file for every attachment for the sake of an event that will not happen. **`is_valid_id` is path traversal protection, not cosmetics:** the id comes from `chats.json`, i.e. from a file the user edits by hand, and without the check an id of `../../settings.json` would read anything at all; the format is strict — 16 lowercase hex characters, a dot, one of four known extensions — and `prune` deletes only names that pass this check, plus the `*.tmp` leftovers of interrupted writes (a foreign file such as `chats.json` that ended up in the folder is left alone). **`.tmp` was added to the cleanup for a reason:** `write_atomic_owner_only_bytes` puts its temporary file IN THE SAME folder, `is_valid_id` does not pass it, and without a separate branch a process killed mid-write would leave rubbish in `images/` that NOBODY deletes — precisely what the cleanup exists for. **The set of supported media types is duplicated and must match:** `SUPPORTED_IMAGE_TYPES` in `lib/composer.ts` (plus `DOWNSCALE_MEDIA_TYPE` in `useChats`) and `extension_for` in `chat_images.rs`. Extend the list on the frontend only and you get an image that works for the whole session and silently fails to survive a restart: `save_chat_image` returns an error, the attachment gets `NOT_PERSISTED_IMAGE_ID` (an empty string), and `serializeChats` filters such references out. That same degradation is the standard reaction to any storage failure: a broken write costs the image in the history but does not derail the send. `ChatMessage.images` is `ChatImage[]` (`ImagePayload` + `id`), while the bare `ImagePayload` remains what travels to Anthropic: `App.requestImages` strips the `id` before sending, **the DTO on the wire has not changed**, and `id` must not be added to it.

**Loading chats is a two-step process, and the second step must complete BEFORE `setChats`** (`loadStoredChats` in `useChats.ts`): chats → ONE `load_chat_images` request with all the ids at once (`chatImageIds`) → `hydrateChatImages` puts the bytes back → `setChats`. Requesting one image at a time, or hydrating after the first render, is not allowed — the history would flash with empty frames. Hydration lives as a pure function in `lib/chats.ts` rather than inside `deserializeChats`: deserialisation has no right to reach into IPC. `load_chat_images` silently skips both invalid ids and missing files, and `hydrateChatImages` drops an image with no bytes — a lost file costs the image in the message, while the text and the chat itself remain. **The `prune_chat_images` cleanup is called exactly once, at start, right after loading.** Cleaning on every save is not allowed: the 500 ms debounce keeps the state half a second in the past, and the cleanup would delete the file of an attachment that had just been added. The accepted remainder is a window of a few milliseconds between loading handing over the list of ids and `prune` running: an attachment added exactly within it stays in the session but disappears from disk (the window opens before the HUD's first frame, so hitting it is practically impossible). **A price we pay knowingly:** the `images/` folder grows for as long as the images are alive in the chats; it is bounded by `CHAT_LIMIT` and by that same cleanup at start — anything no chat references is deleted on the next launch. Old `chats.json` files without references load as they are, and there is nothing to migrate: those images are already lost.

**Debounced saving to disk (500 ms) starts only after the initial load has finished** (the `loaded` flag in `useChats`) — otherwise the empty startup state would overwrite the saved chats. The same invariant applies in `useContextLibrary`.

**The active chat survives a restart and lives in `localStorage` (`active-chat-id`), not in `chats.json` and not in `Settings`** — both "obvious" places were rejected for concrete reasons. `chats.json` will not do: its root is a bare array, and to add `activeId` you would have to wrap it in an object; an older version of the app would read such a file as "no chats" (`!Array.isArray` → `null`) and wipe them on its very first save — data loss on a rollback. `Settings` will not do: chats and settings are loaded by independent asynchronous requests, and in the "settings arrived after the chats" case you would have to switch the chat retroactively under a user who has already clicked. `localStorage` is already used in the project (the redeem idempotency keys), survives the HUD being recreated and touches no contract. The remembered id is checked for existence among the loaded chats (`rememberedActiveId`) — a deleted chat falls back to the first one instead of leaving an empty screen.

**The context library** is a separate `context-library.json` file following the same pattern as chats.json: Rust stores opaque JSON through `chats::load/save`, with the `load_context_library`/`save_context_library` commands; the model and the (de)serialisation are in `lib/context-library.ts`, broken `folderId`s are repaired to the root, and texts are clamped by `DOC_TEXT_LIMIT_CHARS`. The UI is the launcher's "Contexts" screen (`ContextLibraryPanel`, where edits apply immediately through their own commands, bypassing the launcher's draft/autosave); selecting materials for a chat is the Composer's "Context" dialog (checkboxes + your own text).

**File import** — the picker (`input type=file`) and drag-and-drop from the OS file manager (labelled "from Finder" / "from Explorer" by platform):

- HTML5 drop of OS files does NOT work in Tauri (the webview intercepts it) — `getCurrentWebview().onDragDropEvent` is used instead (wrapped by `ipc/events.onFileDrop`, converting physical pixels to CSS through devicePixelRatio), and the target folder is found with `elementFromPoint` by the `data-drop-folder` attribute.
- The types are **.md/.markdown/.txt and .pdf** (`context_import.rs` dispatches by extension): text is read with `read_to_string` (1 MB limit), and PDF goes through `pdf-extract::extract_text_from_mem` inside `catch_unwind` (a corrupt PDF must not bring the process down; 20 MB limit), then `normalize_extracted_text` (CR/form-feed → `\n`, collapsing blank lines, trim). An empty result means a scan with no text layer → the `ERR_PDF_NO_TEXT` error (there is no OCR). The extracted text is clamped by `DOC_TEXT_LIMIT_CHARS` regardless.
- Paths: a drop yields a real path → `read_context_import_file(path)`; the picker has no real path in either WKWebView or WebView2 (`File.text()` for text; for PDF, `File.arrayBuffer()` → `lib/base64.arrayBufferToBase64` → `read_context_pdf_bytes(dataBase64)`). Both commands parse inside `tokio::spawn_blocking` (parsing 20 MB must not block the runtime).
- Moving materials between folders is a custom pointer drag (`useDocDrag`: mousedown + a 5px threshold → mousemove → `moveDoc` by the `data-drop-folder` under the cursor), NOT HTML5 draggable — in-page HTML5 dnd is unreliable in a Tauri webview.
- **PTT must keep working while the prompt field has focus.** `usePttSuspend` silences PTT on focus in text fields ONLY for hotkeys that conflict with typing (`conflictsWithTyping`: a single letter/digit, including with Shift). F-keys and combinations with Cmd/Ctrl/Alt are never silenced — do not bring back the unconditional gag. **The subscription must look at the current `document.activeElement`, not only at future `focusin`/`focusout` events.** With the field auto-focused (`usePromptFocus`), a formerly rare race became deterministic: on mount the settings are still the defaults (PTT = `Cmd+R`, `conflictsWithTyping` is false, the effect bails early), the field is already focused, and once the settings load from disk with the user's PTT on a single letter, the listeners get attached AFTER `focusin`, there is no suspension, and the letter starts a recording instead of typing. The check on subscription is deliberately one-sided: we silence only if the field is already focused, and `setPttSuspended(false)` is NOT called there — that command re-registers the global PTT (`preferences::set_ptt_suspended` → `register_ptt`), so every recreation of the effect would cause a redundant re-registration.
- **Hotkey handlers must defer all work.** `tauri-plugin-global-shortcut` invokes the handler while holding its registry mutex; doing register/unregister synchronously inside (e.g. registering Esc) is a re-entrant deadlock that hard-freezes the app. `hotkey.rs` wraps handlers in `defer()` (spawns onto the async runtime). The same applies to anything a handler triggers.

### Window control goes through Rust commands, not through JS

`set_window_size`, `close_app`, `hide_main_window`, the window's position and visibility are Rust commands and hotkey handlers (the native arrow monitor calls `set_position` directly). A JS path such as `getCurrentWindow().setSize()` **silently does nothing without the matching permission** in `src-tauri/capabilities/default.json`, so by default prefer a Rust command; if you genuinely need the capability from JS, add the permission there first. Exactly one setter has been granted explicitly, `core:window:allow-start-dragging` for `startWindowDrag` — that is the only direct call to a Tauri window API from the frontend. **We do not keep setter permissions "just in case"**: `set-position`/`show`/`hide` had been granted explicitly but were never once called from JS, and have been removed. The getters (`scale-factor`, `outer-position`, `inner-size`/`outer-size`, `current-monitor`) are part of `core:window:default`, which is already inside `core:default`, so there is no need to list them separately — `onWindowResized` with its `scaleFactor()` works even though `allow-scale-factor` never appeared in the capability (and `allow-outer-position` was simply redundant there and was removed too). Check the set's contents against the generated `src-tauri/gen/schemas/acl-manifests.json`, not by eye. The windows are listed by name (`"windows": ["main", "launcher"]`) — a window forgotten in that list will not even get `core:default`, and any `invoke` from it will be rejected.

**"Raise the HUD and put the caret in the field" is one function, `window::show_and_focus_prompt`** (`show()` + `set_focus()` + emitting `focus-prompt`; the emit sits inside `if let Some(w)` — with no `main` window there is nobody to focus). All three returns into input call it: `screenshot::run_capture` (always on a successful shot; on cancel and on error only if we were the ones who hid the HUD, see "Region screenshot"), the show branch of `on_toggle_visibility` (which no longer keeps its own `show()`+`set_focus()`), and the handler of the global `focus_prompt` hotkey. Its mirror image, `window::hide_main`, is likewise shared: the `hide_main_window` command, the hide branch of `on_toggle_visibility` and the hiding before a screenshot (`hide_for_screen_capture`) all go through one body — do not grow your own `w.hide()` next to them. The fourth case, launching the HUD, is **deliberately not from here**: the window is created before the webview manages to subscribe to events, so the emit would go nowhere — at start the caret is placed by a mount effect on the frontend. **The fifth case, a finished transcript, emits the event BARE, bypassing `show_and_focus_prompt`** (`recording::deliver_transcript`, right after `transcript-ready`): the window is deliberately not raised, because PTT is designed to work while the user is in ANOTHER application, and yanking the HUD forward after every recording would break exactly the scenario the hotkey was made global for — the caret simply moves into the field, and the user decides whether to raise the window. The single point chosen is common to both transcription paths (streaming and the fallback over the accumulated buffer) and does not touch cancellation, silence or errors — those bypass `deliver_transcript`. The rejected alternative to an event was listening for `tauri://focus` on the frontend: focusing the field on ANY window activation means tearing the text selection in an answer and breaking button clicks when returning with the mouse, and the main case ("the window is already active, the hotkey was pressed") is not covered by it at all; handling the hotkey on the frontend is impossible too — a global shortcut is registered only in Rust, and a keydown never reaches the webview while the window is unfocused.

**We measure and apply THE SAME size — the inner one.** `set_window_size` takes the current size through `inner_size()`, because it applies it with `set_size`, and that sets precisely the inner size; the `onWindowResized` events on the frontend also carry the inner one. Take `outer_size()` here and nothing shows on macOS (a frameless window has no border, so outer equals inner), while on Windows a resizable window keeps its `WS_THICKFRAME` border — a difference of a few pixels, the epsilon early-out NEVER fires, and every settings change starts a tween that fights with a manual mouse resize and produces a ragged animation.

**The resize tween** (`set_window_size`) animates width+height (ease-out) on a background thread, dispatching each frame through `run_on_main_thread`, with a `resize_gen` generation guard. The top edge Y is fixed (growth downwards), and the target `x` is the current one, merely clamped into the monitor's bounds (`anchored_target_x` → `window_geom::clamp_window_x`): the window grows to the right in place and shifts left only once it hits the right edge (it will not run off the screen). There is deliberately NO centring — it was irritating during hotkey resizes and when opening the preview. The early-out is by a size epsilon; a call with the same size is a complete no-op. **The tween must abort if between frames the actual size has diverged from what the previous frame applied** (`tween_superseded`/`frame_still_ours`): otherwise it fights with a manual mouse resize — during a drag Windows runs its own drag-rect from the grab point, and each of our `SetWindowPos` calls is rolled back by the next `WM_MOUSEMOVE`, producing a jerk every 13 ms. The position is applied only when it actually differs from the target — an extra `SetWindowPos` per frame jolts the origin when dragging by the left or top edge.

**Left-button dragging uses an explicit `getCurrentWindow().startDragging()`** (`startWindowDrag` in `ipc/commands.ts`) and NOT `data-tauri-drag-region`: Tauri's attribute injection did not work in this frameless+transparent window.

- `useWindowDrag` attaches `onMouseDown` to the header (StatusBar); the root `.app-shell` in App.tsx also starts a drag, but only when clicked directly (`target === currentTarget` — the padding and the gap between columns; otherwise clicking on the chat's text would break selection).

- A drag starts only for the left button and only if `isDraggableChromeTarget` (the click is not on something interactive — the selector `button, a, input, textarea, select, [role='tab'], [data-no-drag]`), so buttons and tabs stay clickable, and a click on an icon inside a button (an SVG, not an HTMLElement) does not start a drag.
- The cursor over the drag zone stays an arrow (a global `cursor: default`) — deliberately.

**The HUD header:** the cheat-sheet footer is gone — the reference for every hotkey lives in the `HotkeysPopover` popover (the keyboard icon); the data comes from the single registry `lib/hotkeys.hotkeyGroups(cfg)` (configurable combos come from Settings; **when adding a hotkey, extend the registry, not the markup**). Chat tabs are the numbered squares of `ChatTabs` (they scroll horizontally in a narrow window; the × appears on hover only on the active tab — on inactive ones a click selects the chat; renaming chats has been removed, and the `title` field lives on in the data for chats.json compatibility; do NOT place the tabs on the left — a side rail broke the chat column's symmetry and was rejected). The window buttons are ghost `IconButton` icons at the edges of the header: `Minus` on the left → `hide_main_window` (you come back with the global toggle hotkey), `Square` in the right-hand cluster → "Stop", returning to the launcher. There is no separate close button in the HUD: the `close_app` command remains in the contract, but the frontend never calls it.
- **Modifier+arrows move the window through native key interception, not through the webview** (`platform::install_move_keys_monitor`: a local NSEvent monitor on macOS, a low-level `WH_KEYBOARD_LL` hook on Windows), which swallows the keyDown BEFORE the webview — otherwise the caret would jump around the text field and the window move would travel through IPC. **All the arrow logic is the shared `platform::handle_arrow_key(app, mask, dx, dy)`**: reading the settings, moving the window, emitting `resize-key`; all the backend has to do is intercept the event, translate the native flags into a `ModifierMask` and swallow the keyDown exactly when the function returned `true` (duplicating the settings parsing in a backend is not allowed — polarity and clamps would drift). The interception is installed once in `setup_app` and lives for the whole runtime, so recreating the HUD does not break it — but **it may swallow a keyDown only when it has actually handled it**: with no `main` window the event travels on, otherwise ⌘+←/→ in the launcher's text fields would be eaten instead of moving the caret along the line (the HUD may not have been created yet while the interception is already alive). This is a hot path: **with an empty modifier mask we bail out BEFORE taking the settings lock** — otherwise ordinary arrow navigation in the prompt field (with auto-repeat) locks the global `Settings` on every keyDown. **The Windows hook is global, unlike macOS's local monitor**, so it must compare `GetForegroundWindow()` against the HUD's hwnd: without that, the same arrows would be intercepted inside other applications; it is installed once, and the `AppHandle` for it lives in a `OnceLock`. `resize_modifier`+arrows change the window's **size**: the monitor swallows the keyDown and emits `resize-key {dim, dir}`; the frontend (`useWindowControls` → `useSettings.bumpWindowSize`) steps `Settings.window_width/height` by `resize_step` with the clamps from `lib/window-size.ts`, the window applies it through `useWindowFrameSync`, and persistence is debounced (as with opacity). Polarity: ←/↑ smaller, →/↓ larger.
- **The move and resize arrows belong entirely to the native monitor — there is no parallel JS branch for them and none must be created.** The monitor eats the keyDown of combinations that MATCH the setting, so only the ones the user did NOT choose reach the webview: a JS handler could only contradict that choice (moving the window on someone else's combination), and it was never a "fallback" — the hardcoded `metaKey || ctrlKey` (+Shift) was a bug turned inside out, and a configurable version of the same code would still be a bug. The branch's scaffolding went with it: the "key code → axis and sign" mapping on the frontend (the axis and sign are decided by Rust and sent ready-made in the `resize-key` payload) and the Rust window-move command — the monitor moves the window with `set_position` directly, there was nowhere left to call the command from, and it is no longer in `collect_commands!`. `useWindowControls(onSend, onOpacityStep, onResizeKey)` is now responsible only for opacity, sending on Cmd/Ctrl+Enter and subscribing to `resize-key`. The only remaining JS path for modifiers is chat scrolling (`useHotkeyScroll`: the monitor does not touch its combo and lets it through into the webview), and there the spec is parsed by `parseModifier` ONCE in an effect rather than on every keydown (otherwise every keystroke in the webview allocates an array for `split("+")`); the combos reach the hotkey registry as the `moveWindow`/`resizeWindow`/`scrollChat` fields in `HotkeyConfig`.
- **The modifier vocabulary has one source, `hotkeys::MODIFIER_COMBOS`** (moved out of `settings.rs`), and it is **paired by platform** (`{macos, windows}`): the pair travels into the bindings whole through `.constant()`, the `WindowSection` select takes its own half (`MODIFIER_COMBOS[PLATFORM]`, with no copy of the list on the frontend), and Rust goes through `.current()`. Both parsing implementations are covered by tests: `platform/tests.rs` (every combo in the registry yields a non-empty and unique `modifier_mask`, and the family defaults are in the registry) and `lib/hotkey-modifier.test.ts` (the same for `parseModifier`, run across both platforms plus a check that the Windows list has no combo with Win). The Win key on Windows cannot even be **captured** with the mouse: `hotkeyFromEvent` returns `null` when Meta is held — otherwise you would get a dead binding that `assignHotkey` has already taken away from its previous owner, while the system refuses `RegisterHotKey` with `MOD_WIN` (and the registration error is swallowed). The `ModifierMask::CMD` bit in the Windows backend nevertheless remains bound to `VK_LWIN`/`VK_RWIN` deliberately: a `settings.json` carried over from macOS contains combos with `Cmd`, and they must keep working rather than being silently ignored. When you add a combo, edit the array for the right platform in Rust and run `cargo test` to regenerate the bindings. `formatCombo` must fold a spec made only of modifiers, with no key at the end (`Cmd` → ⌘, `Cmd+Shift` → ⌘⇧): the regex that required a `+` after the token left labels like "⌘Shift"; on Windows there are no glyphs — the tokens are textual (`Ctrl/Shift/Alt/Win`) joined with `+`. **Opacity (`+`/`−`) is deliberately NOT made configurable in the UI** — the select offers the user exactly three modifiers (move, resize, scroll); the opacity combo lives as the `opacity` action in the `hotkeys.rs` registry, from which both the popover's label and the event check in `useWindowControls` read it identically (`effectiveCombo(hotkeys, "opacity")`), because the literal "⌘⇧ + −" in the label and `e.metaKey && e.shiftKey` in the handler had already lived apart and could drift.
- **The mouse pointer never hides and never changes shape.** While you type in a text field, WebKit asks the UI process to hide the pointer "until the mouse moves" through `+[NSCursor setHiddenUntilMouseMoves:]`; at start (`platform::disable_cursor_autohide_on_typing`, called from `setup_app`) that class method is swizzled into a no-op — a public objc-runtime API and a deterministic fix. Calling `setHiddenUntilMouseMoves(false)` after the fact does NOT work: the hiding arrives through asynchronous IPC and wins the race (such a compensation existed in the former window-move command and was removed as unnecessary once swizzling was in place). The pointer's shape is always the standard arrow: the global `cursor: default !important` in index.css deliberately suppresses I-beam/pointer/not-allowed in every case — do not remove it. WebView2 has no such auto-hiding, so `disable_cursor_autohide_on_typing` on Windows is a deliberate empty no-op, not a forgotten implementation.
- **`onEvent` uses a `live` flag** to pair subscribe/unsubscribe across the async `listen` promise — required for React StrictMode double-mount safety. `useClaudeStream` likewise cancels its pending rAF on unmount and gates late deltas after `stop`. A partial answer is NOT discarded on `stop`/`llm-error` — it goes into the history through `onComplete` (there is no duplicate: the `llm-done` of a cancelled stream is suppressed, and the chat has already been removed from `active`). The delta buffers and the set of active streams live in a ref rather than in state: the event handlers are subscribed once and must see the freshest values without re-subscribing — moving them into state/deps would break delta routing.
- **API keys: `.env` is a fallback only.** `lib.rs` setup reads `ANTHROPIC_API_KEY`/`GROQ_API_KEY` and applies them via `settings.apply_key_fallback` **only when** the corresponding settings.json field is empty (UI-saved keys win). `.env` is read from cwd and from `CARGO_MANIFEST_DIR/..` (so a Finder-launched `.app`, whose cwd is `/`, still finds the project `.env`). `.env` is gitignored. **The "no keys" gate lives in the launcher, not in the HUD** (`features/launcher/useLauncherReadiness`): `get_settings` returns settings with the `.env` fallback already applied, so an empty field on the frontend means the key is nowhere. `missingApiKeys(settings)` (`lib/api-keys`) + the audio recording permission (`usePermissions`) produce `ready` (computed once in the hook and passed to the panel as the `readiness` prop rather than recomputed by a formula on the spot); until it is `ready`, the HUD launch button is disabled. The HUD has no permissions banner at all — the launcher's gate will not let you into the HUD without audio access (see "Permissions"). That is why `Composer` **has no `disabled` prop**: there is no gate in the HUD, the flag arrived as a constant `false` and was threaded through a dozen and a half components (`ComposerToolbar` → `RequestParamsPopover` → the selects) — do not bring it back. The `disabled` prop on the thinking toggle did stay: `thinkingLocked` → `thinkingDisabled` → `ParamToggle`.
- **Access codes (proxy mode).** An alternative to your own keys: the user enters a one-time code, and the `redeem_access_code` command (`access.rs`) exchanges it for a bearer token from the proxy server (a Cloudflare Worker, repo `itech-relay`, design in `docs/superpowers/specs/2026-07-09-access-codes-proxy-design.md`) and puts it in `Settings.access_token`. **A non-empty `access_token` silences BOTH keys** — a single source of truth: `build_llm_client`/`build_stt_client` (`app_state.rs`) build the client in proxy mode (`llm::AnthropicClient::for_proxy` — `Auth::ProxyBearer`, the proxy's base_url, `Authorization: Bearer` instead of `x-api-key`; STT uses the same bearer with a different base_url, and the `stt.rs` code was not changed), `apply_key_fallback` does not substitute `.env`, and `missingApiKeys` returns `[]`. `rebuild_changed_api_clients` rebuilds BOTH clients when `access_token` changes. The order in `apply_access_token` is: network (redeem) → `save` to disk → rebuild → in-memory (a save error means a reject with the state untouched). The proxy URL is the `access::PROXY_BASE_URL` constant; the `ITECH_PROXY_ENDPOINT` env override is **`cfg!(debug_assertions)` only and `https://` only** (ignored in release — protection against redirecting the token or the content). Redeem idempotency uses a key from `crypto.randomUUID()` in `localStorage` (`redeem-idem:<normalised code>`), reused on a retry and cleared on success; `normalizeAccessCode` (`lib/access-code.ts`) must match the server's normalisation. In proxy mode `require_ok_status` surfaces the proxy's `error.message` body on 401/403 (a clear "the code is invalid"/"the limit is used up") instead of `BadApiKey`; the STT invariant "401→BadApiKey with no re-fallback" is preserved (the Groq path was not touched).
### The launcher autosaves the `draft` — there is no "Save" button

`LauncherPanel` keeps a local `draft: Settings`; any field change is debounced by `AUTOSAVE_DEBOUNCE_MS` (600 ms) and goes to `set_settings` through `useSettingsStore.save`. The debounce is not cosmetic: typing a key or code character by character collapses into a single client rebuild (`rebuild_changed_api_clients`).

- **Since there is no button, saving must be visible.** `LauncherApp` holds a `saving` flag around `persist`, and for that time the header prints "Saving…" instead of the blocker. Without it there was a visible lag: `useLauncherReadiness` computes blockers from the PERSISTED `settings`, not from the `draft`, so after pasting a key the status kept insisting "no keys" for the 600 ms of debounce plus a `set_settings` round trip — and the user read that as "the key was not accepted". A save error is shown as a banner in `LauncherPanel` under the header, and NOT as a line in the header itself: there it shared a row with the status and the search and was `truncate`d after the first few words, making the error text physically unreadable.
- `onSave` is called THROUGH a ref (`onSaveRef`), NOT from the effect's dependencies: `save` does `adopt(getSettings())` → a parent re-render → a new callback identity, and if the effect depended on `onSave`, every save would restart the effect and loop the autosave (`save → adopt → re-render → save`).
- The effect compares `draft` against the `lastQueuedDraft` ref **by identity** (which is how the first render and the StrictMode remount are skipped; each new change resets the timer through the cleanup).
- Only the copy being saved is normalised (`normalizeDraft`: empty hotkeys → the field of the same name in `DEFAULT_SETTINGS`, plus filtering out unfinished presets via `isPresetFilled` and unfinished quick actions via `isQuickActionFilled`) — the `draft` in the UI is NOT touched, otherwise an emptied hotkey field would be replaced by a fallback right in front of the user, and a half-filled preset or a half-typed quick action would vanish while being edited. **Do not introduce your own `FALLBACK_*` constants for these fallbacks**: the former `FALLBACK_PTT_HOTKEY` was `V` while the default of the day was `F9`, so clearing the PTT field produced a binding that never occurs in a clean install.
- While `launching`, the effect bails out early and the cleanup cancels the pending timer: "Launch" persists the normalised `draft` itself before `launch_main_window`, so there is no double save.
- Merging `settings.access_token` into the `draft` after a redeem returns THE SAME object when the token has not changed — an idle merge must not produce a new `draft` identity and a redundant autosave.
- The autosave relies on a Rust invariant: `reregister_changed_hotkeys` (`preferences.rs`) bails out early while there is no main window, so autosaving hotkeys from the launcher does NOT touch global registration — that happens once in `launch_main_window` from the already-persisted settings.
- **There is one way to reach the backend inside the feature: the sections import commands from `@/ipc/commands` directly** (`SttSection` → `listAudioOutputDevices`, `AutoModeSection` → `listAudioInputDevices`, `AppearanceSection` → `applyTheme` from `lib/window-controls`). There was a `LauncherPort` DI layer and it was removed: half the sections went around the context anyway, and two conventions in one feature cost more than a direct import. Only things that have state in `LauncherApp` arrive as props: `onRedeem` (which on success triggers the store's `reload` so the token flows into `settings`), `onCheckUpdates` and the whole `updater` — the "Updates" screen lives in the launcher, otherwise the `update-available` from the auto-check (which fires 5 s after start, when the launcher is exactly what is on screen) would go nowhere.

### Window chrome (HUD)

The `main` window is `transparent` + `decorations: false` (frameless, no native title bar) + `alwaysOnTop` + `visibleOnAllWorkspaces` + `contentProtected` (invisible during screen sharing; `Settings.screen_share_visible` lifts the protection through `set_content_protected`). On Windows two of these flags behave differently, and that is not a bug in the call: `visible_on_all_workspaces` silently does nothing (it is unimplemented in tao), and `contentProtected` works through `SetWindowDisplayAffinity` and requires **Windows 10 version 2004+** — on older builds the window will show up in a screen share.

**The protection state is visible in the HUD header** — `ScreenShareIndicator` in the `StatusBar`'s action cluster: a crossed-out eye in a neutral colour = the window is hidden from capture, a plain eye in `primary` = the window will appear in the recording. This is that sanctioned case of `primary` (an indicator, not a text colour), and it is "visible" that is made loud — the state the user must notice. **The indicator is clickable, and that is not decoration:** otherwise `screen_share_visible` lives only as a toggle in the launcher — the row "Show the window during screen sharing" is deliberately FIRST under "Behaviour" and is named in the tab's description, because it is the product's pivotal privacy property and used to be unfindable by browsing — and you can only get there by stopping the HUD (`stop_main_window` destroys the window). In other words, noticing mid-call that "I am visible", you would physically be unable to fix it without a clickable indicator. It does not create its own write path: the same `saveSettingsReportingError` → `set_settings` → `apply_screen_share_visibility_change` as any other setting. **An honest limit:** on Windows older than 10 2004, `set_content_protected` silently does nothing and the indicator will show "hidden" for a window that really is being captured; we do not detect the build number — the minimum supported one is 2004+ anyway.

**Size and rounding:**

- Mouse resizing by the invisible edges is allowed and is synced into the settings: `useNativeResizeSync` (App.tsx) listens to `onWindowResized` (`ipc/events.ts`, physical pixels → logical through scaleFactor), subtracts the preview extra and writes into `Settings.window_width/height` through `applyNativeWindowSize` (clamp + debounced persistence).
- **A target that matches the echo of the native size means "the user set the size with the mouse" — and then we do not touch the window AT ALL**: `useWindowFrameSync` bails out before `set_window_size` rather than merely skipping the guard. The echo is computed by `lib/window-size.nativeSizeEcho` — exactly what `applyNativeWindowSize` would have written into the settings from the last native size, complete with the clamp and the preview extra; the comparison is `windowSizesEqual`, and its epsilon must be NO stricter than Rust's `RESIZE_EPSILON_LOGICAL_PX`, otherwise the frontend sends requests that Rust discards on its own. Why a guard alone is not enough: the target is measured at the moment of the resize event, while Rust reads the current size two IPC hops and a re-render later (tens of milliseconds), and during a live drag the discrepancy always exceeds the epsilon — a tween starts, kills the previous one, its frames spawn new events, and the loop never settles. The guard window (600 ms) remains and is armed on programmatic changes. The resize event itself is coalesced through `requestAnimationFrame`: on Windows `WM_SIZE` arrives for every pixel of the drag, and without coalescing each one caused a full HUD re-render with a markdown re-layout. The `readyRef` gate is mandatory: an event arriving before the settings load would otherwise persist DEFAULT_SETTINGS (empty keys!) to disk.
- The rounding is duplicated natively: `platform::clip_native_window_corners` sets `cornerRadius = WINDOW_CORNER_RADIUS_LOGICAL_PX` (22, which must match the `--window-radius` CSS variable in `index.css` — used by the `.app-shell`, `DialogOverlay` and `ConnectivityOverlay`) + `masksToBounds` on the contentView's layer — otherwise WKWebView lags a frame behind during a resize tween and the right-hand corners would flash square. Do not remove the CSS radius while you are at it (the clip draws the shape, the CSS draws the background). On Windows the same call sets the DWM attribute `DWMWA_WINDOW_CORNER_PREFERENCE` = `DWMWCP_ROUND`: the radius there is the system's and is not configurable to 22px.

**Transparency and portals:** `html/body` are transparent and the background is painted by the root `.app-shell` through the `--app-opacity` alpha (the opacity slider sets the variable on `documentElement`; the CSS default `--app-opacity: 0.9` in `index.css` must match the `window_opacity` default — otherwise the window renders with a different opacity before the settings load). Do not override `.bg-background` globally: its only remaining consumer is `ConnectivityOverlay`, and that one must be opaque, otherwise the chat shows through the "no network" overlay. The others have moved off the class and must not be moved back onto it: the `Switch` thumb is coloured directly (`bg-foreground` when off / `bg-primary-foreground` when on), the `outline` button uses `bg-input/20`, and `DialogContent` uses `bg-popover` (see "Modals"). Portalled content (dialog/select/tooltip) needs `body { color: var(--foreground) }`, because it renders outside `.app-shell`.

**Modals:**

- `DialogOverlay` must be rounded with `rounded-[var(--window-radius)]` to match the window's radius: the window is transparent and frameless, and a `fixed inset-0` without rounding would fill the corner triangles with `bg-black/55` and they would stick out square beyond the rounding.

- **`DialogContent` is filled with `bg-popover`, not `bg-background`** (a change to stock shadcn). Elevation: in the launcher `bg-background` is the darkest step (`body.launcher`), and a modal on it sank BENEATH the `bg-card` cards it overlaps; `--popover` in both windows sits at the card's level or above, so the dialog reads as a raised surface.
- `DialogContent` does NOT use `overflow-hidden`: in WKWebView, `overflow:hidden` + `border-radius` on a `transform`ed element (the dialog is centred with `translate`) produces square corners; its own background respects the radius anyway, and the content inside `p-5` never reaches the corners.
- `DialogOverlay` must carry `duration-200` to match `DialogContent`: without it the backdrop faded out over tw-animate-css's default 150 ms while the content took `duration-200` — the background disappeared before the modal did.
- **Data the content of a modal with an exit animation depends on must not be cleared synchronously with the close** — the content has to survive until the animation ends. A modal opened by `open={target !== null}` must render its body from a latched copy of `target` (the sanctioned "adjust state during render" pattern) rather than from `target` itself: otherwise, when target is cleared, the body vanishes instantly while Radix still plays 200 ms of exit, and the modal collapses jerkily in height. A latch in such a place looks redundant — remove it and the jerk comes back.

**HTML preview of answers** is rendered by the built-in `PreviewPanel` (the right-hand column of the same window). The content is loaded from a separate origin (the custom scheme `register_uri_scheme_protocol("preview", …)` in `lib.rs`, serving `App.preview_html`, which is filled by the `set_preview_html` command) into an `<iframe src sandbox="allow-scripts allow-same-origin">` — `localStorage`/network work, but being cross-origin to `tauri://localhost` plus the absence of a capability for the scheme isolates the preview from IPC and from the keys. **The scheme's address is platform-specific** — `preview://localhost` on macOS against `http://preview.localhost` on Windows — so the origin is never assembled by hand: it is built by `ipc/preview.previewUrl` through Tauri's own `convertFileSrc("", "preview")`, and that is **the only place on the frontend that knows about the scheme**; a hardcoded `preview://localhost` simply will not load on Windows. The nonce in the iframe's `src` (`…/?v=N`) is mandatory: it forces WKWebView to reload the iframe even for identical HTML and kills the race between rapid opens (a stale `setPreviewHtml` response is ignored). Opening it widens the window in place through `useWindowFrameSync` (`set_window_size`).

**The teleprompter** (`Teleprompter`, an `absolute inset-0` overlay above `.app-shell`) is the answer's text, large and centred (`toReadingText` strips the markdown), with smooth autoscroll through a single rAF loop (the scroll is a programmatic `scrollTop` on `overflow-hidden`; the offset is computed by `advanceOffset` from dt so the speed does not depend on the frame rate), a fade mask at the edges and a focus band in the centre ("the eye stays in one place"). The container is `overflow-y-auto` (manual scrolling with the wheel; `onScroll` syncs `offsetRef` so the autoscroll continues from the new position rather than jumping back). Space pauses, Esc closes. Position/speed/font are persisted on unmount (`onPersist` in the cleanup — which also catches closing by hotkey): App keeps `{text, offset}` in a ref and on reopening restores the offset if `teleprompter_resume` is set and the text is the same. The text is the streaming `partial`, or otherwise the assistant's last answer.

**The left (chat) column has a derived fixed width** (`chatColumnWidth = window_width − 2·SHELL_PADDING_PX` in App.tsx — symmetric at both edges of the window), NOT `flex-1`: otherwise, while the panel is mounting, `flex-1` would squeeze the chat on every tween frame (a markdown re-layout → visible jitter). The width changes only in discrete steps via the resize hotkey; during the preview tween the column is stable — the panel is simply clipped by `overflow-hidden` while the window is narrow and appears as it widens; the chat is not re-laid-out and the main thread stays free for the tween.
- **The window height changes only by the user.** The height is set by `Settings.window_height` (the `resize_modifier`+↑/↓ hotkey); UI logic never touches the height. The width is that same base plus the preview: the window is `window_width` + `PREVIEW_EXTRA_WIDTH_PX` when the preview is open, all through `useWindowFrameSync` → `set_window_size` (the effect is gated on `!settingsLoading`, otherwise the default would overwrite the persisted size Rust applied at startup).
- **There are two platforms and they are not equal in capability.** macOS 14.2+ (a Core Audio process tap) and Windows 10 version 2004+ (WASAPI loopback). On Windows two things structurally do NOT exist: the system audio recording permission (loopback has none — `permissions::AUDIO_REQUIRES_PERMISSION`) and the screen recording permission (`screen_capture_access`/`request_screen_capture_access` return `true`); also `0600` is not applied there and `visible_on_all_workspaces` is a no-op. Identical on both: external links open through the platform shell (`open(1)` / `ShellExecuteW`), but **the "`http://`/`https://` only" filter lives in the shared `platform::open_web_url`** — deliberate protection against `file://`/`smb://`, and it must not be duplicated in the backends; the system settings panes are `x-apple.systempreferences:` against `ms-settings:`.
- **The process name is "Audio System" by default (a build-time stealth choice), and the `harpyhare.ai` brand is only a caption in the UI.** `productName` + `mainBinaryName` + the window `title` = `Audio System`, identifier = `com.audioservice.helper` (`tauri.conf.json`) → `CFBundleName`; the executable (`Contents/MacOS/Audio System`, i.e. `ps`/`proc_name`/Activity Monitor/the menu bar) and the window metadata (`CGWindowList` owner+title) uniformly show "Audio System"; on Windows the same `productName` yields `Audio System.exe` in Task Manager and an identical entry in the list of installed programs (NSIS, per-user installation, with WebView2 downloaded by the bootstrapper). The `harpyhare.ai` brand (`lib/brand.BRAND_NAME`) is shown only inside the app (a caption in the settings — seen by the user alone). The user cannot change this name — it is set at build time. An accepted ceiling: `contentProtected` hides the window's pixels from capture but NOT the fact of its presence — the process and the window (`CGWindowListCopyWindowInfo` on macOS, enumerating windows and processes on Windows) are always visible; there is no hiding from a dedicated detector on the same machine. Impersonating system processes (`com.apple.*`) is deliberately NOT used: an ad-hoc signature plus somebody else's namespace is itself a signature of a fake and breaks TCC/notarisation. The build artifacts (`Audio System.app.tar.gz`, the dmg, `Audio System_<version>_x64-setup.exe`) are named with a space (Tauri takes `productName` verbatim); in `release.mjs` the uploaded assets and the URLs in `latest.json` use the ASCII slug `AudioSystem` — GitHub replaces spaces with dots in asset names and would break the updater's link.

### Region screenshot

The `screenshot` action's hotkey (default ⌘⇧A / Ctrl+Shift+A) or the `Crop` icon in the Composer toolbar → select a region → the PNG goes as an attachment into the active chat's draft. The shared part (`screenshot.rs`) is the permission check, `backend::capture_region()`, base64 and the events; each platform has its own overlay. On macOS it is **C code compiled into the app's binary** (`src-tauri/native/region_capture.c`, built by `cc` in `build.rs` **only on macOS**, exporting `harpy_capture_region`/`harpy_capture_region_free`, with the Rust wrapper in `screenshot/macos.rs`). The source came from the `harpyshot` plugin (the `harpyhare-plugins` repository) but lives here as a copy: it must not be a sidecar process — the "Screen Recording" TCC grant is keyed by cdhash, and a separate ad-hoc binary would be asked about again after every rebuild, whereas the app itself has one grant per bundle.

Invariants of the macOS C overlay (break them and you get a crash or a hung UI):

- **The full-screen capture happens BEFORE the overlay is shown** (`CGDisplayCreateImage` through `dlsym` — the symbol is deprecated but present on macOS 26), and the selected region is cut out of it afterwards with `CGImageCreateWithImageInRect`. Otherwise our own dimming would end up in the frame. `contentProtected` keeps the HUD window out of the PNG, but **that alone is not enough**: the overlay is transparent and shows the live screen, so a HUD invisible to capture still physically covers the region being selected — which is why the host side hides the window before the capture (see below).
- **The overlay's ObjC classes are registered once**: `objc_getClass` before `objc_allocateClassPair` is mandatory — on a second call `allocateClassPair` returns NULL and `objc_registerClassPair(NULL)` crashes the app (the original plugin did not have this problem: its process lived for a single activation).
- **NSWindow is subclassed for the sake of `canBecomeKeyWindow = YES`** — otherwise a borderless window never becomes key and never receives keyDown, meaning Esc would not cancel the selection.
- **Every event of our own loop is forwarded into `[NSApp sendEvent:]`** — the `nextEventMatchingMask` loop spins inside the app's main thread, and without the forwarding the entire rest of the app stands still while the user drags the frame.
- **Call it from the main thread only** (`app.run_on_main_thread`) — this is AppKit; both the command and the hotkey handler go through `screenshot::on_capture_region`.
- The main display only (`CGMainDisplayID`); multi-monitor is a separate task.

The Windows overlay (`screenshot/windows.rs`) is its own Win32 on GDI, and the traps are the same in meaning but different in mechanics: **the capture of the whole VIRTUAL screen happens BEFORE the window is shown** (`SM_XVIRTUALSCREEN`…, multi-monitor is supported, and the origin may be negative — do not assume it is zero); **the window class is registered once per process** (`OnceLock`: a repeat `RegisterClassW` would return 0 — exactly the same trap as `objc_allocateClassPair` in the ObjC version, and for the same reason: the process survives many activations); drawing uses double buffering with invalidation only of the changed area (the frame plus its previous position), otherwise there would be a full-screen repaint on every mouse move; **`PostQuitMessage` is NOT called** — a `WM_QUIT` would kill Tauri's own message loop, and leaving the local loop goes through a state flag instead; cancellation is Esc, the right mouse button or too small a selection; the result is a PNG without alpha.

The host side: the permission is checked in Rust BEFORE the overlay (`platform::screen_capture_access`; on Windows there is no such right and the function always returns `true`, so the "no access" branch is simply unreachable there); no access → a `screenshot-error` with the `permission` code goes out **with no system prompt** (prompts live only on the "Permissions" screen, see below). Success → the PNG in base64 → `screenshot-ready` → `useRegionScreenshot` → **`useChats.addDraftImage`, i.e. the same attachment pipeline as pasting/dropping an image** (`fileToAttachment`, downscaling above 5 MB, the attachment limit, writing into `images/` and assigning an id) — the screenshot has no image-handling branch of its own. **The HUD window is hidden for the duration of the screenshot, and the whole handler moved into `tauri::async_runtime::spawn` (`run_capture`) for that reason.** We hide it ALWAYS, not only when content protection is off: with the default settings the window is `contentProtected` and did not appear in the PNG before either, but the selection overlay is transparent and the HUD physically covers the very area the user is trying to select — that was the original complaint; and with `screen_share_visible` there is no protection at all and the window would land right in the frame. `window::hide_for_screen_capture` hides the `main` window only if it is visible, waits `SCREEN_CAPTURE_HIDE_SETTLE` = 120 ms and returns whether we were the ones who hid it; the pause is mandatory because BOTH backends capture the whole screen BEFORE showing the overlay, so the window must have physically left the screen rather than merely logically — the countdown starts after `hide()` has run on the main thread and the compositor's transaction has been committed, so 120 ms is headroom on top of one or two frames. **The `spawn` here is mandatory, not an extra layer:** `capture_region_screenshot` is a synchronous command, i.e. it executes on the main thread, and `run_on_main_thread` called FROM the main thread runs the closure INLINE (tauri-runtime-wry 2.11.4) — before the fix, clicking the `Crop` icon started the overlay's nested event loop right inside the IPC handler, and the blocking `is_visible()` getter in the hiding would have waited on itself. The capture itself is therefore marshalled separately (`capture_on_main_thread` — `run_on_main_thread` + `oneshot`, like `window::on_main_thread`), preserving the "`backend::capture_region()` from the main thread only" invariant. `run_capture` brings the window back through `window::show_and_focus_prompt`: on success always, so not only the window but also the caret in the prompt field returns (a question about the attachment can be typed immediately, with no mouse click), and on cancel or error only if we were the ones who hid it, because a HUD the user hid must stay hidden. **Re-entry is cut off by the RAII guard `CaptureSlot`** on top of `App.screenshot_capturing` (claimed in `on_capture_region`, released in `Drop`): `run_on_main_thread` gets through even INTO the overlay's nested loop (on macOS tao's proxy-event CFRunLoopSource lives in the common modes and fires inside `nextEventMatchingMask`; on Windows `GetMessageW(NULL)` picks up tao's thread messages), so pressing the hotkey a second time during an in-flight screenshot would run `harpy_capture_region` recursively on top of its own global state (`g_full`, `g_view`) — a double `CGImageRelease`. The flag is cleared in `Drop` specifically, not by a separate call: a panic inside the task would otherwise leave it raised forever, the screenshot would become a silent no-op until a restart, and the window would stay hidden. **The guard's price is accepted knowingly:** a repeat call during an in-flight screenshot is silently ignored, and the frontend learns nothing about it through any event. The IPC contract did not shift because of the window hiding: no commands and no events were added — the window is hidden from Rust, not from JS. **The same PNG goes to the clipboard** (`screenshot::copy_to_clipboard`, mirroring how `recording::deliver_transcript` puts the transcript there) — the screenshot can be pasted into any other app without re-saving it. This costs the `image-png` feature on the `tauri` crate in `Cargo.toml`: `tauri::image::Image::from_bytes` is declared under `#[cfg(any(feature = "image-ico", feature = "image-png"))]`, and without it the method simply does NOT exist — the error looks like "no such method" rather than "enable the feature". The feature is shared by both platforms and creates no `#[cfg]` branch, so `bindings.ts` does not diverge because of it. The ACL did not need touching: `capabilities/default.json` gates only `invoke` from the webview, and we write to the clipboard from Rust. The hotkey is registered in `window::register_main_window_hotkeys` (the HUD's lifecycle, like PTT/toggle/teleprompter) and re-registered in `set_settings`; while the HUD is not running it is not listened for. The settings UI is the "Hotkeys" group on the settings screen; the "Screen Recording" permission is granted on the "Permissions" screen.

### Permissions (the single place where rights are granted)

This whole section is **about macOS**: on Windows WASAPI loopback has no permission at all (`permissions::AUDIO_REQUIRES_PERMISSION = cfg!(target_os = "macos")` — the audio status is `granted` straight away, with no prompts and no probes), and neither does screen recording, so the "Permissions" screen is hidden there entirely (`screens.ts`, the `platforms` field). **The readiness gate is nevertheless derived ONLY from `permissions_status`, not from the screen's visibility**: on Windows the command returns `granted`, no blocker arises, and there is nowhere to lead. The temptation to write "audio is required only if the permissions screen exists" must be resisted: any edit to the screen registry (moving permissions inside "Settings", another platform) would then silently drop the audio access requirement — exactly the regression the gate lives in the launcher to prevent. The permission commands stay in the contract on both platforms. The `audio_permission_requested`/`screen_permission_requested` fields are unused on Windows and remain in `Settings` deliberately: the shape of the settings and the bindings must match on both platforms.

Every TCC permission is granted from one launcher screen (`features/launcher/screens/PermissionsScreen`, with data from the `usePermissions` hook on top of `permissions.rs`). There is no modal: on the first launch the launcher opens on the blocker's screen by itself (`LauncherPanel`, the `landed` ref + `readiness.blockers[0].screen`), and the rest of the time the screen is reachable from the sidebar. There are no scattered granting points any more and none must be created: `useCapturePermission`/`useScreenCapturePermission`, the permission banner in the HUD, the "Screen Recording" row on the hotkeys tab and six separate commands (`capture_available`, `request_audio_capture_permission`, `open_audio_permission_settings`, `screen_capture_available`, `request_screen_capture_permission`, `open_screen_capture_settings`) have all been deleted — three commands replaced them: `permissions_status`, `request_permission(kind)`, `open_permission_settings(kind)`.

**No system prompt must ever appear on its own** — only in response to the "Grant" button. Two invariants follow:

- **`setup_app` does NOT create the capture** (`App.capture` starts as `None`). Creating a Core Audio tap *is* the permission request: it used to be built at startup and macOS showed the prompt on the very first launch, before the user had pressed anything. The capture is raised lazily — `recording::ensure_capture` when the HUD launches and on an explicit permission request. Do not bring `build_capture` back into `setup_app`. **And do not call it from `launch_main_window` synchronously** — only through `spawn_blocking`: creating the capture is slow (on Windows starting the WASAPI thread waits up to 5 seconds for readiness), and `launch_main_window` is a synchronous command, so waiting inside it holds up the whole launch: the HUD window is already created but the webview has no time to paint (a white window), and the launcher is not destroyed because its `destroy` has not been reached. A window's lifecycle must not depend on audio readiness: with no device the HUD still opens, and PTT reports the error honestly.
- **The audio state cannot be known without a prompt** (Core Audio has no preflight, unlike `CGPreflightScreenCaptureAccess`), so the first request is recorded by the `Settings.audio_permission_requested` flag: while it is `false` the status is `unknown` and no probes are made; after the first press of "Grant" the status is determined and a repeat probe is safe (a prompt is possible only when the status is "not asked"). For the same reason `rebuild_capture_now` (an audio device change) bails out early while the capture has never been built and the flag is not set.
- **`screen_permission_requested` is about "have we asked", not about the access itself.** `CGPreflightScreenCaptureAccess` does not distinguish "denied" from "not asked yet", and without that distinction the modal would pop up on every launch for anyone who deliberately declined an optional permission. Hence: preflight `true` → `granted` (even with no flag — access may have been granted outside the app), otherwise the flag decides between `denied` and `unknown`. Auto-opening the modal is driven by `needsAttention` (audio not granted OR the screen has not been asked about yet), not by `allOk`.

`PermissionState` is `unknown | granted | denied`. Audio is required (without it the HUD launch button is disabled); screen recording is not — it is needed only by the region screenshot. The microphone is likewise optional: it is needed only by auto mode, and its absence blocks nothing.

**A permission row's geometry does not depend on its state** — and that is not cosmetics. The TCC prompt for audio is asynchronous: the command returns `denied` before the user presses "Allow", i.e. the status changes right under the cursor, and any dependence of the sizes on the state would yank the button out from under a finger. Hence: a fixed-width action column (`grid-cols-[…_14rem]` — exactly the same control column that `SettingRow` uses in `fields.tsx`; the former `10.75rem` prevented the controls of neighbouring screens from lining up on a common vertical), `min-w-18` on "Grant", `min-h-9` on the explanation (so one and two lines take the same space), and the same set of buttons for `unknown` and `denied` — for `denied`, "Grant" works as a repeat probe and catches exactly that case ("they allowed it at the prompt after the command had already returned a refusal"); only `granted` removes the buttons, and the row's height does not change because of it. A missing permission is announced by the status in the header next to the "Launch" button: it names the blocker in words and a click leads to its screen — we never leave a `disabled` without an explanation.

### The launcher: header, sidebar, screens

The launcher window has three parts: the **header** (`LaunchBar`: brand, search, readiness status, "Launch"), the **sidebar** (`Sidebar`) and the **screen** (`ScreenShell` + its content). The screen registry is `screens.ts` (`LAUNCHER_SCREENS`: id, label, description, icon, group and an **optional list of platforms**: without it the screen exists everywhere, and with `platforms: ["macos"]` — "Permissions" — it is not rendered on Windows at all); the sidebar draws the `content` group (Contexts, Presets) at the top and the `system` group (Settings, Permissions, Updates) pinned to the bottom with `mt-auto` — **the pinning was reviewed live and confirmed by the owner: do not remove it**, even if the emptiness between the groups looks like a hole in the layout. **The sidebar is icons only, with no labels at any width** (`w-10`): there used to be labels, but with a second rail inside the settings two text columns ate a third of the window. The user sees the screen's name in `title` and in the `ScreenShell` heading, so no meaning is lost. A dot on an item is a `SidebarNotice {screen, label, kind}` (readiness blockers and an available update), and **`label` must end up in the item's `title`** ("Permissions — No access to system audio recording"): in an icon-only sidebar, without it there is a dot with nowhere to ask what it means.

**The launcher's header sits on the line of macOS's traffic lights.** The window's title bar is given over to the content: `platform::merge_titlebar_into_content` (called at the end of `create_launcher_window`) uses objc to set `NSWindowStyleMaskFullSizeContentView` + `titlebarAppearsTransparent` + `titleVisibility = hidden`; on Windows this is a deliberate no-op (it has its own frame there). The builder's `title_bar_style`/`hidden_title` are deliberately not used — they are `#[cfg(target_os = "macos")]`, and a `#[cfg]` branch must not be introduced in the middle of the shared `window.rs` (see the platform splitting rule); the `platform::` facade is the same technique used for `clip_native_window_corners`. Consequences: the header (`h-9`) must have a left inset for the window buttons on macOS (`PLATFORM === "macos"` on the frontend — we never ask Rust for the platform), and dragging the window by the header is now ours (`useWindowDrag`), because the webview covers the native title bar.

**Inside the "Settings" screen there is a second, nested rail of tabs** (`settings-tabs.ts` + `SettingsTabsRail`, seven tabs matching the number of sections; the registry is built like `screens.ts`). Before it, all seven sections hung in a single scroll and finding anything was hard. Three consequences that are easy to break:

- **The breakpoint is `min-[900px]`, not `lg`/`md`, and it was calculated rather than guessed**: the launcher window opens at 1000×720 with a minimum of 520 (`window.rs`). At `lg` (1024) a default-sized window would show one rail as icons; at `md` (768) the first rail is already 160px and there is no room left for the second one's labels. 900 is the only threshold at which the default window has labels and a narrow one does not tear.
- **The tab labels are deliberately short** ("Ключи", "Клавиши", "Действия" rather than "Ключи и доступ"…): with two rails the long ones were truncated with an ellipsis right in the interface. The expanded meaning is carried by `description`, which the screen prints as a line above the section.
- **`SettingsScreen` renders the sections through a `Record<SettingsTabId, ReactNode>`, not a `switch`** — the compiler then requires a section for every tab in the registry. The tab order in the registry follows how often the tasks come up, not the alphabet and not the order in which they appeared, which is why "Действия" comes before "Окно" (a rare task) — do not re-sort them.

**Search across the launcher** (`search.ts` + `LauncherSearch` in the header, centred between the brand and the launch button). The index is built FROM THE REGISTRIES rather than retyped by hand: screens from `LAUNCHER_SCREENS` (with the same `screenGroup` platform filter), hotkeys from `HOTKEY_ACTIONS`, settings tabs from `SETTINGS_TABS` (the label AND the description — a tab is found by what is inside it), permission rows from `PERMISSION_ROWS`, API keys from `API_KEY_IDS`, and the window steps and the quick actions' "Combination" row derived from `hotkeyAction(...)`; the user's presets, quick actions and library materials arrive through the `SearchSources` parameter. Only the list of ordinary settings rows (`SETTINGS_ROWS`) is written by hand — their labels must match the text in the sections word for word, otherwise the search will find wordings that are not on screen; so renaming a row in a section ("Язык" → "Язык распознавания") is always a paired edit. **The `PERMISSION_ROWS` registry was moved out into `features/launcher/permission-rows.ts` rather than left in the screen's file**: it has two consumers (the screen and the search), and exporting data from a file containing a component breaks fast refresh (`react-refresh/only-export-components`; an array does not fall under `allowConstantExport`, and the rule is disabled only for `components/ui/**`). Permission hits are gated by the screen's own visibility (the same `screenGroup`), so they do not appear in the results on Windows. **`API_KEY_IDS` (`lib/api-keys.ts`) is the only list of keys**: a third copy had started to grow in the search, and it would have drifted silently. **The `opacity` action is excluded from the index** by the `HOTKEYS_WITHOUT_SETTINGS_ROW` constant: there is no settings row for the opacity modifier on any tab, and the hit led into "Окно" to a row that does not exist — a dead route. Once such a row appears, remove the exclusion. **A hotkey's tab is derived from `kind`, not from a list of ids**: `combo → hotkeys`, `modifier_arrows`/`modifier_plus_minus → window`, `modifier_digits → quick-actions` — otherwise "Прозрачность" and "Скролл переписки" would lead into "Клавиши", where they are not configured. Clicking a result switches the screen AND the tab in one `goTo({screen, tab})`. **The search results are single-line hits** (title on the left, breadcrumb on the right in `text-hint`, the container on `shadow-pop`) rather than two-storey rows: this is the command-palette pattern (Raycast/VS Code), while the former two storeys repeated the identical "Настройки → …" breadcrumb on every consecutive row — half the list's height went to duplicates. **The header's wrapper in `LauncherPanel` must be `relative z-30`, and that is not decoration**: the results (`z-20`) live INSIDE it, and `.launcher-rise` is an animated element for which WebKit keeps its own stacking context (`animation-fill-mode: both`), so the `z-20` is locked inside the wrapper; the screen block comes later in the DOM and, without the header's layer being raised, painted OVER the results — the settings cards showed through the list and some hits hid beneath them. It is the whole wrapper that must be raised: during the entry animations all three rise wrappers become stacking contexts at once. **The results must carry `data-no-drag`**: the header as a whole is the window's drag zone (`useWindowDrag`) and the list hangs beneath it, so a click on any non-interactive spot (the gap between rows, "Ничего не найдено", the overflow row) dragged the window instead of selecting. **There is deliberately no global shortcut such as ⌘K for the search** — hardcoded combinations are forbidden in this project and the launcher has no hotkey infrastructure of its own; if one is needed, add it as an action in the `hotkeys.rs` registry. Filtering is done by a single `screenGroup(group, platform)`; the readiness gate does NOT rely on screen visibility (see "Permissions"). No modals are left in the launcher: permissions and updates are full screens, not dialogs.

- **Only `ScreenShell` renders a screen's heading and description**, from the data in `screens.ts`. A panel must not grow headings of its own — otherwise the old tautology returns, where a tab's label was repeated by the heading of the card inside it. Both sit on ONE line: the heading is `shrink-0`, the description next to it is `truncate` plus a `title` with the full text — so **a long description in `screens.ts` will not wrap, it will be cut off**, and you must not count on a second line.
- **Readiness is structural, not boolean.** `useLauncherReadiness` returns `blockers: {label, screen, tab?}[]`, `checking` and `ready`. `tab` is carried by the keys blocker (`"access"`), so both the header status and the first screen you land on lead to a specific tab rather than merely to the "Settings" screen; `DEFAULT_SETTINGS_TAB` currently coincides with it, but you must not rely on that coincidence — it is cosmetic. `checking` (`!permissions.loaded`) is mandatory: before `permissions_status` answers, `audioOk` is `false`, and without that flag a fully configured user saw "no audio access" and a disabled launch button on EVERY start. The launch button is disabled while `checking || !ready || launching`, and the status next to it names the first blocker in words and leads to its screen.
- **The first screen is chosen by the blocker** (the `landed` ref in `LauncherPanel` — exactly once per window session, after the permissions have been queried). No keys → "Settings" + the tab from `blocker.tab`; no audio → "Permissions"; everything fine → `DEFAULT_SCREEN`.
- **The settings form speaks one language across every row** (`fields.tsx`): `SettingGroup` (**the heading and description are OUTSIDE the card** — a `SectionLabel` plus an explanation above it, with only rows separated by `divide-y` inside the `rounded-lg` card; there is no header inside the card any more), `SettingRow` (label + explanation on the left, the control in a fixed-width column on the right), `SettingBlock` (when the control takes the full width), `SettingSelect`/`SettingSwitch`/`SettingSlider`. The former `Field`/`SelectField`/`SwitchRow`/`SectionColumns` were deleted: a field's label and a toggle's label were drawn in two different ways, and the three-column grid broke long labels.
- **`SectionLabel` is the only uppercase micro-step in either window** (`text-hint` + `font-semibold` + `tracking-wider` + `uppercase`): the `SettingGroup` heading, the `HotkeysPopover` groups, the sections of the "Context" dialog, the library's folders and the preview's header all go through the component — do not duplicate that string of classes in the markup. There is no other uppercase anywhere in the interface except the `LaunchBar`'s brand line: uppercase marks exactly one level of the hierarchy, and a second such step must not be introduced.
- **A bounded number is only ever set with a slider plus a readout.** A bare `type=number` for `move_step`/`resize_step`/`scroll_step`/`buffer_seconds` was removed deliberately: `Number("")` gave 0, and a value typed above the limit stayed in the UI even though Rust had already clamped it on disk (`draft` is synced from `settings` only for `access_token`). A slider physically cannot leave `SETTINGS_LIMITS` — there is no desync by design. **A dependent row is greyed out, not hidden**: "Глубина буфера" is always rendered and goes `disabled` when `buffer_enabled` is off (a `SettingSlider` prop, which also mutes the readout). Conditional hiding jolted the card's height when the toggle flipped and left a dead route in the search — a hit led to a row that was not on screen at that moment.
- **Paired settings live in one row.** A modifier and its step (move / resize / scroll) are configured together in `WindowSection`; the modifier used to be on the "Hotkeys" tab and the step on the "Appearance" tab, three times over.
- **The launcher's surfaces are separated by lightness, not by alpha.** The overrides live in `body.launcher` (and `:root[data-theme="black"] body.launcher` — otherwise the black theme would not get through, because of equal specificity): `--background`/`--card`/`--popover`/`--surface`/`--surface-active` are opaque steps, and `--ring` is detached from `--primary` (a burgundy ring at 50% alpha was practically invisible in the settings window). **The order of the steps matters: in the launcher `--popover` (0.245) is LIGHTER than `--card` (0.21)** — that is precisely the elevation of menus, popovers and dialogs above the form's cards; equalise them and a dropdown merges into the card it hangs over. The neutral base is deepened in both themes (launcher 0.17/0.12, HUD 0.25/0.16 for gray/black) — do not raise it any lighter: the contrast of the `oklch(1 0 0 / 8…12%)` hairline borders rests on it. This is the only seam that does not touch the HUD: the windows are different documents but `index.css` is shared, so nothing is edited in `:root` for the launcher's sake.
- The font scale is `--text-hint`/`--text-caption`/`--text-body`/`--text-chat`/`--text-title` (`cn` knows about them through the `font-size` group in `lib/utils.ts`); do not invent other steps, there are none. **The `components/ui/*` primitives have been moved off raw `text-sm`/`text-xs`/`text-lg` onto the scale's steps**: Tailwind's 14px on a button, an input and a select against the 12.5px of `--text-body` on the label beside them meant a control larger than its own label. The primitives are shared by both windows, so the HUD got the same scale — that is not a side effect but a condition: two scales cannot be held inside one set of primitives. Changing `--text-body`/`--text-caption` globally is still not allowed — the whole chat layout rests on them.
- **Switching a screen or a tab is an entry animation, and it must have a `motion-reduce` exit.** The content wrappers carry `key={screen}` / `key={tab}` (without a remount the animation will not restart) and `animate-in duration-150 fade-in-0 slide-in-from-bottom-1 motion-reduce:animate-none` — the same pattern and the same tw-animate-css duration as `SelectContent`/popovers; the window's entry cascade is `.launcher-rise` at 0.38s with a `RISE_STEP_MS` = 50 ms step per wrapper. **The `@media (prefers-reduced-motion: reduce)` block in `index.css` silences both the entry cascade and both infinite animations — `.launcher-rise`, `.eq-bar`, `.thinking-shimmer`**: if you introduce your own `@keyframes`, add it to the same selector, otherwise with animation disabled system-wide it will be the one remaining twitching detail. Transform and opacity animations over cards are allowed here even though they are forbidden in the HUD (see "A message's action buttons"): unflushed compositing-layer pixels are an artifact of a TRANSPARENT frameless window, and the launcher is opaque (`body.launcher` fills the background and the window is built without `transparent`) — the `.launcher-rise` precedent has lived there for a long time and leaves no traces.

### Hotkeys: the action registry

Every keyboard command in the app is listed **in one place** — `src-tauri/src/hotkeys.rs`, the `HOTKEY_ACTIONS` constant (which travels into the bindings through `.constant()`, and the frontend reads the very same thing). An action has an `id`, `group`, `label`, `hint`, `kind`, `scope` and `default_combo`. There are no hardcoded combinations left in the code and none may be introduced: both Rust and the frontend ask `hotkeys::effective(&settings.hotkeys, ACTION_X)` / `effectiveCombo(settings.hotkeys, "x")`.

- **`kind`** — `combo` (a full combination), `modifier_arrows` (a modifier + arrows), `modifier_plus_minus` (a modifier + `+`/`−`) and `modifier_digits` (a modifier + a digit 1…`QUICK_ACTION_LIMIT`; its only carrier is `quick_action`). Families are not expanded into a binding per key: only the modifier is stored for them, and a family's label is produced by `comboLabel` from the `KIND_HINTS` table in `lib/hotkeys.ts` — the "1…9" there is likewise derived from `QUICK_ACTION_LIMIT` rather than written out as a literal.
- **`scope`** — where the action is listened for: `global` (an OS shortcut, living alongside the HUD), `recording` (only while a recording is in progress), `hud` (webview handlers), `teleprompter` (only while the teleprompter is open).
- **`scope: global` is described in the registry but registered by a second, independent list — the `GLOBAL_HOTKEYS` table in `window.rs`** (triples of id + `register_*`/`unregister_*`). Drift between them is silent: a global action forgotten in the table is NEVER registered and produces neither an error nor a line in stderr — the settings field exists in the launcher, the hint exists in the HUD's popover, and the hotkey simply does not work. Locked down by the `window/tests.rs::global_scope_actions_and_the_registration_table_agree` test: the check runs in both directions (every `Global` action must be in the table, every row of the table must be `Global` in the registry) and both lists are read by code rather than enumerated as id literals — otherwise the test would be edited together with the bug.
- **An empty `combo` = "not assigned"**, and the action is simply not registered. `normalizeDraft` in the launcher no longer substitutes the default for an empty value — otherwise a hotkey you removed would come back by itself.
- **`default_combo` is not a string but a pair of platforms** (`PlatformCombo {macos, windows}`): Rust takes its own through `.current()` and the frontend through `defaultCombo(id, platform)` defaulting to `PLATFORM`. The primary modifier is derived by the `primary_combo!` macro (⌘ on macOS, Ctrl on Windows), so the pairs are not written out by hand. **On Windows the Win key is not offered as a modifier** — it is taken by the system's window snapping, and `Win+Shift+S` is the system screenshot outright; locked down by the `windows_defaults_avoid_the_super_key` test (which checks both the defaults and `MODIFIER_COMBOS.windows`). The Windows defaults: `Ctrl+R` (record), `Ctrl+Shift+L` (auto mode), `Ctrl+Enter`, `Ctrl+Shift+A` (screenshot), `Ctrl+Shift+D` (focus the input field), `Ctrl+Shift+H`, `Ctrl+Shift+N` (duplicate the chat), `Ctrl+Shift+T` (teleprompter), `Ctrl` (move the window and quick action), `Ctrl+Shift` (size and opacity), `Alt` (scroll); the only ones shared across platforms are `Escape` (cancel recording, close the teleprompter), `Space` (pause the teleprompter) and `Alt`. **Not a single F-key is left in the defaults**: `record` was `F9`, `teleprompter` was `F10`, and the screenshot was ⌘⇧S / Ctrl+Shift+S; they are inconvenient, and the defaults were pulled towards what the owner set by hand anyway (⌘R and ⌘⇧A), with the teleprompter picked from the offered options. **The price is knowingly accepted:** a global shortcut takes the combination away from the whole system while the HUD is running — ⌘R/Ctrl+R stops reloading a page in the browser, and ⌘⇧T/Ctrl+Shift+T stops reopening a closed tab. **Users who sat on the defaults move together with the default** (an empty `hotkeys[]` = "everything from the registry", and `effective` takes the value from `HOTKEY_ACTIONS`): F9 dies for them and recording moves to ⌘R — a migration pinning old installations to the previous values was discussed and rejected, and the move is deliberate; anyone who configured their combinations by hand notices nothing. **The default tests do not copy the values as literals** but ask the registry (`effective(&[], ACTION_X)` in Rust, `defaultCombo(id, platform)` on the frontend) — otherwise the next default change would break half a dozen tests in four files and they would be edited together with the bug; literals remain exactly where the platform substitution ITSELF is checked (`⌘R` against `Ctrl+R` in the `hotkeyGroups` labels). The registry tests (`hotkeys/tests.rs`) run parsing and conflict-freedom for BOTH platforms, not for the current one: the test host's platform says nothing about the other.

**A conflict = an overlap in keys AND coexisting scopes.** The overlap: two `combo`s match on modifiers and key (case and modifier order do not matter, and `KeyS` and `S` are the same thing); two families of the same kind match on the modifier; a `combo` conflicts with a family if its modifier matches and its key falls into the family (an arrow, `+`/`−` or a digit 1…9). Different families on the same modifier do NOT conflict — which is exactly why the default "resize" and "opacity" both live on ⌘⇧ / Ctrl+Shift, and "quick action" peacefully shares a bare ⌘ / Ctrl with "move the window". The only scopes that do not coexist are `recording` and `teleprompter`, which is why `Esc` legitimately sits on both cancelling a recording and closing the teleprompter.

**The resolution policy is to take it from the previous owner** (as IDEs do): a new assignment is always applied and the conflicting action is left with no hotkey, which the UI reports with the line "‹combination› was taken from the action ‹name›". This rule is implemented twice and both implementations are covered by tests: `hotkeys::normalize` in Rust (the last one in the list of bindings wins; called from `Settings::clamp`, i.e. on every `set_settings`) and `assignHotkey` on the frontend (`lib/hotkey-conflicts.ts`, giving instant feedback and a `stolenFrom` list). They must not diverge — the overlap rules are mirror images and the test cases match in meaning. **A new `kind` must appear in BOTH implementations**, and the mirror has already drifted once: Rust knew about the digits family and `fallsIntoFamily` on the frontend did not, so assigning `send` to ⌘1 did not show "⌘1 was taken from the action 'Quick action'", while `Settings::clamp` silently removed that hotkey on disk after the fact. **The theft note is rendered where the user ACTED, not where the victim lived**: `stolen` carries both `from` and `to`, and `StolenNote` filters by the group of the `to` action (with no `group` prop it does not filter at all — which is how the single-section `WindowSection` and `QuickActionsSection` show it). The former filter by the victim's group stayed silent in precisely the most common case — theft across groups and across tabs: you assign a combination in "Клавиши" that was taken from an action in "Окно", and no explanation appeared anywhere.

**Migration.** `hotkeys::migrate_legacy_fields` edits the raw JSON **before** deserialisation into `Settings` (`Settings::load`): seven old fields turn into bindings, values matching the default are not carried over, and the fields themselves are removed from the json. If `hotkeys` is already non-empty, the migration does nothing. That is why the user's custom combinations survive an update while `Settings` does not drag legacy fields along. A side effect of the default change: a very old json with `hotkey: "F9"` now migrates into an EXPLICIT `record: F9` binding (previously the value matched the default and was discarded) — so legacy installations do stay on F9, unlike those sitting on an empty `hotkeys[]`.

**The key vocabulary.** `Shortcut::from_str` (tauri) accepts letters, digits, F1–F24, arrows, `Space`/`Enter`/`Tab`/`Escape`/`Backspace`/`Delete`, `Home`/`End`/`PageUp`/`PageDown`, punctuation and the numpad. The bottleneck used to be the frontend: `hotkeyFromEvent` only handled letters, digits and F-keys — it now returns `event.code` for everything listed above (letters and digits are normalised into the short form). **`Escape` remains the capture's cancel** in `HotkeyCapture`, so it cannot be assigned with the mouse — it only ever arrives as a default, and the row's reset button brings it back.

**The hot path.** The `keydown` handlers do not parse the combination string on every press: `prepareCombo` is called once in an effect (`useWindowControls`, `Teleprompter`, `useDuplicateChatKey`), and chat scrolling still keeps `parseModifier` in an effect (`AnswerPanel`). Otherwise auto-repeating arrows would allocate an array on every frame.

**Deliberately not configurable:** `↵` (send) and `⇧↵` (a line break) in the input field — that is text-field behaviour, not an app command; `⌘V`/`Ctrl+V` is a paste event, not a hotkey. In the HUD's reference they are shown as separate hints — `fieldHints(platform)` in `lib/hotkeys.ts` (it used to be the `FIELD_HINTS` constant and became a function: the labels are platform-specific and the group comes from the registry rather than a literal).
