# Фокус в поле промпта: автоматический и по хоткею

## Задача

Каретка должна оказываться в поле ввода промпта сама, без клика мышью, в четырёх ситуациях:

1. при запуске HUD;
2. после возврата из снимка области экрана;
3. после того как окно спрятали и показали снова;
4. по явному хоткею — в любой момент, из любого приложения.

Хоткей настраивается на экране «Настройки → Горячие клавиши» лаунчера, как остальные.

## Мотив

Сейчас `.focus()` не вызывается во фронте ни разу. После скриншота Rust возвращает окну нативный фокус (`window::show_and_focus_main`, зовётся из `screenshot.rs`), но DOM-фокус не восстанавливает — пользователь снимает область и обязан кликнуть в поле, чтобы дописать вопрос. То же после каждого показа спрятанного окна.

## Решение

### Одна точка «поднять HUD и поставить каретку»

Три из четырёх моментов сходятся в существующую функцию `window::show_and_focus_main` (`show()` + `set_focus()`). Она переименовывается в **`show_and_focus_prompt`**, дополняется эмитом события `focus-prompt` и становится единственным смыслом «активировать HUD для ввода»:

| Момент | Кто зовёт |
| --- | --- |
| после скриншота | `screenshot::deliver` — уже зовёт, правок не требует |
| после скрытия и показа | show-ветка `window::on_toggle_visibility` — вместо собственных `show()` + `set_focus()` |
| по хоткею | новый обработчик глобального хоткея |
| при запуске | **не Rust**: эффект маунта во фронте |

Запуск намеренно вынесен во фронт: окно создаётся раньше, чем вебвью успевает подписаться на события, и эмит из Rust ушёл бы в никуда.

### Почему событие, а не оконный фокус

Отвергнутая альтернатива — слушать во фронте `tauri://focus` и фокусировать поле на любой активации окна. Это ломает выделение текста в ответе и клики по кнопкам при возврате в приложение мышью, и при этом не покрывает главный случай — «окно уже активно, нажали хоткей». Ещё одна отвергнутая альтернатива — обрабатывать хоткей во фронте: глобальный шорткат регистрируется только в Rust, а keydown в вебвью не приходит, когда окно не в фокусе.

## Состав изменений

### 1. Реестр действий

`hotkeys.rs`: одна запись в `HOTKEY_ACTIONS`.

| поле | значение |
| --- | --- |
| `id` | `focus_prompt` |
| `group` | `Отправка` (там же `send` и подсказки поля ввода) |
| `kind` | `Combo` |
| `scope` | `Global` |
| `default_combo` | `primary_combo!(shift_token!(), "D")` → `Cmd+Shift+D` / `Ctrl+Shift+D` |

Из реестра бесплатно приезжают: строка редактирования в лаунчере (`HotkeysSection` перебирает действия с `kind === "combo"`), подсказка в поповере HUD (`hotkeyGroups`), разрешение конфликтов обеими реализациями (`hotkeys::normalize`, `assignHotkey`), прогон дефолтов обеих платформ существующими тестами реестра. Миграция не нужна — действие новое, пустой `hotkeys` означает «всё по дефолтам».

**Конфликта с ⌘⇧ нет**: на этом модификаторе живут семейства «изменить размер» (стрелки) и «прозрачность» (`+`/`−`), а `D` не попадает ни в одно из них — ровно как уже сосуществующие ⌘⇧S и ⌘⇧H.

### 2. Регистрация хоткея

`hotkey.rs` — `register_focus_prompt` / `unregister_focus_prompt` по образцу `register_screenshot`; обработчик обязан идти через `defer` (реентрант-дедлок реестра плагина). `window.rs` — пятая строка в `GLOBAL_HOTKEYS`. Жизненный цикл (регистрация на `launch_main_window`, снятие на `stop_main_window`) и перерегистрация в `set_settings` подхватываются существующим кодом.

### 3. Событие

`events.rs` — константа `focus-prompt`, пустой payload, типизированный хелпер. Зеркало в `EventMap` (`ipc/types.ts`) и утверждение в `ipc/contract.test.ts`.

### 4. Фронт

Новый хук `usePromptFocus`:

- владеет `promptRef` на textarea; `App` пробрасывает его в `Composer` → `PromptTextarea`, где он **заменяет** нынешний приватный ref и продолжает обслуживать авторост — второго ref не появляется;
- фокус на маунте (запуск) и по событию `focus-prompt`;
- каретка ставится **в конец текста**: иначе после диктовки или скриншота печатать пришлось бы в начало строки;
- запрос игнорируется, пока открыт телесуфлёр — поле под полноэкранным оверлеем, а `Space`/`Esc` там принадлежат суфлёру.

### 5. Тесты

- `usePromptFocus.test.ts` по образцу `useRegionScreenshot.test.ts`: фокус на маунте, фокус по событию, тишина при открытом суфлёре, каретка в конце текста.
- `hotkey/tests.rs`: разбор нового дефолта.
- Реестровые тесты `hotkeys/tests.rs` покрывают новое действие сами (прогон обеих платформ, отсутствие конфликтов, обход клавиши Win на Windows).

### 6. Документация

`apps/desktop/CLAUDE.md`: раздел «Хоткеи: реестр действий» (пятое глобальное действие), список событий, новый смысл `show_and_focus_prompt` в разделах про управление окном и про снимок области.

## Границы

Хоткей возврата из HUD в лаунчер в эту работу не входит — возврат остаётся кнопкой в шапке HUD.

## Риски

- **DOM-фокус сразу после `show()`** может не прилипнуть, пока окно не стало key в WKWebView / WebView2. Проверяется вручную; лечится доресфокусом по `tauri://focus`, но закладываться заранее не нужно.
- **PTT при сфокусированном поле.** `usePttSuspend` глушит PTT только для комбинаций, конфликтующих с печатью; дефолтная `F9` не конфликтует. Но поле теперь в фокусе с первой секунды — проверить, что запись работает сразу после запуска.
