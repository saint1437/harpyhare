# Коды доступа: бесплатный режим через прокси владельца

Дата: 2026-07-09. Статус: дизайн (реализация не начата).

## Задача

Владелец раздаёт **одноразовые уникальные коды доступа**. Пользователь вводит код в
приложение и дальше пользуется LLM и STT бесплатно — за счёт API-ключей владельца.
Ключи владельца не должны быть извлекаемы с машины пользователя.

## Модель угроз

Пользователь **враждебен**: полный контроль над своей машиной, бинарём, файлами,
памятью процесса и трафиком. Отсюда два неустранимых следствия, принятые by design:

1. Всё, что попало на машину пользователя, извлекаемо. Поэтому реальные ключи
   Anthropic/Groq на клиент не передаются **никогда и ни в каком виде** (ни в бинаре,
   ни по сети после активации, ни «зашифрованными»).
2. Выданный пользователю токен доступа извлекаем и может быть расшарен. Токен — это
   не секрет системы, а персональный ключ с потолком расходов: утечка токена = утечка
   квоты одного пользователя, гасится отзывом.

## Архитектура: код → токен → прокси

```
[приложение] --код--> [прокси /v1/redeem] --> одноразовое погашение, выдача токена
[приложение] --Bearer токен--> [прокси] --x-api-key/gsk_--> Anthropic / Groq
```

Ключи владельца живут только в секретах прокси-сервера. Клиент при непустом
`access_token` переключает **оба** API-клиента (`AnthropicClient`, `GroqStt`) на
base URL прокси — сеамы `with_base_url` уже существуют (llm.rs:219, stt.rs:79),
меняется только источник авторизации: `Authorization: Bearer <token>` вместо
`x-api-key` (LLM) и вместо `gsk_`-ключа (STT, там уже Bearer).

## Формат кода

- 20 символов Crockford Base32 группами `XXXXX-XXXXX-XXXXX-XXXXX` — 100 бит энтропии
  из CSPRNG. Никаких счётчиков/дат/смысла внутри — чистая случайность.
- **Без брендового префикса** — стелс-требование проекта: строка вида `HARE-…` в
  переписке/логах — фингерпринт продукта.
- Нормализация ввода: uppercase, дефисы/пробелы игнорируются, Crockford-маппинг
  I→1, L→1, O→0 (прощает опечатки).
- В БД хранится **только** `sha256(normalized_code)`. Плейнтекст печатается
  админ-инструментом ровно один раз при генерации, нигде не логируется.
- Атрибуты кода: `batch_label` (кому выдана партия — для пост-фактум отзыва
  перехваченных кодов), `quota_profile`, `expires_at` непогашенного кода (30–90 дней).

## Активация (redeem)

1. UI: поле «Код доступа» в `MissingKeysDialog` (главная точка входа без ключей)
   и в `SettingsDialog` → «Ключи API».
2. Фронт → IPC-команда `redeem_access_code(code)` → Rust-модуль `access.rs` →
   `POST {PROXY}/v1/redeem` `{code, idempotency_key}`.
3. **Идемпотентность обязательна**: клиент генерирует случайный idempotency-ключ,
   персистит его ДО запроса и ретраит с ним же. Сервер дедуплицирует (тот же ключ →
   тот же токен, плейнтекст токена доступен по этому ключу короткий TTL). Без этого
   потерянный ответ (таймаут, обрыв) навсегда сжигает одноразовый код.
4. Сервер: rate-limit по IP (≈10 попыток/час) → одноразовость строго **одним
   атомарным CAS-стейтментом**:
   `UPDATE codes SET status='redeemed', … WHERE code_hash=? AND status='unused'`,
   `rows_affected==1` — единственный источник истины. Никогда SELECT-затем-UPDATE,
   никогда eventually-consistent хранилище (Cloudflare KV **запрещён** для стейта
   кодов/токенов — двойная активация на двух edge).
5. Ответ на «нет такого кода», «уже погашен», «отозван» — **один и тот же** (никакого
   оракула перебора). Плюс глобальный circuit breaker на всплеск 4xx.
6. Клиент, порядок как в `set_settings`: сохранить `Settings` на диск (ошибка =
   reject, память не тронута) → обновить in-memory → пересобрать ОБА клиента →
   событие фронту. Код эфемерен: не персистится, не логируется.

## Токен

- Opaque случайные 256 бит (`префикс_` + base64url). **Не JWT**: нечего парсить =
  нечего подделывать; отзыв и квоты всё равно требуют lookup — сервер проверяет
  `sha256(token)` в БД на каждом запросе, ревокация действует со следующего запроса.
- Хранение на клиенте: плейнтекстом в `settings.json` (0600, атомарная запись) — тот
  же уровень доверия, что у сегодняшних ключей пользователя. Осознанно: токен = квота
  этого пользователя, не ключи владельца.
- Состояния: `active | suspended (квота) | revoked`. TTL — решение владельца
  (например 180 дней со скользящим продлением); refresh-протокола нет — при
  истечении пользователь получает новый код (минимум машинерии).
- На 401/403 от прокси клиент токен **не стирает** (временный сбой прокси не должен
  уничтожить рабочий токен) — помечает статус, баннер «Код доступа недействителен —
  введите новый» с полем повторного ввода.

## Прокси-сервер

**Рекомендация: Cloudflare Workers (Paid, $5/мес) + D1 + Durable Objects.**
Один Worker ~300–400 строк TS. Секреты (`ANTHROPIC_KEY`, `GROQ_KEY`, `ADMIN_TOKEN`) —
только `wrangler secret put`, не в коде/репо. Домен — нейтральный, без бренда.

Почему не альтернативы:

- **Vercel — дисквалифицирован**: лимит тела запроса 4.5 МБ и буферизация входящего
  тела ломают главный путь — стриминговый chunked-аплоад аудио неизвестной длины
  (до ~19 МБ за 10 минут записи).
- **VPS (Hetzner + Caddy + axum + SQLite)** — план Б: технически безупречен для
  стриминга, но добавляет опс (патчи, TLS, бэкапы). Архитектура переносится 1:1.

Роуты — **строгий allowlist точных (method, path), никакого prefix-форвардинга**
(иначе прокси — открытый релей во весь Anthropic API: `/v1/messages/batches`,
`/v1/files` и т.д. за счёт владельца):

| Роут | Auth | Поведение |
|---|---|---|
| `POST /v1/redeem` | — (IP rate-limit) | активация кода |
| `POST /v1/messages` | Bearer | квоты → форвард с `x-api-key` из секрета; SSE вниз — побайтовый passthrough без переписывания (SseParser клиента чувствителен к точным `data: ` и `\n\n`) |
| `GET /v1/models` | Bearer | форвард (иначе фронт тихо деградирует на FALLBACK_MODELS и capabilities собираются эвристиками) |
| `GET /v1/models`, `GET /openai/v1/models` | без auth | **статический 200, upstream не трогать** — это `warm_up()` клиента (старт + каждый PTT) |
| `POST /openai/v1/audio/transcriptions\|translations` | Bearer | `fetch(groq, {body: request.body, duplex:'half'})` — chunked-тело течёт к Groq по мере записи, НЕ буферизуется (иначе ломается «отпустил PTT → текст»); таймауты ≥ 11 мин |
| `/admin/*` | ADMIN_TOKEN + Cloudflare Access | админка |
| всё остальное | — | 404 до любого upstream-fetch |

От клиента форвардятся только allowlist-заголовки `anthropic-version` /
`anthropic-beta` (логика fast-mode остаётся на клиенте). Ошибки прокси — всегда
`{"error":{"message":"…","code":"…"}}` (клиент уже парсит `error.message`); коды:
401 токен недействителен, 402 квота исчерпана, 413 тело больше лимита, 429 rate-limit.
Upstream-ошибки пере-заворачиваются (не форвардить сырые тела — могут нести
идентификаторы аккаунта владельца).

## Квоты и анти-абьюз (все — на сервере; клиентские лимиты бессмысленны)

1. **Лимит конкуренции — обязательный**: максимум 1 LLM-стрим + 1 STT-стрим на токен
   одновременно (легитимному приложению больше не нужно), через сериализованное
   хранилище (Durable Object / атомарный lease с TTL), проверка ДО форварда.
   Это одновременно убивает главный обход квот (параллельный fan-out до коммита
   счётчиков) и обесценивает шаринг токена.
2. **Списание до форварда**: floor-оценка стоимости (по размеру тела / max_tokens)
   списывается при старте, сверка по реальному `usage` из SSE после. Tee-парсер
   usage работает под `waitUntil` и дочитывает upstream **даже при обрыве клиента**
   (иначе обрыв соединения перед `message_stop` = бесплатные токены).
3. Счётчики — только атомарный increment-then-check
   (`UPDATE … SET n=n+1 WHERE n<limit`), никогда check-then-increment.
4. Суточные капы per-token (профиль): токены LLM in/out, минуты аудио (по байтам,
   1.92 МБ ≈ минута, плюс кап wall-clock), запросы/день, burst/мин.
   Исчерпание → 402 с человекочитаемым message.
5. **Обрезка тела во время стрима**: byte-counter не просто считает, а **абортит**
   запрос при превышении (STT ~25 МБ, LLM ~20–30 МБ — base64-скриншоты истории
   должны влезать). Пост-фактум учёт обходим бесконечным телом.
6. Валидация запроса: allowlist моделей (только используемые приложением), кламп
   `max_tokens`, `web_search` — отключить или отдельно метрить и капить (server-side
   tool биллится отдельно; иначе прокси = бесплатный SERP-API). `metadata.user_id`
   ставит сервер (хэш-префикс токена), клиентское значение игнорируется.
7. Глобальный дневной circuit breaker по суммарному расходу → 429 всем
   (деградация вместо счёта на тысячи).
8. **Провайдерский рубеж — обязателен до раздачи первого кода**: ОТДЕЛЬНЫЙ Anthropic
   workspace с monthly spend cap + ОТДЕЛЬНЫЙ Groq-ключ со спенд-лимитом, оба не от
   основного аккаунта. Единственный контроль, который переживает любой баг учёта,
   расшаренный токен и полную компрометацию прокси: худший случай = сумма cap.

## Изменения в клиенте

- `settings.rs` — поле `access_token: String` (дефолт `""`); `#[serde(default)]` уже
  даёт совместимость старых `settings.json`. **Синхронно** зеркалировать в
  `src/ipc/types.ts` (`Settings` + `DEFAULT_SETTINGS`) — иначе первый же save полного
  Settings с фронта (включая дебаунс прозрачности) сотрёт токен пустым дефолтом.
- Новый `src-tauri/src/access.rs`: `PROXY_BASE_URL` (https-литерал), redeem-запрос,
  идемпотентность. Env-override `ITECH_PROXY_ENDPOINT` (паттерн `update.rs`) —
  **только под `cfg!(debug_assertions)` и только https**: безусловный override в
  релизе + `.env`-чтение из cwd = ридирект токена и всего контента на чужой хост.
- `lib.rs`: команда `redeem_access_code` в `generate_handler!`; выбор режима клиентов
  в setup (строки ~180, ~244); `rebuild_changed_api_clients` — сравнение
  `access_token` пересобирает ОБА клиента; `apply_key_fallback` не подставляет
  `.env`-ключи при непустом токене.
- `llm.rs` / `stt.rs`: `enum ApiAuth { ApiKey(String), ProxyBearer(String) }`;
  ветка bearer в `messages_request` и `list_models`; в прокси-режиме
  401/403 → текст «код доступа недействителен» (не «проверь ключ»), 402 → «лимит
  исчерпан». **Инвариант STT**: 401 от прокси обязан классифицироваться как
  `BadApiKey` — единственная ошибка без фолбэка на повторный батчевый аплоад.
- Приоритет режимов: непустой `access_token` глушит оба ключа — один источник
  истины, смешанного режима нет.
- `src/lib/api-keys.ts`: `missingApiKeys` → `[]` при непустом токене (начинать
  отсюда — pure-слой с юнит-тестами). UI: поле кода в `MissingKeysDialog` и блок
  статуса/отвязки в `SettingsDialog`; браузерный мок — `?badtoken` по образцу
  `?nokeys`.
- `warm_up()` не меняется: бьёт в `{base_url}/v1/models` без auth, прокси отвечает
  дешёвым 200 — прогрев TLS/H2 до хоста прокси сохраняется.
- Ни код, ни токен не попадают в логи/stderr клиента (там уже есть `[perf]`-вывод).

## Админ-инструменты

CLI-скрипт (в приватном репо Worker'а, НЕ в harpyhare) поверх `/admin/*`:
`gen --count N --profile default --label "кому"` (плейнтексты печатаются один раз),
`list-tokens` (расход, last_seen, флаги аномалий), `revoke <prefix|batch>`,
`suspend/resume`, `usage --days N`. `/admin/*` — под длинным ADMIN_TOKEN
(constant-time сравнение) + Cloudflare Access (бесплатный zero-trust) поверх.
В логах — только 8-hex хэш-префиксы.

## Обязательный шаг 0 (до написания клиентского кода)

Однодневный прототип Worker'а и живой прогон реального приложения через
`with_base_url`:

1. 10-минутная запись STT-стримом — аплоад обязан течь инкрементально
   («отпустил PTT → текст сразу», а не «аплоад после отпускания»);
2. длинный SSE-ответ с паузами — паузы < 60 s `read_timeout` клиента, `\n\n` доходят
   байт-в-байт, нет обрывов на H2 keep-alive 30 s / `pool_idle_timeout(None)`;
3. обрыв соединения посреди стрима — учёт usage всё равно коммитится.

Если хоть один пункт падает — план Б: VPS (Hetzner + Caddy `flush_interval -1`,
buffering off, таймауты 12 м + axum + SQLite), схема переносится 1:1.

## Принятые остаточные риски

- Токен извлекаем и шарим; обладатель может скриптовать прокси curl'ом в рамках
  allowlist/квот (аттестации клиента нет). Ограничение — квоты + конкуренция 1+1 +
  ревокация, устранение невозможно.
- Код перехватываем в канале доставки (кто первый активировал — того и токен);
  лечится expires_at + связью партия→получатель для отзыва.
- Прокси — SPOF: его падение кладёт LLM и STT всем токен-пользователям сразу.
- Ревокация не убивает уже открытый стрим (макс. один, ограничен капами).
- Даунгрейд приложения на версию без поля молча теряет токен при первом save →
  нужна админ-процедура перевыдачи.
- Весь контент промптов и аудио проходит через инфраструктуру владельца —
  вопрос доверия пользователей (no-log политика).
- Новый постоянный исходящий хост в трафике процесса — наблюдаемый артефакт
  (нейтральный домен смягчает; аналогично уже существующему хосту пресетов).
